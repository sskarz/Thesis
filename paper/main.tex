\begin{abstract}
Assistants that \emph{act}---edit a file, lock a car, place an order---do so by emitting \emph{tool calls} that a surrounding program executes. Running that loop on a local machine with a small language model (under five billion parameters) keeps data private and costs nothing per request, but small models often fail when a task takes several dependent calls. We study why, on the multi-turn base split of the Berkeley Function Calling Leaderboard (BFCL v4; 200 tasks graded by the final state of a simulated backend), using Gemma-4-E2B-it served locally on a MacBook Pro.

Three findings stand out. First, the failures are about \emph{state}, not \emph{syntax}. Gemma-4-E2B-it itself scores 83.1\% on single-call selection (823/990), yet completes only 27.0\% of multi-turn tasks through the native tool API, and most remaining errors are tools that never ran or a world that ended in the wrong state. Forcing syntactically valid output makes things worse (10.5\% and 13.5\%). Second, \emph{structured inference-time control} helps without any training. Writing calls as JSON text (IFFC), a harness-written state scratchpad, stopping on repeated calls, and a four-line status card that pushes the model to act rather than abstain together reach 77/200 (38.5\%, 95\% interval 32.0--45.4\%), +8.0 points over JSON text alone (paired McNemar $p=0.023$, uncorrected for multiple comparisons). This configuration was chosen after earlier results on the same 200 tasks. It beats a five-sample majority vote (36.5\%) without that method's roughly sevenfold generation time. A three-part minimal recipe without the scratchpad reaches 35.5\%. Third, fine-tuning on public and synthetic tool data did not help. The best supervised fine-tune reached 15.0\%, clearly below the untuned model; preference tuning reached 26.5\%, within noise of it, and models trained on a rebuilt mix scored 1--2/20 on a 20-task gate where the untuned model with the status card scores 17/20. A null test that pushes the untuned model's own answers through the same pipeline scored 15/20, which rules out the pipeline; the exact data cause remains open. With 200 tasks, neighbouring differences of a few points are within noise; the gap between inference-time control and the best supervised fine-tune is not.
\end{abstract}

\section{Introduction}
\label{sec:intro}

A useful assistant has to act, not only chat. To check a calendar or lock a car, a language model emits a \emph{tool call}: a machine-readable request (a function name plus arguments) that a surrounding program---the \emph{harness}---runs against a \emph{backend}, here a simulated vehicle or filesystem, and whose result is fed back to the model (Figure~\ref{fig:vignette}). Real tasks need several dependent calls in a row (\emph{multi-turn} or \emph{consecutive} tool calling): look up a value, use it, check the outcome, and know when to stop.

Running this loop locally with a \emph{small language model} (SLM; under five billion parameters here) keeps private data on the device, works offline, and has no per-request cost. The catch is accuracy. We measure Gemma-4-E2B-it~\cite{gemma4e2b}, a two-billion-effective-parameter model, on BFCL v4~\cite{patil2024bfcl}, served with llama.cpp~\cite{llamacpp} on a MacBook Pro (Apple M4~Pro, 48~GB). Out of the box, through the native tool interface, it completes 27.0\% of 200 multi-turn tasks.

We tried two families of fixes over several months: changing what happens \emph{at inference time} (how calls are written, what the harness shows the model, when the harness stops), and changing the \emph{weights} with supervised fine-tuning and preference optimization. This paper reports what that body of measurements says about \emph{why} small models fail and \emph{what helps}. Our contributions:

\begin{enumerate}
  \item \textbf{A failure anatomy: state, not syntax.} On the same hardware, the same model scores 83.1\% on single-call selection but fails most multi-turn tasks. After calls parse, the dominant errors are \emph{under-calls} (a required tool never ran) and \emph{state mismatches} (tools ran, but the world ended wrong). Decoders that force valid output lower accuracy to 10.5--13.5\% (Section~\ref{sec:fail}).
  \item \textbf{Training-free control that helps.} JSON-text calls plus a state scratchpad, a gated stop rule and a status card reach 38.5\% (77/200) with no weight updates, +8.0\pp over JSON text alone (McNemar $p=0.023$ uncorrected; not significant after correcting for the eight tests we ran). This full stack was assembled after seeing earlier results on the same tasks. A minimal three-part recipe without the scratchpad reaches 35.5\%, and a five-sample vote reaches 36.5\% at about $7\times$ generation time. The card works mainly as an act-versus-abstain control. We report Wilson 95\% intervals and exact McNemar tests on per-task results (Section~\ref{sec:helps}).
  \item \textbf{Evidence on how fine-tuning goes wrong, with controls.} Fine-tuning on public data taught the model to stop early (0.5\%); the best repair reached 15.0\%, below the untuned model. Models trained on a rebuilt mix collapsed on a 20-task gate (1--2/20 where the untuned model scores 17/20), and a null test (15/20) clears the training pipeline. An autopsy pointed to a shift in the kinds of calls in the training mix as a \emph{candidate} cause; targeted retrains did not confirm it (Section~\ref{sec:train}).
\end{enumerate}

\section{Background and Related Work}
\label{sec:related}

\paragraph{Benchmark.} The Berkeley Function Calling Leaderboard (BFCL) evaluates language models as API callers~\cite{patil2023gorilla,patil2024bfcl}. Its single-turn categories check one emitted call against a reference with an abstract-syntax-tree (AST) matcher. A \emph{turn} is one user request and everything the model does before handing control back. Its multi-turn categories run the model in an agent loop against simulated backends (for example VehicleControl and GorillaFileSystem, a sandboxed Unix-like filesystem) and compare the backends' final state to a reference. We use the \emph{multi-turn base} split (200 tasks, all tools available). Accuracy here is the fraction of the 200 tasks whose final state matches; it is not the public overall BFCL score, which averages many categories.

\paragraph{Output channel.} With \emph{native function calling} (NFC), the server receives a tool list and the model returns structured \texttt{tool\_calls}, as in most production APIs. With \emph{instruction-followed function calling} (IFFC), the model is instead asked in the prompt to write its calls as a JSON list in ordinary text, which the harness parses. Taheri et al.\ report that small models follow such JSON instructions more reliably than native tool APIs on single-turn BFCL~\cite{taheri2026iffc}; we use their single-model variant (their Appendix~B).

\paragraph{Constrained decoding.} Grammar-constrained generation restricts the next token so that output is always valid, for example to a JSON schema or to a list of tool names~\cite{willard2023outlines,dong2026xgrammar2}. Format restrictions can also reduce answer quality~\cite{tam2024format}. Yu et al.\ constrain tool names with a prefix-tree automaton~\cite{yu2026ptc}.

\paragraph{Prompting and test-time compute.} Guided-structured templates add a reasoning scaffold before calls~\cite{he2025gst}. Context-compression methods summarize long histories~\cite{kang2025acon}; our scratchpad is instead written by the harness from executed results. Typed observe--orient--decide--act (OODA) controllers structure agent steps~\cite{guo2026ooda}; our status card borrows only the name. Spending extra inference compute, for example by sampling several answers and voting, is a standard alternative to scaling parameters~\cite{snell2024testtime}.

\paragraph{Training for tool use.} Specialist small callers such as xLAM~\cite{zhang2024xlam}, Hammer~\cite{ye2025hammer} and FunctionGemma~\cite{google2025functiongemma} are trained on synthetic tool data such as ToolACE~\cite{liu2024toolace} and APIGen~\cite{liu2024apigen}. \emph{Supervised fine-tuning} (SFT) trains the model to reproduce target responses; we use low-rank adapters (LoRA)~\cite{hu2021lora}, small trainable matrices added to a frozen model, with MLX~\cite{mlx}. \emph{Direct Preference Optimization} (DPO) instead trains on pairs of preferred and rejected responses~\cite{rafailov2023dpo,jung2025diatool}.

\section{Setup and Methods}
\label{sec:setup}

\paragraph{Models and serving.} The multi-turn model is Gemma-4-E2B-it, quantized with Q4\_K\_M (a 4-bit weight-quantization format of llama.cpp), served by \texttt{llama-server} (llama.cpp build 8111) with Metal acceleration on a MacBook Pro M4~Pro with 48~GB of memory. Decoding is greedy (temperature 0) except for majority voting. Most runs used four parallel server slots and a 65{,}536-token context; the native-API baseline used eight slots, a difference we return to in Section~\ref{sec:limits}. Peak process memory for the multi-turn jobs is about 15~GB. For the single-turn contrast we also serve Qwen2.5-3B~\cite{qwen25}, Llama-3.2-3B~\cite{llama32}, Qwen3.5-4B~\cite{qwen35} and FunctionGemma-270M~\cite{google2025functiongemma}.

\paragraph{Inference-time interventions.} All of these leave the model weights untouched and use the same checker (Appendix~\ref{app:method} gives the exact rules):
\begin{itemize}\setlength{\itemsep}{1pt}
  \item \textbf{JSON in text (IFFC)} instead of the native tool API (NFC).
  \item \textbf{State scratchpad.} After each executed call, the harness writes a short snapshot of facts from real results (current directory, known files, last calls) into the conversation.
  \item \textbf{Stop on repeats.} The harness ends a turn when the model re-proposes calls it has already executed, but only once at least six tool steps have occurred in the current user request, so short legitimate re-calls are not cut off. An \emph{ungated} variant stops at the first repeat.
  \item \textbf{Status card.} A four-line card (goal, known facts, last call and its outcome, and an advisory next move: call, ask, finish or refuse) is prefixed to the latest user message. It is filled deterministically from the conversation and executed results; it never sees reference answers. We call this the OODA card after the observe--orient--decide--act loop it loosely mirrors. The card stacked on stop-on-repeats (JSON text + stop + card) is our \emph{minimal recipe}.
  \item \textbf{Vote of five (Best-of-N, BoN).} At each step, sample five candidate calls at temperature 0.7, execute the most common one, and continue; applied on top of the scratchpad.
  \item \textbf{Full stack (headline).} JSON text + scratchpad + stop on repeats + status card, with the scratchpad written before the card in each user message. Greedy decoding; no sampling.
  \item \textbf{Forced-valid decoding.} \emph{Constrained decoding} restricts output in two passes: first to an empty list or a list of valid tool names, then arguments to each tool's schema (an approximation of tag-triggered grammars~\cite{dong2026xgrammar2}). A \emph{tool-name automaton} constrains only the name and leaves arguments free, inspired by~\cite{yu2026ptc}.
\end{itemize}

\paragraph{Training-time interventions.} We train LoRA adapters on Gemma-4-E2B-it with MLX, merge, quantize to Q4\_K\_M and evaluate with JSON-in-text calls. Early mixes combine ToolACE multi-turn dialogues with sampled xLAM data; later mixes filter or rebalance specific target types. A later \emph{rebuilt mix} (30{,}000 training rows) combines about 45\% newly simulated, execution-checked episodes with cleaned public data. We also train one full DPO model.

\paragraph{Early checks.} A 200-task run takes hours, so trained models first pass cheaper checks: a 10-task tripwire and a 20-task gate. Both use fixed tasks drawn from the same 200-task split, and the two sets are disjoint. The 20 gate tasks were chosen after the inference-time experiments, using historical per-task results. Neither check is a 200-task accuracy; Section~\ref{sec:gates} reports how well each predicts the full ranking.

\paragraph{Error labels.} Each failed task gets one primary label: \emph{empty turn} (no call on a turn that needed one), \emph{under-call} (a required tool never ran), or \emph{state mismatch} (tools ran but the backend's final state differs from the reference).

\paragraph{Statistics.} We report Wilson 95\% intervals computed from counts; a Wilson interval is a confidence interval for a proportion that stays accurate for small counts. For paired comparisons on the same 200 tasks we report how many tasks only one condition solves, computed from per-task results in our evaluation database (a task is correct if the checker logged no error for it). A McNemar test is a paired test that uses only the tasks where two conditions disagree; we report exact two-sided binomial p-values (Table~\ref{tab:mcnemar}). We ran eight planned tests; p-values are uncorrected, and we note where a Holm correction for eight tests changes the conclusion.

\section{Where Small Models Fail}
\label{sec:fail}

\paragraph{One call is easy; a chain is not.} On single-call BFCL categories, Gemma-4-E2B-it itself is competent (Table~\ref{tab:st}): through the native API it scores 823/990 (83.1\%, Wilson interval 80.7--85.3\%) on the same five categories used for the other models (simple, multiple, irrelevance, Java, JavaScript), comparable to Qwen3.5-4B (82.5\%). On multi-turn tasks, the \emph{same model, quantization and server} completes only 54 of 200 (27.0\%). So the gap is a within-model contrast between choosing one call and carrying a chain of calls through a changing state, not a difference between models.

\paragraph{After calls parse, errors are about the world.} Figure~\ref{fig:fail} breaks down failed tasks. Switching from the native API to JSON text reduces empty turns (59 to 41) but leaves state mismatch as the largest bucket (68 to 60). The two conditions fail together on 124 tasks. Across all inference-time conditions, state mismatch and under-call make up most failures, concentrated in VehicleControl and the filesystem: with the scratchpad, 22 and 21 of the 64 state mismatches respectively.

\paragraph{Forcing valid syntax hurts.} If failures were mostly malformed output, guaranteeing valid output should help. It does the opposite. Two-pass constrained decoding scores 21/200 (10.5\%; interval 7.0--15.5\%), 20.0\pp below JSON text, with 70 under-calls and 95 state mismatches. The tool-name automaton scores 27/200 (13.5\%; 9.4--18.9\%), with state mismatch rising to 102. Our two-pass approach approximates, rather than reproduces, full grammar engines~\cite{dong2026xgrammar2}, and we have not audited the token-level mechanism. Still, the measured effect is large and in the wrong direction: on this task, a valid call is not a correct next step.

\paragraph{JSON text over the native API (+3.5\pp).} Writing calls as JSON text scores 61/200 versus 54/200 natively. Paired, JSON text solves 22 tasks the native run misses and loses 15 (McNemar $p=0.32$, not significant). Part of this gap may come from serving: the native run used eight parallel slots and the others four.

\paragraph{State scratchpad (+3.5\pp).} The harness-written snapshot scores 68/200; versus JSON text it gains 20 tasks and loses 13 (McNemar $p=0.30$, not significant). Empty turns fall (41 to 31) while state mismatches do not (60 to 64), so the scratchpad mainly helps the model remember to keep calling.

\paragraph{Stop on repeats (+2.0\pp) and the status card (minimal recipe, 35.5\%).} Stopping on a repeated call, but only after six tool steps in the request, scores 65/200 (versus JSON text: gains 11, loses 7; $p=0.48$). Stopping at the \emph{first} repeat instead scores 54/200: all 37 forced stops were on tasks that failed, so stopping at the first repeat never rescued a task. Adding the status card on top scores 71/200: +3.0\pp over stop-on-repeats alone (gains 26, loses 20; $p=0.46$) and +5.0\pp over JSON text (gains 26, loses 16; $p=0.16$), neither significant. Against the native API it gains 37 and loses 20 ($p=0.033$ uncorrected; not significant after Holm correction), and part of that gap is the output format. The card is best read as an act-versus-abstain control: empty turns fall from 38 to 17, while state mismatches rise from 60 to 71. It helps the model act, not track state better.

\paragraph{Majority vote: the costly upper bound (36.5\%).} Voting over five samples on top of the scratchpad scores 73/200, two tasks more than the minimal recipe and four fewer than the greedy full stack below. Versus the greedy scratchpad it gains 17 and loses 12 (McNemar $p=0.46$, not significant), and it cuts filesystem state mismatches from 21 to 13. It costs about $7\times$ the generation wall-clock (about 3.0 to 21.3 hours for 200 tasks) and about $5\times$ the server requests (8.4 to 42.7 per task), from a single sampling seed. For an on-device agent, the greedy full stack below is both cheaper and more accurate.

\paragraph{Full stack: the best measured result (38.5\%).} Combining all four greedy changes (JSON text, scratchpad, gated stop-on-repeats and the status card, with the scratchpad written before the card) scores 77/200 (38.5\%, interval 32.0--45.4\%) in 175 minutes for 200 tasks, without sampling. Paired against JSON text it gains 30 tasks and loses 14 ($p=0.023$), the only inference-time gain that is significant before correction. Against the minimal recipe (+19/$-13$, $p=0.38$), the scratchpad alone (+24/$-15$, $p=0.20$) and the vote of five (+24/$-20$, $p=0.65$) the differences are within noise. Two caveats apply. This configuration was assembled \emph{after} we had seen the earlier results on the same 200 tasks, so its lead is subject to tuning leakage. Its harness code is on an unmerged branch (draft pull request \#90, commit \texttt{c894ec6}), run from a separate worktree with the same model, quantization and server.

\paragraph{How sure are we?} Every interval in Table~\ref{tab:ladder} is about $\pm6$--7\pp wide. Table~\ref{tab:mcnemar} lists the paired tests. Among inference-time conditions, only the full stack versus JSON text ($p=0.023$) and the minimal recipe versus the native API ($p=0.033$) fall below 0.05, and neither survives a Holm correction for eight tests. The ordering among the inference-time rows is therefore observed, not proven; the full stack's +8.0\pp over JSON text is suggestive, not established. Two contrasts are robust. The full stack's interval (32.0--45.4\%) does not overlap the best fine-tune's (10.7--20.6\%) or the forced-valid decoders'. Preference tuning (26.5\%) is \emph{not} separable from JSON text by these data.

\section{Why Fine-Tuning Did Not Help}
\label{sec:train}

Fine-tuning is the obvious way to teach a small model a task. Here no trained model beat the untuned model: supervised fine-tunes scored clearly lower, and preference tuning was within noise of it. We treat the runs as evidence about \emph{what} goes wrong.

\subsection{Public data taught the model to stop}
\label{sec:stop}
The first mixes scored 1/200 (0.5\%). A \emph{stop target} is a training response that is an empty list, meaning ``no further call; hand back to the user''. In the training data, 5{,}520 assistant targets were stop targets, all from ToolACE. After a tool result, 78.1\% of targets were empty (2{,}121 empty versus 596 continue). The model learned to stop after its first tool result, while BFCL needs further calls on later turns. Dropping only mid-dialogue empty targets still scored 1/200; deleting trailing empty answers at serving time scored 4/200.

\subsection{Repairing the mix restored calling, not accuracy}
Removing those targets and adding recovery examples scored 30/200 (15.0\%), our best fine-tune. Empty turns nearly vanished (167 to 2), but failures moved to state mismatch (109) and under-call (59). Two further filtering variants scored 23/200 and 26/200; adding the scratchpad to the best fine-tune lowered it to 26/200, although the scratchpad helps the untuned model. Each variant changed several filters at once, so this is a supported reading, not a single-factor ablation. A full DPO model scored 53/200 (26.5\%), also below JSON text.

\subsection{Cheap checks: a 10-task tripwire cannot rank, a 20-task gate can}
\label{sec:gates}
Two fine-tuned checkpoints and the untuned model with the status card all scored 3/10 on the 10-task check, passing the same three tasks. Rank correlation (Spearman) measures how well a check orders runs the same way as the 200-task score. Among 11 strong historical 200-task runs (at least 50/200, out of 23 full runs), the 10-task score's rank correlation with the 200-task score was 0.118, so we keep it only as a regression tripwire. With only 11 runs this estimate is very uncertain (approximate 95\% interval $-0.52$ to $0.67$), so it is illustrative. A 20-task gate tracked the historical ranking better in our selection analysis, but we do not report its correlation because the number of runs behind it is not recorded, and because its tasks were themselves chosen using those historical results (selection leakage). The gate bar itself was set by the configuration it screens against. The untuned model with the status card scores 17/20 on it; a trained model must match that before a full run.

\subsection{A rebuilt mix collapsed; a null test clears the pipeline}
Training on the rebuilt mix was stopped early at step 26{,}500 of 32{,}000. The best validation loss (0.030) was at step 22{,}000, and that checkpoint, the one we evaluated, scored 2/20 on the gate (Figure~\ref{fig:gate}). It usually made one call and stopped, even when a setup step was needed (looking up a stock symbol, changing directory, logging in), and invented missing values such as an order number. Removing the status card scored 1/20. Continuing training for 2{,}500 steps on tool lists laid out exactly as in the test restored some multi-call behaviour but still scored 2/20.

Was the pipeline itself the problem? A \emph{null test} is a run that should change nothing if the machinery is sound. We fine-tuned the untuned model for one pass on 156 of its own logged answers, through the same template, adapter, merge, quantization and serving steps. It scored 15/20 (interval 53--89\%) and kept the untuned model's habits. Two tasks below the bar is within noise for one 20-task run (the bar's own interval is 64--95\%), while the rebuilt mix's 2/20 (3--30\%) is far outside it. The collapse came from \emph{what} the rebuilt mix taught, not from the training machinery.

\subsection{Self-distillation and a candidate cause}
\emph{Self-distillation} means training the model on its own answers, here only those the checker marked correct (440 self-generated rows). It scored 8/20. Output stayed well formed, but in 6 of 12 failures the model said an ID, price or recipient was missing and stopped instead of calling the tool that would supply it. An autopsy found only partial support for the obvious explanation (too many stop rows). The stop rows were not give-ups: none followed an error and all ended a completed turn. The mix had changed, though. Look-up-type calls fell from 37.9\% of calls in the null-test data (67/177) to 19.7\% (78/395), and the share of stop targets rose from 23.1\% (36/156) to 33.2\% (146/440). The self-distillation run also took about three times as many training updates as the null test (110 versus 39), so the mix is not the only difference.

\paragraph{Targeted retrains did not confirm it.} Capping the stop share near the null-test level (22.9\% versus 23.1\%) scored 14/20, but the look-up share stayed low (20.6\%). Adding simulated look-up-then-act episodes restored the look-up share (39.6\%, close to the null test's 37.9\%) yet scored 12/20. That run lost 7 tasks the untuned model solves, and empty turns returned (9 of 66 turns). On a fresh bank of 20 other tasks it scored 2/20, against 3/20 for the untuned model. Restoring the look-up share therefore did not repair the model. The data are \emph{consistent with}, but do not establish, a mix-shift explanation; look-up counts also rest on a name-matching heuristic.

\paragraph{Stop targets in the rebuilt mix.} In the rebuilt mix, stop targets were 22\% of all rows, all placed after a tool result. That is a different denominator from the first mix's 78.1\% (the share of targets \emph{after a tool result} that were stops; Section~\ref{sec:stop}), so the two are not directly comparable. The stop-target problem of the first mix was therefore addressed in design, yet the rebuilt-mix models still under-called, so stop share alone does not explain the collapse.

\paragraph{Summary.} Fine-tuning a 2B model on tool dialogues proved fragile. Validation loss did not reveal collapses on real tasks, the pipeline itself is not to blame, and the distribution of decisions in the targets (stop versus continue, look up versus act) is a candidate, not an established, cause. None of the trained models beats the untuned model with inference-time control.

\section{Discussion}
\label{sec:discussion}

\paragraph{State, not syntax.} Across conditions, the hard part is deciding the next step given the current state of the world---including whether to keep going---not writing a valid call. Interventions that support the model's decisions help modestly: a scratchpad of real results, and a status card that mostly controls whether the model acts or abstains rather than improving state tracking. Interventions that \emph{constrain} its surface form (grammars, name automata) hurt. Training appeared to shift the balance between acting and stopping rather than improve tracking; the reason is not isolated.

\paragraph{What we recommend for on-device agents.} Use JSON-in-text calls, a harness-written state summary, a gated stop rule and a status card. This full stack is the best configuration we measured (38.5\%) and is greedy, so it costs a fraction of sampling-and-voting. If context budget is tight, the three-part recipe without the scratchpad (35.5\%) is a smaller fallback. Both need no training data or GPU time. Treat sampling-and-voting as an upper bound unless latency does not matter. Before fine-tuning, gate on task-level checks rather than validation loss, and audit the decision mix of the training targets as one plausible risk.

\paragraph{Absolute level.} Even the best configuration completes about one task in three. Small models are not yet reliable multi-step agents on this benchmark; the value of the results is in showing which levers move accuracy and which do not.

\section{Limitations}
\label{sec:limits}

\begin{itemize}\setlength{\itemsep}{1pt}
  \item \textbf{One model, one split, tuned in place.} All multi-turn results use Gemma-4-E2B-it on the 200-task base split. Settings (stop threshold, card fields, mix filters) were tuned and reported on the same 200 tasks, so the headline may be optimistic. Other models and the harder BFCL splits are untested.
  \item \textbf{Decoding.} Greedy decoding with one quantization (Q4\_K\_M) and one seed; the vote of five uses one sampling seed.
  \item \textbf{Gate design (threat to validity).} The 20 gate tasks were picked post hoc using historical per-task results from the same split, and the 17/20 bar was set by the configuration it screens against. Leave-one-run-out estimates do not remove that selection leakage, so the gate is a screening heuristic, not an unbiased predictor.
  \item \textbf{Headline selection.} The full-stack configuration was assembled after seeing earlier results on the same 200 tasks, and its only nominally significant gain (over JSON text, $p=0.023$) does not survive a multiple-comparison correction. Its code is not yet merged (draft PR \#90).
  \item \textbf{Sample size.} 95\% intervals are about $\pm7$\pp; the ordering among inference-time conditions is not statistically established. The 20-task gate is a screening tool, not a measurement.
  \item \textbf{Fairness of comparisons.} The native baseline used eight server slots versus four elsewhere; the status card and majority vote were never run on plain JSON text; majority vote used one seed. No new pairwise tests were run, because per-task results are not in the repository.
  \item \textbf{Home-made constrained decoding.} Our constrained decoding is a two-pass approximation built on stock llama-server, not XGrammar or Outlines proper, so ``forcing valid syntax hurts'' may partly mean ``our approximation hurts''.
  \item \textbf{Training confounds.} Mix variants changed several factors at once. The self-distillation run differs from the null test in both mix and number of updates (about $3\times$), and the targeted retrains did not confirm the mix explanation.
  \item \textbf{``Edge'' hardware.} Results are from a 48~GB laptop with about 15~GB peak memory; 8~GB embedded boards are unmeasured.
\end{itemize}

\section{Future Work}
\label{sec:future}

\begin{itemize}\setlength{\itemsep}{1pt}
  \item \textbf{Retrieval-augmented tool selection.} Retrieve the few relevant tools (and their documentation or past usage) for each step instead of placing every schema in context, as in retriever-aware tool use~\cite{patil2023gorilla,qin2023toolllm}. Shorter, more relevant context could help small models choose look-ups before actions, a failure seen in the training runs.
  \item \textbf{Confirmatory runs.} Re-score the full stack and JSON baseline on the harder BFCL multi-turn splits and a second small model, with matched serving.
  \item \textbf{Decision-balanced training data.} Test the mix-shift hypothesis directly: vary the look-up and stop shares while holding everything else fixed.
  \item \textbf{Embedded hardware.} Repeat the headline configuration on an 8~GB device.
\end{itemize}

\section{Conclusion}
\label{sec:conclusion}

Small language models running locally can pick a single tool well but fail most multi-step tasks: Gemma-4-E2B-it scores 83.1\% on single calls and 27.0\% on multi-turn tasks through the same native interface. On 200 BFCL v4 multi-turn tasks, those failures are mostly about state---tools that never ran and worlds that end wrong---not malformed output, and forcing valid output makes them worse. Training-free control in the harness reached 38.5\% with no sampling, +8.0 points over JSON-text calls alone and above costly voting (36.5\%); that gain is suggestive ($p=0.023$ uncorrected) but was found on the same tasks used for tuning. Fine-tuning on tool data did not reach that level: the best supervised fine-tune scored 15.0\%, a clear drop, while preference tuning (26.5\%) was within noise of the untuned baseline. A null test rules out the training pipeline; the data are consistent with, but do not establish, a shift in the decision mix as the cause. For practitioners, the best configuration we measured is also one of the cheapest: four greedy harness changes, no training.

\section{Intervention details}
\label{app:method}

\paragraph{JSON in text (IFFC).} Following Appendix~B of~\cite{taheri2026iffc}, the tool list is omitted from the API request; the system prompt asks for a JSON list of \texttt{\{function\_name, parameters\}} objects in assistant text. Tool results return as user messages. Calls map to the same BFCL function strings as native calling.

\paragraph{State scratchpad.} After each successful tool execution, the harness writes a compact \texttt{[STATE]} block from real results (current directory, known files, last executed calls). The last two turns stay verbatim; older raw outputs are dropped. It is not a model-written summary. Example:
\begin{quote}\footnotesize\ttfamily
[STATE]\\ cwd: /workspace/notes\\ files: todo.txt, log.csv\\ last: cd(folder='notes')->ok
\end{quote}

\paragraph{Stop on repeats.} After a tool result: (1) if the proposed call set equals the previous one, stop; (2) else if every proposed call was already executed in this user request \emph{and} at least six non-empty tool turns have occurred, stop; (3) otherwise execute. The six-step window resets on a new user question. The ungated variant applies rule (2) with no minimum.

\paragraph{Status (OODA) card.} Prefixed to a working copy of the latest user message (the stored transcript is unchanged), stacked on stop-on-repeats. Fields: \texttt{goal} (latest user question, truncated); \texttt{slots} (up to eight key--value facts from executed arguments and results); \texttt{last} (last executed call and outcome); \texttt{next} (advisory: \texttt{refuse} if no tools are available, \texttt{ask} if the last result signals a missing or invalid argument, \texttt{final} if the user's message is a closing ``thanks/done'', otherwise \texttt{call}). The hint does not constrain decoding and the card never reads reference trajectories. It is not the multi-pass OODA-Tool of~\cite{guo2026ooda}. Example:
\begin{quote}\footnotesize\ttfamily
[OODA]\\ goal: lock the doors and start the engine\\ slots: lockStatus=locked\\ last: startEngine()->error: brake pedal must be pressed\\ next: call
\end{quote}

\paragraph{Vote of five.} On the scratchpad configuration, each step samples five completions at temperature 0.7, majority-votes the \texttt{(function\_name, arguments)} tuple, executes the winner once, and continues. It is not a learned verifier.

\paragraph{Constrained decoding.} Two requests per call: the first constrained to an empty list or a list of valid tool names, the second constraining arguments with each tool's JSON schema. No native tool grammar is active. This approximates XGrammar-2's tag-triggered dispatch~\cite{dong2026xgrammar2} on stock llama-server.

\paragraph{Tool-name automaton.} A live finite automaton restricts the tool name to valid names while arguments are free, on JSON text, not stacked on stop-on-repeats. Execution accuracy here is not comparable to the F1 reported by Yu et al.~\cite{yu2026ptc}.

\paragraph{Training.} LoRA adapters~\cite{hu2021lora} on Gemma-4-E2B-it with mlx-lm; best-validation checkpoint fused and quantized to Q4\_K\_M; evaluated with JSON text. The rebuilt mix: 30{,}000 training / 1{,}500 validation rows; 45/40/10/5\% simulated / APIGen / ToolACE / xLAM; 22\% empty-list targets (all after a tool result); 41.2\% of rows with multi-call targets; no evaluation tool names copied into simulations. DPO: $\beta{=}0.2$, LoRA, scored on JSON text.
