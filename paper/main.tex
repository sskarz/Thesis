\begin{abstract}
A useful assistant has to \emph{do} things, not just describe them: check a calendar, edit a file, lock a car. Models do this by emitting \emph{tool calls}---machine-readable requests that a surrounding program executes and feeds back. Running that loop on a laptop rather than a cloud API keeps private data local, works offline, and costs nothing per request, which makes small language models (under five billion parameters) appealing. The hard part is multi-step \emph{state tracking}: the model must remember what already happened in a simulated car or filesystem and decide the next call, or when to stop.

We measure four small open models on a MacBook Pro (M4~Pro, 48~GB) with the Berkeley Function Calling Leaderboard (BFCL) v4. On single-turn tool selection the best model exceeds 80\%. On multi-step agent episodes---200 tasks, graded by whether the environment ends in the right state---the same class of model fails most of the time.

The interventions we scored on Gemma-4-E2B-it tell a two-part story. Parsing tool calls from ordinary text lifts native structured calling from 27.0\% to 30.5\%. A harness-written scratchpad reaches 34.0\%; hanging up on repeating turns reaches 32.5\%; a four-line status cheat sheet on that hang-up reaches 35.5\%; a majority vote of five candidates reaches 36.5\% at roughly $7\times$ generation time. Forcing valid tool names hurts (a live name automaton scores 13.5\%). Asking a second small model to rank the next tool also hurts (25.0\%). Fine-tuning on public corpora also hurts: the best repaired mix scores 15.0\%, below the untuned model, because the original data taught the model to emit an empty list and stop after the first tool result. Preference training on the same channel scores 26.5\%, still below the untuned JSON baseline. A later training mix still ties the untuned model on a 10-task early check that cannot separate training from prompt tricks, so we switched to a 20-task gate. A further repaired mix (v11) reached its best validation loss and then scored only 2 of 20 on that gate, against 17 for the untuned model; training the untuned model on its own answers through the same pipeline scored 15/20, pointing at the data rather than the pipeline. Beating the best prompt-engineering result (35.5\% on 200 tasks) with training remains open.

Two conclusions matter more than the ladder. First, plumbing---how calls are written and parsed---can swing scores by tens of points. Second, remaining errors are state tracking, not malformed JSON. Everything we tried sits below 40\%: about one in three episodes succeed at the 36.5\% best. With 200 tasks, neighbour gaps of a few points sit inside ordinary noise (${\sim}{\pm}7$ percentage points); the ordering is observed, not proven. A ${\sim}15$~GB serving footprint is not an 8~GB embedded board.
\end{abstract}

\section{Introduction}
\label{sec:intro}

A useful assistant has to act, not only chat. Checking a calendar, editing a file, or locking a car means the model must emit a \emph{tool call}: a machine-readable request that a surrounding program (the \emph{harness}) executes against a \emph{backend}---here, a simulated vehicle or sandbox filesystem---and then feeds the result back. Figure~\ref{fig:vignette} is that loop before the jargon. \emph{Format} errors are when the harness cannot even parse the request (native \texttt{tool\_calls} versus JSON in text, stringly-typed arguments, a truncated grammar). \emph{State} errors are when every call is valid JSON but the simulated world ends up wrong: the engine left on, a file in the wrong folder, a lock issued twice, or the model \emph{under-calls} (stops before a required tool has run). Errors cascade; later turns inherit a broken environment.

We run that loop locally. A cloud API keeps the data and the meter off-box; a laptop keeps private data on-device, works offline, and costs nothing per request. All own measurements use llama.cpp~\cite{llamacpp} on a MacBook Pro with Apple M4~Pro (48~GB) and Metal. Peak resident set size for the Gemma multi-turn jobs is about 15~GB. NVIDIA Jetson Orin Nano Super (8~GB) deployment is unmeasured; this paper does not claim that the reported accuracies run on that board. Retrieval-augmented generation (RAG) appeared in an earlier registered title and is \emph{out of scope}: not evaluated, and not deferred.

Small models (under five billion parameters) make that local loop feasible. The empirical questions:

\begin{enumerate}
  \item How well do quantized small models select tools in one shot, and how well do they finish multi-step episodes, on BFCL v4 when served locally?
  \item How much of measured failure is plumbing (output channel, parser, serving flags) versus genuine state tracking?
  \item Which inference-time tricks (channel, scratchpad, hang-up, status card, voting, validity-forcing) and which training-time interventions (supervised fine-tuning, preference optimization) move the primary multi-step metric?
\end{enumerate}

A glossary of acronyms is in Appendix~\ref{app:acro}. Differences are reported in percentage points (\pp). Accuracy numbers live in Results, not in the list below.

\paragraph{Contributions.}
\begin{enumerate}
  \item \textbf{A Mac-local baseline.} Four small open models on single-turn tool selection, plus Gemma-4-E2B-it on multi-step agent episodes, all served with llama.cpp on the MacBook Pro above.
  \item \textbf{Plumbing is first-order.} How the model writes a call, and how the harness parses it, can swing scores by tens of points---including a published specialist checkpoint that looks dead on the native channel and merely very low once the channel matches training. A separate Llama diagnostic is consistent with argument serialization, not tool selection, as the gap. Native versus JSON-in-text on Gemma is a real point-estimate lift; the native run used more parallel server slots, so part of that gap may be serving (disclosed in Results).
  \item \textbf{Cheap harness tricks help a little; forcing valid names---or a second model ranking the next name---can hurt.} A scratchpad, hanging up on repeated calls, a four-line status cheat sheet, and a five-way majority vote all sit above the JSON-in-text baseline as an observed ranking. Validity-forcing (constrained decoding; a live tool-name automaton) scores well below that baseline. Asking a second small model to pick the next tool also hurts (about 25\%). Stacking that helper with the status cheat sheet still scores about 26\%. A trained picker in the same role scores about 5.5\%. Details and run IDs live in Results. Adjacent gaps among the winners are small relative to a 200-task sample; missing stacks are listed in Section~\ref{sec:roadmap}.
  \item \textbf{Supervised fine-tuning on public corpora can teach the model to hang up.} Empty-list targets after tool results in the mix produce a checkpoint that almost never continues. Repairing the mix restores calling but still underperforms the untuned model. The scratchpad that helps the base model does not help that checkpoint. This is a supported reading of the mix, not a single-factor ablation. Later mix surgery is still an open result versus the 35.5\% prompt-engineering bar; the best historical trained accuracy is about 15\%. That is not a win.
  \item \textbf{Preference optimization is scored and still below the untuned JSON channel.} Direct Preference Optimization (DPO) passed a 10-example health gate. The full-train checkpoint scores 53/200 (26.5\%) on plain JSON-in-text---below IFFC 30.5\% and NFC 27.0\%. That is a scored row, not a method win.
  \item \textbf{A 10-task early check cannot rank training; a 20-task gate stands in; the repaired mix failed it.} Trained and untuned models both score 3/10 on the same easy IDs. A 20-task check (no overlap with those ten) is the go/no-go gate; the untuned model scores 17/20 there. The repaired mix (v11) reached its lowest validation loss yet and still scored only 1--2/20. Training the untuned model on its own answers through the same pipeline scored 15/20, so the pipeline is not the problem; the training data is. A filtered self-distillation follow-up scored 8/20. Beating the prompt-engineering bar (35.5\% on 200 tasks) with training remains open.
\end{enumerate}

\section{Background and Related Work}
\label{sec:related}

\subsection{BFCL and consecutive tool calling}
The Berkeley Function Calling Leaderboard (BFCL) and the Gorilla line of work evaluate language models as API callers~\cite{patil2023gorilla,patil2024bfcl}. We use BFCL v4. Figure~\ref{fig:vignette} is the loop the multi-turn checker grades.

Single-turn categories are scored with an AST checker: the model sees a user query and a tool schema and must emit a call (or none) whose structure matches a reference, allowing equivalent argument order. Categories include \texttt{simple} (one available function), \texttt{multiple} (several functions, pick the right one), \texttt{parallel} / \texttt{parallel\_multiple} (several calls in one turn), \texttt{irrelevance} (the query needs no call), and Java / JavaScript typed variants.

Multi-turn categories are scored with an \emph{execution} checker. The model enters an agent loop; tools run against a live \emph{backend}---a simulated application whose instance state the checker compares to a reference trajectory. Recurring backends in this paper include VehicleControl (start/lock/brake-style vehicle APIs) and GorillaFileSystem (a sandbox Unix-like filesystem). The four slices are \texttt{multi\_turn\_base} (full tool set), \texttt{miss\_func} (some tools withheld until later), \texttt{miss\_param} (required arguments omitted from the query), and \texttt{long\_context} (large histories). This paper's optimization target is \texttt{multi\_turn\_base} ($N{=}200$). Paper percentages on that slice are \emph{not} public overall-BFCL leaderboard scores, which mix many categories and often different serving stacks.

We bucket failed entries with one primary label each. \emph{Empty turn} means the model emitted no callable output on a turn that needed one. \emph{Under-call} (missing ground-truth execution) means required tools never ran. \emph{State mismatch} means tools ran but the backend instance diverged from the reference. Observe--orient--decide--act (OODA) in this paper is a one-pass status card, not Boyd's four-stage military loop and not a four-pass controller~\cite{guo2026ooda}.

\subsection{Native versus instruction-followed function calling}
\paragraph{Native function calling (NFC).}
The server is given OpenAI-style \texttt{tools} and the model is expected to return structured \texttt{tool\_calls}. llama.cpp may compile a grammar (GBNF) once chat-template trigger tokens appear. This is the default production channel for many local stacks.

\paragraph{Instruction-followed function calling (IFFC).}
Taheri et al.~\cite{taheri2026iffc} argue that small models can follow JSON instructions more reliably than native tool APIs. Their paper reports large gains on BFCL v3 \emph{single-turn} suites, often with a dual-model design that separates a QA model from a small reasoning model (their Algorithm~1). We implement only Appendix~B: the \emph{same} model emits a JSON list of \texttt{\{function\_name, parameters\}} objects in assistant text, with no native \texttt{tools} field. Dual-model IFFC is deferred (Section~\ref{sec:roadmap}).

\subsection{Structured decoding, templates, and test-time compute}
XGrammar-2 describes efficient dynamic structured generation, including TagDispatch for tag-triggered grammar switches~\cite{dong2026xgrammar2}. That work reports, for example, lifting Llama-3.2-3B correct-call rates from 33\% to 78\% \emph{under its engine and metric}---prior-work figures, not our measurements, and \emph{not} comparable to the Llama 33.50\% BFCL v4 \texttt{multiple} cell in Table~\ref{tab:single-turn} (different task, checker, and serving stack). Our constrained-decoding ablation approximates TagDispatch with two stock llama-server requests and is not full XGrammar-2. Guided generation more broadly is studied by Willard and Louf~\cite{willard2023outlines}; format restrictions can also hurt quality~\cite{tam2024format}.

He et al.~\cite{he2025gst} propose seven-step guided-structured templates (GST) that improve function calling on BFCL v2. We overlay their Detail template as a prompt on NFC; the checker executes native \texttt{tool\_calls} and ignores GST draft text. This is not a grammar and not IFFC.

Snell et al.~\cite{snell2024testtime} frame test-time compute versus parameter scaling. Our Best-of-N is majority vote over sampled tool-call tuples, not tree search and not a learned verifier.

\subsection{Working memory and specialist SLM callers}
ACON compresses older turns with learned or LLM-written summaries~\cite{kang2025acon}. Our STATE overlay is a harness-written key-value snapshot from \emph{executed} tool results, not an LLM summary.

Guo et al.\ propose OODA-Tool, a typed observe--orient--decide--act controller, including a multi-pass Specialized variant~\cite{guo2026ooda}; we do not score that paper's method. Yu et al.\ propose PTC-Decoder (plan-to-act plus a tool-name DFA) and report F1 on a Jetson/satellite LLM-judge setup~\cite{yu2026ptc}; we do not reproduce those F1 numbers. Our PTC-A row is execution accuracy on this BFCL harness.

Error taxonomies for sub-7B callers often rank type mismatch among dominant failures~\cite{liu2024apigen}. Specialist models such as FunctionGemma~\cite{google2025functiongemma}, Hammer~\cite{ye2025hammer}, and xLAM~\cite{zhang2024xlam} show that fine-tuning and format design can make small models competitive. We treat type coercion as an inference-time mitigation that does not change weights, and we score a published xLAM-1b GGUF on \emph{this} harness rather than citing the public overall figure (${\sim}78.94\%$) as a reproduction.

\subsection{Training-time methods}
QLoRA is the standard efficient-finetuning reference~\cite{dettmers2023qlora}; we train LoRA adapters with MLX on Apple Silicon~\cite{mlx}, not QLoRA-on-CUDA. ToolACE~\cite{liu2024toolace} and xLAM supply the IFFC JSON-in-text mix. Direct Preference Optimization~\cite{rafailov2023dpo} and dialogue-level variants such as DiaTool-DPO~\cite{jung2025diatool} motivate a preference path after SFT proved brittle; our DPO evidence is a 10-ID health gate plus a scored full-train row of 26.5\% on plain IFFC, which does not beat the untuned JSON baseline.

\subsection{Output channels}
\label{sec:method-channels}

\paragraph{NFC (native API).}
The harness sends \texttt{tools} and \texttt{tool\_choice=auto}. Assistant outputs are native \texttt{tool\_calls}. This is the Gemma multi-turn baseline and the channel used for the xLAM native-tools probe.

\paragraph{IFFC (JSON-in-text).}
Following Appendix~B of~\cite{taheri2026iffc}, we omit \texttt{tools}. The system prompt asks for a JSON list of \texttt{function\_name} / \texttt{parameters} objects in assistant text. Tool results return as user-role messages. Trajectories are mapped to the same BFCL function strings used by NFC.

\paragraph{xLAM JSON channel.}
Salesforce xLAM-1b-fc-r is trained to emit \texttt{\{"tool\_calls":[\ldots]\}} in content, not OpenAI \texttt{tool\_calls}. A format adapter parses that JSON and executes tools. This is a channel fix for a published checkpoint, not a new training method.

\paragraph{Shell dialect.}
An allowlisted Unix-like text dialect is mapped onto GorillaFileSystem calls (e.g., \texttt{cd notes} $\to$ \texttt{cd(folder='notes')}) and scored only on the 13 filesystem-only IDs in \texttt{multi\_turn\_base}. It is a format ablation, not a substitute for the 200-entry score.

\subsection{Inference overlays on IFFC or NFC}
\label{sec:method-overlays}

\paragraph{Guided-structured templates (GST$+$NFC).}
The He et al.\ Detail curriculum is prepended as a one-shot system prompt on top of NFC~\cite{he2025gst}. The model is asked to write a \texttt{[GST]} scaffold before native \texttt{tool\_calls}. The checker ignores the scaffold.

\paragraph{Harness STATE (scratchpad).}
IFFC is unchanged as a channel. After each successful tool execution, the harness writes a compact \texttt{[STATE]} snapshot from real results (cwd, known files, last executed calls) and attaches it in user messages. The last two turns stay verbatim; older raw dumps are dropped. This is not LLM summarization~\cite{kang2025acon}. Example shape (fields come from executed backends, not from the model):

\begin{quote}
\footnotesize\texttt{[STATE]}\\
\texttt{cwd: /workspace/notes}\\
\texttt{files: todo.txt, log.csv}\\
\texttt{last: cd(folder='notes')->ok; cat(file\_name='todo.txt')->ok}\\
\texttt{[/STATE]}
\end{quote}

\paragraph{Best-of-N (BoN; vote of five).}
On the IFFC$+$STATE channel, each agent step samples $N{=}5$ completions at temperature 0.7, majority-votes the \texttt{(function\_name, arguments)} tuple, executes the winner once, and continues. Latency is roughly $N$ greedy decodes. This is not a verifier. \emph{API calls} in timing tables are llama-server request counts (BoN inflates them by about $N$ samples per step), distinct from tools executed and from user turns.

\paragraph{Stop-on-repeat (hang-up).}
After a tool-result observation, the harness may stop the turn without re-executing. Logic (from \texttt{benchmark/stop\_on\_repeat.py}):

\begin{enumerate}
  \item If the proposed IFFC call set equals the previous assistant call set (\texttt{consecutive\_identical}), stop immediately.
  \item Else if every proposed call was already executed in this user-ask \emph{and} at least $\mathrm{MIN}{=}6$ nonempty assistant tool-turns have occurred (\texttt{observe\_same\_call}), stop.
  \item Otherwise execute. The MIN window resets on a fresh BFCL user question, not on an execution dump, so short VehicleControl re-calls (3--5 steps) are not treated as loops.
\end{enumerate}

An \emph{ungated} version fires observe-same immediately ($\mathrm{MIN}{=}0$). This is a decode/harness guardrail, not a retrain.

\paragraph{OODA-card (status cheat sheet).}
A one-pass \texttt{[OODA]} card is prefixed on a \emph{working copy} of the latest user message (the persistent transcript stays IFFC-clean so stop-on-repeat still sees unmodified dumps) and stacked on gated stop-on-repeat ($\mathrm{MIN}{=}6$). Fields are filled deterministically from the live conversation and \emph{executed} tool results only. The construction does not read BFCL reference trajectories, gold function strings, or checker instance state (harness \texttt{benchmark/ooda\_card.py}, PR~\#61):

\begin{itemize}\setlength{\itemsep}{2pt}
  \item \texttt{goal}: the latest BFCL user question (execution dumps and retry prompts skipped), truncated.
  \item \texttt{slots}: up to eight key=value facts from executed arguments/results (cwd, directory listing, a few argument keys such as \texttt{folder} / \texttt{file\_name}).
  \item \texttt{last}: last executed call plus a compact outcome from that result.
  \item \texttt{next}: an advisory mode in $\{\texttt{call},\texttt{ask},\texttt{final},\texttt{refuse}\}$. If the live tool set is empty, \texttt{refuse}; if the last execution looks like a missing/invalid argument, \texttt{ask}; if the latest user utterance matches a closing thanks/done pattern, \texttt{final}; otherwise \texttt{call}. The hint does not constrain decoding: the model still emits ordinary IFFC JSON (or \texttt{[]}).
\end{itemize}

Example shape:

\begin{quote}
\footnotesize\texttt{[OODA]}\\
\texttt{goal: lock the car after I park}\\
\texttt{slots: cwd=/workspace; folder=notes}\\
\texttt{last: cd(folder=notes)->ok}\\
\texttt{next: call}\\
\texttt{[/OODA]}
\end{quote}

This is not Guo et al.'s four-pass Specialized OODA-Tool~\cite{guo2026ooda} and not the STATE overlay. An OODA-card on \emph{plain} IFFC (without stop-on-repeat) remains unscored.

\paragraph{Decision sidecar.}
A second small model (\texttt{tev1:latest}) ranks the next tool name on the IFFC channel and may execute, skip, or hang up. Name hints are injected on a working copy of the messages; the persistent transcript stays IFFC-clean. As shipped this overlay does \emph{not} carry the OODA-card or gated hang-up (a recipe confound versus the 35.5\% row). A composed mode (\texttt{iffc-decision-ooda}) later landed (compose smoke PASS at Thesis \texttt{50b743f}; OODA source \texttt{1dea341}). Turn-0 timeout hygiene landed (Thesis \texttt{ee4d877} / probe \texttt{98f1b56}; smoke/hygiene PASS; Acc not invented from smoke). The composed treatment is scored at 52/200 $=$ 26.0\% (Run~61; Table~\ref{tab:scoreboard})---a failure versus IFFC through OODA-card. Replacing tev1 with a Choice-SLM helper (\texttt{choice\_slm\_chat}, menu log-likelihood) scores 11/200 $=$ 5.5\% (Run~64)---a failure versus Decision and Decision+OODA. Decision treatments are treatment-only: there is no same-session plain-IFFC twin.

\paragraph{TagDispatch-style constrained decoding (CD).}
Stock llama-server does not expose intra-request tag-triggered grammar switches. We approximate TagDispatch with two requests and never send \texttt{tools}, so native tools GBNF does not activate. Pass~1 constrains the completion to an empty list or a list of live \texttt{function\_name} values. Pass~2 constrains arguments for the selected names via \texttt{json\_schema}. This is not full XGrammar-2 (no intra-request tag switch, two HTTP requests per tool invocation).

\paragraph{Prefix-tree name constraint (PTC-A).}
A live deterministic finite automaton constrains the tool \emph{name} while arguments remain free. This is inspired by Yu et al.'s PTC-Decoder~\cite{yu2026ptc}; it is not a reproduction of that work's F1 numbers (different metric, hardware, and judge), and it is not the two-pass CD ablation above. PTC-A is scored on base IFFC, not stacked on stop-on-repeat. Token-level forced-name decoding versus loop behavior is not fully audited; we report measured residuals without a mechanism claim.

\subsection{Type coercion}
\label{sec:method-coerce}

Llama-3.2-3B often selects the correct function on \texttt{multiple} but serializes integers, floats, arrays, and objects as JSON strings. We apply (i)~a system prompt requiring native JSON types and (ii)~schema-aware post-hoc coercion of argument values to the BFCL parameter types. Both are inference-time only.

\subsection{Parallel grammar bug}
\label{sec:method-parallel}

When \texttt{tools} are present, llama-server may compile a tools grammar whose repetition structure mismatches the model's trained multi-call delimiters. Generation can stop after the first closing tag, truncating parallel output. A bypass (\texttt{tool\_choice none} with content parsing) is implemented; re-measurement is pending, so tables still report 0\% for \texttt{parallel} and \texttt{parallel\_multiple}.

\subsection{Supervised fine-tuning and preference optimization}
\label{sec:method-sft}

We train LoRA adapters on Gemma-4-E2B-it with mlx-lm~\cite{mlx} using an IFFC JSON-in-text mix (ToolACE multi-turn~\cite{liu2024toolace} plus stratified xLAM~\cite{zhang2024xlam}), fuse a best-validation checkpoint, quantize to Q4\_K\_M, and evaluate under IFFC on \texttt{multi\_turn\_base}. Mix variants drop empty-list assistant targets after tool results, drop first-turn empty answers, and try turn-0 / state-consistency filters. A serve-time diagnostic strips trailing assistant \texttt{[]} from chat history without retraining; we do not treat that diagnostic as a method.

A 100-update DPO smoke ($\beta{=}0.2$) from the untouched Gemma MLX base is used only as a health gate (call volume, parseability, first-turn tool use on 10 IDs). A later full DPO checkpoint is scored on plain IFFC at 53/200 (26.5\%); other serving fields for that run are not verified here. That score is below IFFC and NFC. It is not a method win.

Later mixes (v10, then a repaired v11) keep the same LoRA-on-Gemma recipe. Before a 200-task score we use two early checks, defined once here and used in Section~\ref{sec:results-train}: a \emph{soft10} is a 10-task tripwire; a \emph{mid20} is a 20-task go/no-go gate (no overlap with those ten). Neither is the 200-task execution accuracy, and neither rewrites the prompt-engineering bar of 71/200 (35.5\%).

\section{Experimental Setup}
\label{sec:setup}

\subsection{Hardware and serving}
All own experiments run on the MacBook Pro with Apple M4~Pro (48~GB) stated in Section~\ref{sec:intro}, with Metal GPU acceleration, llama.cpp build 8111 (commit \texttt{11c325c6e}), compiled with \texttt{-DGGML\_METAL=ON}. Models are served with \texttt{llama-server --jinja}, flash attention on, and full GPU offload (\texttt{-ngl 99}). Peak resident set size (RSS) on this stack is dominated by the KV cache at the configured context length, plus model weights (bf16 for FunctionGemma). Overnight multi-turn jobs use \texttt{-np 4 -c 65536}, except the NFC baseline, which used \texttt{-np 8}; that serving asymmetry is disclosed with the IFFC-versus-NFC comparison in Section~\ref{sec:results-helped}.

\subsection{Models}
Single-turn matrix (Q4\_K\_M unless noted): Qwen2.5-3B-Instruct~\cite{qwen25}, Llama-3.2-3B-Instruct~\cite{llama32}, Qwen3.5-4B~\cite{qwen35}, and FunctionGemma-270M-IT~\cite{google2025functiongemma} (bf16; the published precision). Multi-turn primary model: Gemma-4-E2B-it~\cite{gemma4e2b} Q4\_K\_M (Google's effective-2B instruct checkpoint, HuggingFace \texttt{google/gemma-4-e2b-it}; served from bartowski). External baseline: Salesforce xLAM-1b-fc-r~\cite{zhang2024xlam} Q4\_K\_M. Decoding for reported accuracy uses temperature 0.0 except BoN (temperature 0.7, $N{=}5$). Parallel server slots and context length are as in the hardware subsection above.

\subsection{Evaluation protocol}
Single-turn: BFCL AST checker. Multi-turn: BFCL execution checker. FunctionGemma control-token outputs are normalized with a dedicated parser when llama-server does not already map them to \texttt{tool\_calls}. Weighted single-turn averages exclude \texttt{parallel} and \texttt{parallel\_multiple} (990 remaining cases). Failure buckets use one primary error per failed entry unless noted as raw eval-error rows. In timing tables, \emph{API calls} means llama-server / model-server request count, not tools executed and not user turns; BoN inflates the count by about $N$ samples per agent step. Chronological IDs in Appendix~\ref{app:runs} are local SQLite bookkeeping for the \texttt{multi\_turn\_base} $N{=}200$ scoreboard, plus 10-task and 20-task probes that are not 200-task percentages.

\subsection{What helped (observed ordering)}
\label{sec:results-helped}

On this 200-task slice, cheap harness changes raise the point estimate from native 27.0\% into the mid-30s, and a five-way vote reaches 36.5\%. The observed ranking is Best-of-N 36.5\% $>$ OODA-card 35.5\% $>$ STATE 34.0\% $>$ gated stop-on-repeat 32.5\% $>$ IFFC 30.5\% $>$ NFC 27.0\%. Neighbour gaps of a few points on 200 tasks sit inside ordinary binomial noise (a 95\% interval around 36.5\% is roughly ${\pm}7$ percentage points). Pairwise McNemar tests on adjacent rows are not significant. Treat the order as observed, not proven.

\paragraph{IFFC versus NFC (${+}3.5$\pp point estimate).}
JSON-in-text (IFFC) outscores native structured calls (NFC): 61/200 versus 54/200. Pairwise, both fail on 124 entries; IFFC rescues 22 and regresses 15. Using the same primary buckets as Table~\ref{tab:fail} (one error per failed entry), empty-turn counts fall 59$\to$41 and state-mismatch 68$\to$60. (Raw NFC \texttt{eval\_errors} rows are much larger because one entry can contribute several rows; we do not mix those with IFFC primaries.) Once calls parse, residual error is environment fidelity, not the channel label.

The native run used eight parallel server slots (\texttt{-np 8}); IFFC used four (\texttt{-np 4}). A matched NFC@\texttt{-np 4} accuracy has not been measured, so part of the ${+}3.5$\pp gap may be serving rather than channel.

\paragraph{Harness STATE (${+}3.5$\pp over IFFC).}
A scratchpad written by the harness from executed tools scores 68/200 (34.0\%) on \emph{base} Gemma, above the 30.5\% IFFC/GST plateau. Versus IFFC the overlap is shared 48, rescue 20, regress 13 (net ${+}7$). Empty turns fall 41$\to$31 while state mismatch does not improve (60$\to$64). STATE appears to help forgotten calls more than env-diff fidelity. Stored response blobs contain literal \texttt{[STATE]} in 0/200 rows, as expected: STATE is conversation context written by the harness.

\paragraph{Gated stop-on-repeat (${+}2.0$\pp over IFFC).}
Hanging up after six repeated observations, rather than at the first repeat, scores 65/200 (32.5\%). Versus plain IFFC: shared 54, rescue 11, regress 7; McNemar $p{\approx}0.48$ (n.s.). Stop flags fall from 37/200 (ungated) to 3/200, all still failures. VehicleControl state-mismatch counts return to the IFFC baseline (22, versus 33 ungated). This is a harness hang-up on the base checkpoint, not a training win.

\paragraph{OODA-card on gated stop-on-repeat (${+}3.0$\pp over gated stop-on-repeat).}
The four-line status cheat sheet, stacked on $\mathrm{MIN}{=}6$ hang-up, scores 71/200 (35.5\%): best non-BoN point estimate, 1.0\pp\ below BoN. Versus gated stop-on-repeat: shared 45, rescue 26, regress 20; McNemar $p{\approx}0.46$ (n.s.). Empty-turn primaries fall 38$\to$17 while state mismatch rises 60$\to$71 and under-call 37$\to$41, consistent with anti-abstention rather than better state tracking. Median TTFT was 517.8~ms versus 630.5~ms on gated stop-on-repeat; we do not interpret that as a causal end-to-end speedup (card-build cost and generate wall were not the claim). An OODA-card on \emph{plain} IFFC remains unscored.

\paragraph{Best-of-N majority vote on IFFC$+$STATE (${+}2.5$\pp over STATE, ${\sim}7\times$ generate wall).}
Sampling five candidates and majority-voting the call, on IFFC$+$STATE, scores 73/200 (36.5\%), the best measured inference point estimate. Versus greedy STATE: shared 56, BoN-only 17, greedy-only 12. \subsection{GST$+$NFC ties IFFC, not a lift over IFFC}
\label{sec:results-gst}

GST$+$NFC scores 61/200, matching IFFC in count via a 19-row swap each way (both correct 42) and beating NFC by ${+}3.5$\pp. Empty turns fall to 31 (NFC 59, IFFC 41) while state mismatch rises to 79 (NFC 68, IFFC 60). \subsection{What did not beat IFFC}
\label{sec:results-hurt}

\paragraph{Ungated stop-on-repeat (27.0\%, ${-}3.5$\pp versus IFFC).}
Stopping at the first repeated observation matches NFC's 54/200 but is a different method, not a reproduction of native calling. All 37 stop flags land among the 146 failures (zero stopped-and-correct). VehicleControl state mismatches rise 22$\to$33. Early stopping helps only loop-dominated traces; on healthy base Gemma it cuts good trajectories.

\paragraph{Constrained decoding (10.5\%).}
The two-pass name-then-args approximation scores 21/200: ${-}16.5$\pp versus NFC and ${-}20.0$\pp versus IFFC (179 errors). Syntactic validity is not consecutive correctness on this stack. This is not a claim about full XGrammar-2 TagDispatch.

\paragraph{PTC-A (13.5\%, scored failure).}
A live tool-name automaton on \emph{base IFFC} scores 27/200: ${-}22.0$\pp\ versus OODA-card on gated stop-on-repeat, ${-}19.0$\pp\ versus gated stop-on-repeat, ${-}17.0$\pp\ versus IFFC. Measured residuals: state mismatch 102, empty turn 17, under-call 54. Yu et al.\ report F1 in a different setting~\cite{yu2026ptc}; those F1 numbers are not this harness Acc. A token-level diagnosis of forced-name decoding versus loop behavior is not fully audited; we report those residuals without a mechanism claim. We treat PTC-A as a scored failure and do not remix prefix constraints as the next accuracy bet. A second PTC variant is unscored.

\paragraph{Decision sidecar (25.0\%, scored failure / no lift).}
A second small model ranking the next tool name on \emph{plain} IFFC (no OODA-card, no gated hang-up) scores 50/200: ${-}10.5$\pp versus OODA-card, ${-}7.5$\pp versus gated stop-on-repeat, ${-}5.5$\pp versus IFFC. \section{Multi-turn Results: Training-Time Interventions}
\label{sec:results-train}

\subsection{SFT empty-list mixes collapse}
\label{sec:results-sft-collapse}

In plain language: the public training mix often asked the model to answer with an empty list after seeing a tool result---the equivalent of hanging up. The fine-tuned model learned that habit. On BFCL, later user turns still need more calls, so the checkpoint stops too soon and scores 1/200 (0.5\%). A live single-step probe still emits valid IFFC JSON, so this is not a parser or chat-template failure.

The MLX mix contains 5520 assistant \texttt{[]} targets, all from ToolACE (32.5\% of ToolACE assistant turns; xLAM 0\%). After a ``Function execution results'' user message, 78.1\% of assistant targets are \texttt{[]} (2121 empty versus 596 continue). A \textbf{supported hypothesis}, not a single-factor proof, is that this mix teaches stop-after-tools, whereas BFCL multi-turn requires continued calls on later user turns. Mix variants v2--v6 change several filters at once; no ablation holds optimizer, rank, and mix size fixed while toggling only empty-list targets.

Filtering 334 mid-trajectory empty-after-exec rows while keeping 552 terminal empty-after-exec examples (SFT-v2) again scores 1/200. Empty primary fails rise 101$\to$167. Figure~\ref{fig:sft} shows the scored slice. Stripping trailing assistant \texttt{[]} from chat history at serve time, without retraining, reaches only 4/200 (2.0\%). Turn-0 empty errors remain 153. History bookkeeping does not rescue a never-start collapse.

\subsection{SFT-v4 recovers empty lists, not consecutive accuracy}
\label{sec:results-sft-v4}

Removing those empty-list targets stops the hang-up (empty errors nearly vanish) but does not teach the model to track the simulated car or filesystem. Dropping empty-after-exec targets (including terminal), adding recovery rows, and dropping first-assistant-empty and clarifying empty-after-user \texttt{[]} yields 30/200 (15.0\%): ${+}29$ entries versus SFT-v2, still ${-}31$ versus IFFC and ${-}24$ versus NFC. Correct-set overlap versus IFFC: shared 23, SFT-only 7, IFFC-only 38. Empty-turn primaries fall 167$\to$2. Residual error is state mismatch (109) and under-call (59), including 35 turn-0 under-calls. This is the best SFT recovery in the study. It is not a win over the untuned base model.

\subsection{Further mix surgery regresses; STATE does not transfer}
\label{sec:results-sft-later}

IFFC$+$STATE on the same v4 GGUF scores 26/200 (13.0\%): ${-}2.0$\pp versus plain IFFC on that checkpoint. Contrast: STATE on base Gemma was ${+}3.5$\pp. Empty stays rare (3); residual remains state mismatch (112) and under-call (59).

SFT-v5 keeps the v4 empty-recovery curriculum and adds turn-0 completeness plus state-consistency filters (${\sim}29850$ train rows). It scores 23/200 (11.5\%): a regression versus v4. Empty primaries fall to 0/177, but state mismatch rises to 133. Mean API calls jump to 40.27 (v4 was 17.32).

SFT-v6 keeps v4 empty/recovery plus only the state-inconsistency drop (turn-0 underspecification filters off). It scores 26/200 (13.0\%): a miss versus v4, a modest lift versus v5. Empty remains essentially suppressed (1). Mean API calls return to 13.34. State mismatch is 118 and under-call 55.

Thin filter ablations on this ToolACE$+$xLAM IFFC family did not beat v4. A later 10-ID quota-remix smoke failed a health gate (mean 25.7 llama-server requests, 6/10 traces hit the step limit); that gate is not a BFCL percentage, and no $N{=}200$ score is claimed.

\subsection{DPO: scored 26.5\%, not a method win}
\label{sec:results-dpo}

A 100-update DPO smoke ($\beta{=}0.2$, LoRA, fused Q4\_K\_M) passed the same style of 10-ID health gate used to reject collapsed SFT smokes: mean llama-server requests 4.4 (band 4--8.3), 0/10 step-limit hits, 0/10 unparseable IFFC, 7/10 first-turn tool uses. That is evidence the training stack did not immediately collapse. It is not a \texttt{multi\_turn\_base} score.

A later full DPO checkpoint, scored on plain IFFC, is 53/200 (26.5\%): ${-}4.0$\pp versus IFFC and ${-}0.5$\pp versus NFC. Other serving fields for that run (throughput, gates) are not verified here. We treat DPO-full as a scored row below the untuned JSON baseline, not as a method win, and we do not treat the 10-ID smoke as a scoreboard percentage.

\subsection{A 10-task early check cannot rank training}
\label{sec:results-soft10}

In plain language: before spending a night on 200 tasks, we ran a 10-task early check (soft10). Two later SFT-v10 checkpoints and the untuned model with the status cheat sheet all score 3/10, and they pass the same three easy IDs (\texttt{\_101}, \texttt{\_126}, \texttt{\_130}). An earlier smoke of the same mix collapsed to 0/10 from undertraining. The 10-task slice does not tell supervised fine-tuning from prompt engineering---the untuned base plus harness overlays. Across historically strong 200-task runs, that 10-task score barely agrees with the full ranking (rank correlation 0.118)---almost no help picking a winner---so we keep those three easy IDs as a regression tripwire only. We do not treat 3/10 as a 200-task percentage.

The two trained 3/10 rows are SFT-v10 best-validation (hang-up harness) and a longer continuation of the same mix (no lift; format adherence worse). The matching 3/10 on the untuned model used the same status-cheat-sheet harness as the 35.5\% 200-task bar. Fail classes on the trained versus untuned 3/10 rows are not identical; the pass set is.

\subsection{A 20-task gate replaces it}
\label{sec:results-mid20}

We replaced that 10-task check as a discriminator with a 20-task early check (mid20): twenty fixed IDs, no overlap with the 10-task set. On past runs, this 20-task score usually agrees with which methods look stronger on all 200 (leave-one-run-out rank correlation 0.857). The untuned model plus the status cheat sheet scores 17/20; that is the bar a trained model must clear before a full 200. It is not the 200-task prompt-engineering bar (71/200 $=$ 35.5\%). We once saw two more passes than an older slice of that 35.5\% run; we do not treat that ${+}2$ as a real method gain. Mid20 is not a 200-task percentage.

We rebuilt the training data so it matches how the checker grades: teach the model to end a turn with an empty list when it should stop, practice several calls in one turn, and copy values from earlier tool results. \section{Discussion}
\label{sec:discussion}

\paragraph{Format versus reasoning.}
Several large swings are format. IFFC versus NFC (with the serving-slot caveat), Llama type coercion on a separate snapshot, and xLAM's native-tools collapse all show that the channel the harness parses can dominate the score before agentic policy is tested. That is useful: format is often cheaper to fix than weights. It is also a warning. Publishing an overall BFCL number from a different channel, or treating NFC 0\% on xLAM as an ability floor, would mis-state the result.

Once calls parse, consecutive accuracy is limited by environment-state tracking. IFFC still shares 124 failures with NFC. STATE and BoN move the point estimate by a few points and still leave VehicleControl and GorillaFileSystem mismatches as the mode. GST increases calling without reducing those mismatches. OODA-card on gated stop-on-repeat improves the point estimate while empty turns fall and state-mismatch counts stay above the IFFC baseline. Constrained name decoding (CD, PTC-A) and a Decision sidecar (plain IFFC 25.0\%; composed Decision+OODA 26.0\%; Choice-SLM Decision 5.5\%) both \emph{lower} execution accuracy. Validity of a call, and a second model ranking the next name, are not fidelity of a trajectory.

\paragraph{Cost--accuracy.}
On base Gemma, the observed Pareto picture is: IFFC at 30.5\% as the cheap JSON channel; gated hang-up and a status cheat sheet on that hang-up as low-overhead harness additions (32.5\% and 35.5\%); STATE at 34.0\% with extra context tokens; BoN on IFFC$+$STATE at 36.5\% for about $7\times$ generate wall. For a local laptop agent, a 2.5\pp\ BoN point-estimate gain at $7\times$ wall is a research measurement, not an obvious default. We did not apply BoN to collapsed or below-IFFC SFT checkpoints: majority vote cannot be assumed to rescue a policy that abstains or drifts.

\paragraph{Why SFT failed, then plateaued.}
The first SFT mixes taught the model to hang up after tools, because empty-list targets dominate post-execution assistant turns in ToolACE. Removing those targets restores calling (empty errors ${\approx}0$) but does not install BFCL-style state tracking. Further filters that try to complete turn~0 or drop state-inconsistent continues either over-call (v5) or miss the v4 recovery (v6). STATE, which helps the base model remember executed facts, is null or negative on the v4 checkpoint: the overlay is not a universal substitute for a policy that already mismatches the environment. Preference data that contrasts advance versus loop, rather than another supervised empty-list filter, was the remaining training hypothesis. A full DPO checkpoint later scored 53/200 (26.5\%) on plain IFFC---still below the untuned JSON baseline.

A later mix (v10) improved validation loss and still tied the untuned model on the 10-task check; extra epochs hurt format adherence. The data, not more epochs on that mix, is the remaining hypothesis. A repaired mix (v11) then trained to its best validation loss and collapsed on the 20-task gate (2/20 versus 17/20 for the untuned model; Section~\ref{sec:results-v11}). Beating 35.5\% with training remains open; 15.0\% is still the best historical trained row.

\paragraph{Paper IFFC versus the IFFC paper.}
Large lifts in~\cite{taheri2026iffc} are reported on single-turn Live/Non-Live suites, often where NFC is already weak, and often under dual QA / small-reasoner decoupling. Our Appendix~B-only multi-turn setup sits in a modest-gain band (${+}3.5$\pp point estimate, with the serving-slot caveat above). That is a different claim, not a refutation of theirs.

\section{Limitations and Roadmap}
\label{sec:roadmap}

All accuracy numbers are from the MacBook Pro in Section~\ref{sec:intro}. The registered working title still says ``edge devices'' (local branding); body claims are that measured laptop setting. RAG appeared in an earlier title framing and is \emph{out of scope} for this work---not evaluated, and not deferred as a near-term claim before December 2026. Multi-turn coverage is Gemma-centric, plus an xLAM channel contrast. Parallel AST categories remain artifactual zeros. Method knobs (STATE fields, $\mathrm{MIN}{=}6$, OODA card, SFT filters) were selected against the same \texttt{multi\_turn\_base} $N{=}200$ slice used for ranking; confirmatory re-score on \texttt{miss\_func}, \texttt{miss\_param}, \texttt{long\_context}, or an untouched split is future work. Health-gate probes are not BFCL percentages.

The following items remain open. No additional accuracies are reported here.

\begin{description}
  \item[DPO full train.] A $\beta{=}0.2$ 100-update smoke passed a 10-ID health gate. The full-train checkpoint is scored at 53/200 (26.5\%) on plain IFFC (Table~\ref{tab:scoreboard})---below IFFC 30.5\% and NFC 27.0\%. Other serving fields for that run are not verified. It is not a method win.
  \item[Decision compose / knowledge distillation.] Second-model helpers that pick the next tool scored below the plain JSON baseline on the full 200 (about 25--26\%, and ${\sim}5.5\%$ for a trained picker). Small 10-task trails are not full scores. We park this path; no rerun proposed. Smoke checks that the wiring works are not accuracy.
  \item[Missing inference ablations.] An OODA-card on plain IFFC is unscored, as is Best-of-N on plain IFFC. NFC at \texttt{-np 4} is an optional matched re-run; Contribution~2 remains the observed ${+}3.5$\pp under the disclosed eight-versus-four serving-slot asymmetry. Multi-seed BoN, parallel-category re-score after the GBNF bypass, and a unified type-coercion re-score with logged run IDs are likewise future work.
  \item[Other models' multi-turn.] Qwen2.5-3B, Llama-3.2-3B, Qwen3.5-4B, and FunctionGemma-270M have single-turn numbers only.
  \item[Jetson Orin Nano Super.] CUDA / 8~GB replication of the Mac result in Section~\ref{sec:intro} is not run.
  \item[Dual-model IFFC.] Paper Algorithm~1 (QA LLM $+$ small reasoning model) is deferred; this draft uses Appendix~B JSON-in-text on one model.
  \item[Parallel categories.] Re-run after the llama-server tools GBNF truncation fix; tables still report 0\%.
  \item[OODA factorial.] The scored card is stacked on gated stop-on-repeat. OODA-on-plain-IFFC remains a missing ablation. The \texttt{next} field is the deterministic advisory rule in Section~\ref{sec:method-overlays} (executed-tool history and the live user utterance; no reference trajectory). Whether the card can be revised without losing the 35.5\% point estimate is open.
  \item[Prefix constraints.] PTC-A is a scored failure (measured residuals in Table~\ref{tab:fail-later}). Token-level forced-name versus loop diagnosis is not fully audited. A second PTC variant is unscored and is not the next accuracy bet.
  \item[SFT-v11 and self-distillation (December critical path).] v11 training stopped early at 26{,}500/32{,}000 (best validation loss 0.030 at 22{,}000) and failed the 20-task gate (2/20, 1/20 without the card, 2/20 after a layout fix, versus 17/20 untuned). The null test (15/20) clears the pipeline. Filtered self-distillation scored 8/20 with a look-up-starved mix as the unproven cause; a rebalanced retrain is in progress with no result. Full 200 only after a model clears $\geq$17/20 and an explicit go. Best historical trained accuracy remains SFT-v4 at 15.0\%. Quota remixes after v4 are not scored at $N{=}200$. Preference/DPO is scored at 26.5\% and does not beat IFFC---not more epochs on v5/v6 and not BoN on those checkpoints.
  \item[SAP (later explore).] State-guided synthesis with argument provenance is a literature note, not the current train path. The v11 mix already used a SAP-style execute-validate recipe; unlocking the public SAP dump is future work.
  \item[Type-coercion protocol.] Table~\ref{tab:single-turn} versus Table~\ref{tab:coerce} Llama \texttt{multiple} baselines remain two snapshots; config/run IDs for the 41.5\% cell were not recovered from the evaluation database. A unified re-score with logged IDs is future work.
  \item[Preference-pair audit.] Contrastive advance-versus-loop pairs are an engineering draft, not a scored method.
  \item[IFFC serving metrics.] A 50-request metrics collect for the IFFC baseline remains pending; Table~\ref{tab:perf} therefore has no IFFC row.
\end{description}

\section{Conclusion}
\label{sec:conclusion}

Quantized small models on a MacBook Pro M4~Pro with llama.cpp already achieve strong single-turn tool selection in the Qwen 3--4B family (weighted non-parallel AST up to 82.53\%). FunctionGemma-270M is the generation-throughput winner and has the second-lowest median TTFT (Table~\ref{tab:perf}; not plotted in Figures~\ref{fig:perf}--\ref{fig:mem}). A separate type-coercion diagnostic is consistent with Llama \texttt{multiple} gaps being partly serialization, but that diagnostic is not a recovery of the single-turn table.

For consecutive tool calling on Gemma-4-E2B-it, cheap harness changes move the 200-task point estimate from failing most episodes (27.0\%) to finishing about one in three (36.5\% at roughly $7\times$ generate wall). Parsing calls from ordinary text, a scratchpad, hanging up on repeats, and a four-line status cheat sheet all sit in the low-to-mid 30s. Constrained decoding, a live name automaton, and a second-model Decision sidecar hurt (25.0\%; composed Decision+OODA 26.0\%, still below IFFC; Choice-SLM Decision 5.5\%). Supervised IFFC fine-tuning is easy to get spectacularly wrong (0.5\%) and, even after repairing empty-list hang-ups, stalls at 15.0\%---below the untuned model. Preference training scores 26.5\%, still below the JSON baseline. Residual failures are environment-state mismatches, especially on VehicleControl and filesystem backends, not unparsable JSON. Neighbour gaps on 200 tasks sit inside ordinary noise; treat the ranking as observed. The native-versus-JSON comparison used more parallel server slots on the native run.

Best-of-N remains the best measured inference point estimate (36.5\%); OODA-card remains the best non-BoN harness (35.5\%). Training still sits below that prompt-engineering bar (35.5\%); 15.0\% is the best historical trained row. The December critical path is finishing the repaired-mix train, then measuring on the 20-task gate and---only with a go---the 200-task bar. Decision and ranking sidecars are parked. Optional NFC at four server slots, other models' multi-turn baselines, dual-model IFFC, and parallel re-runs after the GBNF fix will determine how far local serving of this size can be pushed on the measured Mac stack before December 2026. RAG is out of scope.

\section{Method caveats}
\label{app:caveats}

These distinctions are part of the method identity:

\begin{itemize}
  \item Constrained decoding is a two-pass TagDispatch-style approximation on stock llama-server, not full XGrammar-2.
  \item GST is a prompt overlay on NFC. It is not GBNF and not IFFC. The checker ignores GST drafts.
  \item STATE is a harness-written snapshot from executed tool results, not LLM summarization.
  \item Best-of-N is majority vote at $N{=}5$ \emph{on IFFC$+$STATE}, not a learned verifier; generate wall is about $7\times$ (${\sim}3.0$~h$\to{\sim}21.3$~h).
  \item The OODA-card \texttt{next} field is a deterministic advisory hint from executed-tool history and the live user utterance (Section~\ref{sec:method-overlays}); it does not read reference trajectories or constrain decoding.
  \item Strip-empty (2.0\%) is serve-time history bookkeeping on the SFT-v2 GGUF, not a training method.
  \item SFT-v4 (15.0\%) is a recovery from 0.5\% collapse, not a win over IFFC or NFC.
  \item STATE on SFT-v4 (13.0\%) is a null/negative overlay: STATE helps base Gemma, not that checkpoint.
  \item xLAM 0\% / 3\% are this harness's native versus JSON channels, not published overall BFCL ${\sim}78.94\%$.
  \item PTC-A (13.5\%) is execution accuracy on this harness, not Yu et al.'s reported F1~\cite{yu2026ptc}. Token-level forced-name versus loop diagnosis is not fully audited.
  \item Decision sidecar (25.0\%) is a scored failure on plain IFFC (treatment-only). The helper was not dead. Composed \texttt{iffc-decision-ooda} is also a scored failure (52/200 $=$ 26.0\%; treatment-only; ${+}1.0$\pp over Run~58; still below IFFC--OODA). Choice-SLM Decision is a later scored failure (11/200 $=$ 5.5\%; treatment-only; ${-}19.5$\pp versus Run~58, ${-}20.5$\pp versus Run~61). Ranking is not Acc. Compose smoke and turn-0 timeout hygiene (Thesis \texttt{ee4d877} / probe \texttt{98f1b56}) are PASS; those are not Acc claims. Runs~59/60 (1/10 vs 0/10) and Runs~62/63 (0/10 vs 0/10) are 10-ID trails, not $N{=}200$.
  \item The DPO 10-ID result is a health-gate pass, not a BFCL percentage. Full DPO on plain IFFC is scored at 26.5\% (Run~51) and is not a win over IFFC or NFC.
  \item Soft10 (10-task) is a regression tripwire only; mid20 (20-task) is a go/no-go gate. Neither is the 200-task prompt-engineering bar (71/200 $=$ 35.5\%).
  \item SFT-v11 training stopped early at 26{,}500/32{,}000 (best validation 0.030 at 22{,}000) and failed the 20-task gate (Runs 70--72). Runs 73--74 are 20-task diagnostics, not 200-task scores.
  \item RAG appeared in an earlier registered-title framing and is out of scope for this paper---not evaluated, not deferred.
  \item Title ``edge devices'' is registered/local branding; measured accuracies are the MacBook Pro of Section~\ref{sec:intro}.
\end{itemize}
