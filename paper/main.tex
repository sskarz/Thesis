\begin{abstract}
Assistants that \emph{act}---edit a file, lock a car, place an order---do so by emitting \emph{tool calls} that a surrounding program executes. Running that loop on a local machine with a small language model (under five billion parameters) keeps data private and costs nothing per request, but small models often fail when a task takes several dependent calls. We study why, on the multi-turn base split of the Berkeley Function Calling Leaderboard (BFCL v4; 200 tasks graded by the final state of a simulated backend), using Gemma-4-E2B-it served locally on a MacBook Pro.

Three findings stand out. First, the failures are about \emph{state}, not \emph{syntax}: the same class of models that scores up to 82.5\% on single-call selection completes only 27.0\% of multi-turn tasks through the native tool API, and most remaining errors are tools that never ran or a world that ended in the wrong state. Forcing syntactically valid output makes things worse (10.5\% and 13.5\%). Second, \emph{structured inference-time control} helps without any training: writing calls as JSON text, a harness-written state scratchpad, stopping on repeated calls, and a four-line status card reach 71/200 (35.5\%, 95\% interval 29.2--42.3\%); a five-sample majority vote reaches 36.5\% at about seven times the generation time. Third, supervised fine-tuning on public and synthetic tool data \emph{lowered} accuracy: the best fine-tuned model reached 15.0\%, and a rebuilt training mix fell from 17/20 to 1--2/20 on a 20-task check. A null test that pushes the untuned model's own answers through the same pipeline scored 15/20, which points at the training data rather than the pipeline. With 200 tasks, neighbouring differences of a few points are within noise; the gap between inference-time control and fine-tuning is not.
\end{abstract}

\section{Introduction}
\label{sec:intro}

A useful assistant has to act, not only chat. To check a calendar or lock a car, a language model emits a \emph{tool call}: a machine-readable request (a function name plus arguments) that a surrounding program---the \emph{harness}---runs against a \emph{backend}, here a simulated vehicle or filesystem, and whose result is fed back to the model (Figure~\ref{fig:vignette}). Real tasks need several dependent calls in a row (\emph{multi-turn} or \emph{consecutive} tool calling): look up a value, use it, check the outcome, and know when to stop.

Running this loop locally with a \emph{small language model} (SLM; under five billion parameters here) keeps private data on the device, works offline, and has no per-request cost. The catch is accuracy. We measure Gemma-4-E2B-it~\cite{gemma4e2b}, a two-billion-effective-parameter model, on BFCL v4~\cite{patil2024bfcl}, served with llama.cpp~\cite{llamacpp} on a MacBook Pro (Apple M4~Pro, 48~GB). Out of the box, through the native tool interface, it completes 27.0\% of 200 multi-turn tasks.

We tried two families of fixes over several months: changing what happens \emph{at inference time} (how calls are written, what the harness shows the model, when the harness stops), and changing the \emph{weights} with supervised fine-tuning and preference optimization. This paper reports what that body of measurements says about \emph{why} small models fail and \emph{what helps}. Our contributions:

\begin{enumerate}
  \item \textbf{A failure anatomy: state, not syntax.} On the same hardware, small models reach up to 82.5\% on single-call selection but fail most multi-turn tasks. After calls parse, the dominant errors are \emph{under-calls} (a required tool never ran) and \emph{state mismatches} (tools ran, but the world ended wrong). Decoders that force valid output lower accuracy to 10.5--13.5\% (Section~\ref{sec:fail}).
  \item \textbf{Training-free control that helps.} Four cheap harness changes raise accuracy from 27.0\% to 35.5\% (71/200) with no weight updates; a five-sample vote reaches 36.5\% at about $7\times$ generation time. We report Wilson 95\% intervals and paired comparisons (Section~\ref{sec:helps}).
  \item \textbf{Evidence on how fine-tuning goes wrong, with controls.} Fine-tuning on public data taught the model to stop early (0.5\%); the best repair reached 15.0\%, below the untuned model. A rebuilt mix collapsed on a 20-task check (1--2/20 versus 17/20), a null test (15/20) clears the training pipeline, and an autopsy of a follow-up run points to a shift in the kinds of calls in the training mix as a likely, but unproven, cause (Section~\ref{sec:train}).
\end{enumerate}

\section{Background and Related Work}
\label{sec:related}

\paragraph{Benchmark.} The Berkeley Function Calling Leaderboard (BFCL) evaluates language models as API callers~\cite{patil2023gorilla,patil2024bfcl}. Its single-turn categories check one emitted call against a reference with an abstract-syntax-tree (AST) matcher. Its multi-turn categories run the model in an agent loop against simulated backends (for example VehicleControl and GorillaFileSystem, a sandboxed Unix-like filesystem) and compare the backends' final state to a reference. We use the \emph{multi-turn base} split (200 tasks, all tools available). Accuracy here is the fraction of the 200 tasks whose final state matches; it is not the public overall BFCL score, which averages many categories.

\paragraph{Output channel.} With \emph{native function calling} (NFC), the server receives a tool list and the model returns structured \texttt{tool\_calls}, as in most production APIs. With \emph{instruction-followed function calling} (IFFC), the model is instead asked in the prompt to write its calls as a JSON list in ordinary text, which the harness parses. Taheri et al.\ report that small models follow such JSON instructions more reliably than native tool APIs on single-turn BFCL~\cite{taheri2026iffc}; we use their single-model variant (their Appendix~B).

\paragraph{Constrained decoding.} Grammar-constrained generation restricts the next token so that output is always valid, for example to a JSON schema or to a list of tool names~\cite{willard2023outlines,dong2026xgrammar2}. Format restrictions can also reduce answer quality~\cite{tam2024format}. Yu et al.\ constrain tool names with a prefix-tree automaton~\cite{yu2026ptc}.

\paragraph{Prompting and test-time compute.} Guided-structured templates add a reasoning scaffold before calls~\cite{he2025gst}. Context-compression methods summarize long histories~\cite{kang2025acon}; our scratchpad is instead written by the harness from executed results. Typed observe--orient--decide--act (OODA) controllers structure agent steps~\cite{guo2026ooda}; our status card borrows only the name. Spending extra inference compute, for example by sampling several answers and voting, is a standard alternative to scaling parameters~\cite{snell2024testtime}.

\paragraph{Training for tool use.} Specialist small callers such as xLAM~\cite{zhang2024xlam}, Hammer~\cite{ye2025hammer} and FunctionGemma~\cite{google2025functiongemma} are trained on synthetic tool data such as ToolACE~\cite{liu2024toolace} and APIGen~\cite{liu2024apigen}. \emph{Supervised fine-tuning} (SFT) trains the model to reproduce target responses; we use low-rank adapters (LoRA)~\cite{dettmers2023qlora} with MLX~\cite{mlx}. \emph{Direct Preference Optimization} (DPO) instead trains on pairs of preferred and rejected responses~\cite{rafailov2023dpo,jung2025diatool}.

\section{Setup and Methods}
\label{sec:setup}

\paragraph{Models and serving.} The multi-turn model is Gemma-4-E2B-it, 4-bit quantized (Q4\_K\_M), served by \texttt{llama-server} (llama.cpp build 8111) with Metal acceleration on a MacBook Pro M4~Pro with 48~GB of memory. Decoding is greedy (temperature 0) except for majority voting. Most runs used four parallel server slots and a 65{,}536-token context; the native-API baseline used eight slots, a difference we return to in Section~\ref{sec:limits}. Peak process memory for the multi-turn jobs is about 15~GB. For the single-turn contrast we also serve Qwen2.5-3B~\cite{qwen25}, Llama-3.2-3B~\cite{llama32}, Qwen3.5-4B~\cite{qwen35} and FunctionGemma-270M~\cite{google2025functiongemma}.

\paragraph{Inference-time interventions.} All of these leave the model weights untouched and use the same checker (Appendix~\ref{app:method} gives the exact rules):
\begin{itemize}\setlength{\itemsep}{1pt}
  \item \textbf{JSON in text (IFFC)} instead of the native tool API (NFC).
  \item \textbf{State scratchpad.} After each executed call, the harness writes a short snapshot of facts from real results (current directory, known files, last calls) into the conversation.
  \item \textbf{Stop on repeats.} The harness ends a turn when the model re-proposes calls it has already executed, but only after six tool steps in the current user request, so short legitimate re-calls are not cut off. An \emph{ungated} variant stops at the first repeat.
  \item \textbf{Status card.} A four-line card (goal, known facts, last call and its outcome, and an advisory next move: call, ask, finish or refuse) is prefixed to the latest user message. It is filled deterministically from the conversation and executed results; it never sees reference answers. We call this the OODA card after the observe--orient--decide--act loop it loosely mirrors. The scored version is stacked on stop-on-repeats; this combination is our headline.
  \item \textbf{Vote of five (Best-of-N, BoN).} At each step, sample five candidate calls at temperature 0.7, execute the most common one, and continue; applied on top of the scratchpad.
  \item \textbf{Forced-valid decoding.} \emph{Constrained decoding} restricts output in two passes: first to an empty list or a list of valid tool names, then arguments to each tool's schema (an approximation of tag-triggered grammars~\cite{dong2026xgrammar2}). A \emph{tool-name automaton} constrains only the name and leaves arguments free, inspired by~\cite{yu2026ptc}.
\end{itemize}

\paragraph{Training-time interventions.} We train LoRA adapters on Gemma-4-E2B-it with MLX, merge, quantize to Q4\_K\_M and evaluate with JSON-in-text calls. Early mixes combine ToolACE multi-turn dialogues with sampled xLAM data; later mixes filter or rebalance specific target types. A later \emph{rebuilt mix} (30{,}000 training rows) combines about 45\% newly simulated, execution-checked episodes with cleaned public data. We also train one full DPO model.

\paragraph{Early checks.} A 200-task run takes hours, so trained models first pass cheaper checks: a 10-task tripwire and a 20-task gate (no overlap between them). Neither is a 200-task accuracy; Section~\ref{sec:gates} reports how well each predicts the full ranking.

\paragraph{Error labels.} Each failed task gets one primary label: \emph{empty turn} (no call on a turn that needed one), \emph{under-call} (a required tool never ran), or \emph{state mismatch} (tools ran but the backend's final state differs from the reference).

\paragraph{Statistics.} We report Wilson 95\% intervals computed from counts. For paired comparisons on the same 200 tasks we report how many tasks only one condition solves. Exact McNemar tests on adjacent rows were logged during the experiments and are quoted where available. We did not run new McNemar tests: per-task results are not stored in the repository, so in particular the headline versus the JSON and native baselines has not been tested pairwise.

\section{Where Small Models Fail}
\label{sec:fail}

On multi-turn tasks, Gemma-4-E2B-it through the native API completes 54 of 200 (27.0\%). Different models are involved, so this is a contrast of task difficulty rather than a controlled comparison; Gemma-4-E2B-it was used only for multi-turn work.

\paragraph{Forcing valid syntax hurts.} If failures were mostly malformed output, guaranteeing valid output should help. It does the opposite. Two-pass constrained decoding scores 21/200 (10.5\%; interval 7.0--15.5\%), 20.0\pp below JSON text, with 70 under-calls and 95 state mismatches. The tool-name automaton scores 27/200 (13.5\%; 9.4--18.9\%), with state mismatch rising to 102. Our two-pass approach approximates, rather than reproduces, full grammar engines~\cite{dong2026xgrammar2}, and we have not audited the token-level mechanism. Still, the measured effect is large and in the wrong direction: on this task, a valid call is not a correct next step.

\paragraph{JSON text over the native API (+3.5\pp).} Writing calls as JSON text scores 61/200 versus 54/200 natively. Paired, JSON text solves 22 tasks the native run misses and loses 15. Part of this gap may come from serving: the native run used eight parallel slots and the others four.

\paragraph{State scratchpad (+3.5\pp).} The harness-written snapshot scores 68/200; versus JSON text it gains 20 tasks and loses 13. Empty turns fall (41 to 31) while state mismatches do not (60 to 64), so the scratchpad mainly helps the model remember to keep calling.

\paragraph{Stop on repeats (+2.0\pp) and the status card (headline, 35.5\%).} Stopping after six repeated steps scores 65/200 (gains 11, loses 7 versus JSON text; logged McNemar $p\approx0.48$). Stopping at the \emph{first} repeat instead scores 54/200: every one of its 37 stops was on a failed task, so early stopping cuts healthy trajectories. Adding the status card on top scores 71/200 (versus stop-on-repeats alone: gains 26, loses 20; logged McNemar $p\approx0.46$). The card mostly reduces abstention---empty turns fall from 38 to 17---while state mismatches rise from 60 to 71. It helps the model act, not track state better.

\paragraph{Majority vote: the costly upper bound (36.5\%).} Voting over five samples on top of the scratchpad scores 73/200, one task more than the headline. Versus the greedy scratchpad it gains 17 and loses 12, and it cuts filesystem state mismatches from 21 to 13. It costs about $7\times$ the generation wall-clock (about 3.0 to 21.3 hours for 200 tasks) and about $5\times$ the server requests (8.4 to 42.7 per task), from a single sampling seed. For an on-device agent, the status card gives nearly the same accuracy at a fraction of the cost.

\paragraph{How sure are we?} Every interval in Table~\ref{tab:ladder} is about $\pm6$--7\pp wide, and none of the logged adjacent comparisons is significant. The ordering among the inference-time rows is therefore observed, not proven. Two contrasts are robust: the headline's interval (29.2--42.3\%) does not overlap the best fine-tune's (10.7--20.6\%) or the forced-valid decoders', and the best fine-tune solves only 7 tasks that JSON text misses while missing 38 that it solves.

\section{Why Fine-Tuning Did Not Help}
\label{sec:train}

Fine-tuning is the obvious way to teach a small model a task. Here it consistently lowered accuracy. We treat the runs as evidence about \emph{what} goes wrong.

\subsection{Public data taught the model to stop}
The first mixes scored 1/200 (0.5\%). In the training data, 5{,}520 assistant targets were an empty list---``no further call''---all from ToolACE. After a tool result, 78.1\% of targets were empty (2{,}121 empty versus 596 continue). The model learned to stop after its first tool result, while BFCL needs further calls on later turns. Dropping only mid-dialogue empty targets still scored 1/200; deleting trailing empty answers at serving time scored 4/200.

\subsection{Repairing the mix restored calling, not accuracy}
Removing those targets and adding recovery examples scored 30/200 (15.0\%), our best fine-tune. Empty turns nearly vanished (167 to 2), but failures moved to state mismatch (109) and under-call (59). Two further filtering variants scored 23/200 and 26/200; adding the scratchpad to the best fine-tune lowered it to 26/200, although the scratchpad helps the untuned model. Each variant changed several filters at once, so this is a supported reading, not a single-factor ablation. A full DPO model scored 53/200 (26.5\%), also below JSON text.

\subsection{Cheap checks: a 10-task tripwire cannot rank, a 20-task gate can}
\label{sec:gates}
Two fine-tuned checkpoints and the untuned model with the status card all scored 3/10 on the 10-task check, passing the same three tasks. Among 11 strong historical 200-task runs (at least 50/200), the 10-task score's rank correlation with the 200-task score was 0.118, so we keep it only as a regression tripwire. A 20-task gate tracks the 200-task ranking much better (leave-one-run-out rank correlation 0.857). The untuned model with the status card scores 17/20 on it; a trained model must match that before a full run.

\subsection{A rebuilt mix collapsed; a null test clears the pipeline}
The rebuilt mix trained to its best validation loss (0.030; early stopping at step 26{,}500 of 32{,}000). Its best checkpoint scored 2/20 on the gate (Figure~\ref{fig:gate}). It usually made one call and stopped, even when a setup step was needed (looking up a ticker, changing directory, logging in), and invented missing values such as an order number. Removing the status card scored 1/20; retraining on the test's exact tool-list layout restored some multi-call behaviour but still scored 2/20.

Was the pipeline itself the problem? As a \emph{null test}, we fine-tuned the untuned model for one pass on 156 of its own logged answers, through the same template, adapter, merge, quantization and serving steps. It scored 15/20 (interval 53--89\%) and kept the untuned model's habits. Two tasks below the bar is within noise for one 20-task run (the bar's own interval is 64--95\%), while the rebuilt mix's 2/20 (3--30\%) is far outside it. The collapse came from \emph{what} the rebuilt mix taught, not from the training machinery.

\subsection{Self-distillation and an unproven cause}
Training on only the turns the checker marked correct (440 self-generated rows) scored 8/20. Output stayed well formed, but in 6 of 12 failures the model said an ID, price or recipient was missing and stopped instead of calling the tool that would supply it. An autopsy found that the training ``stop'' rows were \emph{not} give-ups: none followed an error and all ended a completed turn. What changed was the mix. Look-up-type calls fell from 37.9\% of calls in the null-test data (67/177) to 19.7\% (78/395), and the share of stop targets rose from 23.1\% to 33.2\%. A model that rarely sees ``missing value, so look it up'' learns to stop. This cause is \emph{unproven}: the look-up counts come from a name-matching heuristic and there is no controlled ablation. A retrain with the stop share capped at the null-test level is in progress and is not reported here.

\paragraph{Summary.} Fine-tuning a 2B model on tool dialogues is fragile in a specific way: the \emph{distribution of decisions} in the targets (stop versus continue, look up versus act) is copied into behaviour, and validation loss does not reveal it. None of the trained models beats the untuned model with inference-time control.

\section{Discussion}
\label{sec:discussion}

\paragraph{State, not syntax.} Across conditions, the hard part is deciding the next step given the current state of the world---including whether to keep going---not writing a valid call. Interventions that \emph{inform} the model's decisions (a scratchpad of real results, a status card) help modestly. Interventions that \emph{constrain} its surface form (grammars, name automata) hurt. Training changed the balance between acting and stopping more than it improved tracking.

\paragraph{What we recommend for on-device agents.} Start with JSON-in-text calls, a harness-written state summary, a gated stop rule and a status card. These need no training data or GPU time, add little latency, and gave the best cost--accuracy point we measured. Treat sampling-and-voting as an upper bound unless latency does not matter. Before fine-tuning, audit the decision mix of the training targets, and gate on task-level checks rather than validation loss.

\paragraph{Absolute level.} Even the best configuration completes about one task in three. Small models are not yet reliable multi-step agents on this benchmark; the value of the results is in showing which levers move accuracy and which do not.

\section{Limitations}
\label{sec:limits}

\begin{itemize}\setlength{\itemsep}{1pt}
  \item \textbf{One model, one split.} All multi-turn results use Gemma-4-E2B-it on the 200-task base split. Settings (stop threshold, card fields, mix filters) were chosen on the same split used for ranking; other models and the harder BFCL splits are untested.
  \item \textbf{Sample size.} 95\% intervals are about $\pm7$\pp; the ordering among inference-time conditions is not statistically established. The 20-task gate is a screening tool, not a measurement.
  \item \textbf{Fairness of comparisons.} The native baseline used eight server slots versus four elsewhere; the status card and majority vote were never run on plain JSON text; majority vote used one seed. No new pairwise tests were run, because per-task results are not in the repository.
  \item \textbf{Approximate baselines.} Our constrained decoding approximates, rather than reproduces, full grammar engines.
  \item \textbf{Training confounds.} Mix variants changed several factors at once; the self-distillation cause is a hypothesis.
  \item \textbf{``Edge'' hardware.} Results are from a 48~GB laptop with about 15~GB peak memory; 8~GB embedded boards are unmeasured.
\end{itemize}

\section{Future Work}
\label{sec:future}

\begin{itemize}\setlength{\itemsep}{1pt}
  \item \textbf{Retrieval-augmented tool selection.} Retrieve the few relevant tools (and their documentation or past usage) for each step instead of placing every schema in context, as in retriever-aware tool use~\cite{patil2023gorilla,qin2023toolllm}. Shorter, more relevant context could help small models choose look-ups before actions, which is exactly the failure seen in the training runs.
  \item \textbf{Confirmatory runs.} Re-score the headline and JSON baseline on the harder BFCL multi-turn splits, on a second small model, with matched serving, and with stored per-task results for paired tests.
  \item \textbf{Decision-balanced training data.} Test the mix-shift hypothesis directly: vary the look-up and stop shares while holding everything else fixed.
  \item \textbf{Embedded hardware.} Repeat the headline configuration on an 8~GB device.
\end{itemize}

\section{Conclusion}
\label{sec:conclusion}

Small language models running locally can pick a single tool well but fail most multi-step tasks. On 200 BFCL v4 tasks with Gemma-4-E2B-it, those failures are mostly about state---tools that never ran and worlds that end wrong---not malformed output, and forcing valid output makes them worse. Training-free control in the harness lifted accuracy from 27.0\% to 35.5\% (36.5\% with costly voting). Fine-tuning on tool data did not reach that level: the best fine-tune scored 15.0\%. Controlled checks trace the damage to the decisions encoded in the training data rather than to the training pipeline. For practitioners, the cheapest lever is also the most effective one we measured.

\section{Intervention details}
\label{app:method}

\paragraph{JSON in text (IFFC).} Following Appendix~B of~\cite{taheri2026iffc}, the tool list is omitted from the API request; the system prompt asks for a JSON list of \texttt{\{function\_name, parameters\}} objects in assistant text. Tool results return as user messages. Calls map to the same BFCL function strings as native calling.

\paragraph{State scratchpad.} After each successful tool execution, the harness writes a compact \texttt{[STATE]} block from real results (current directory, known files, last executed calls). The last two turns stay verbatim; older raw outputs are dropped. It is not a model-written summary. Example:
\begin{quote}\footnotesize\ttfamily
[STATE]\\ cwd: /workspace/notes\\ files: todo.txt, log.csv\\ last: cd(folder='notes')->ok
\end{quote}

\paragraph{Stop on repeats.} After a tool result: (1) if the proposed call set equals the previous one, stop; (2) else if every proposed call was already executed in this user request \emph{and} at least six non-empty tool turns have occurred, stop; (3) otherwise execute. The six-step window resets on a new user question. The ungated variant applies rule (2) with no minimum.

\paragraph{Status (OODA) card.} Prefixed to a working copy of the latest user message (the stored transcript is unchanged), stacked on stop-on-repeats. Fields: \texttt{goal} (latest user question, truncated); \texttt{slots} (up to eight key--value facts from executed arguments and results); \texttt{last} (last executed call and outcome); \texttt{next} (advisory: \texttt{refuse} if no tools are available, \texttt{ask} if the last result signals a missing or invalid argument, \texttt{final} if the user's message is a closing ``thanks/done'', otherwise \texttt{call}). The hint does not constrain decoding and the card never reads reference trajectories. It is not the multi-pass OODA-Tool of~\cite{guo2026ooda}. Example:
\begin{quote}\footnotesize\ttfamily
[OODA]\\ goal: lock the car after I park\\ slots: engine=on\\ last: startEngine()->ok\\ next: call
\end{quote}

\paragraph{Vote of five.} On the scratchpad configuration, each step samples five completions at temperature 0.7, majority-votes the \texttt{(function\_name, arguments)} tuple, executes the winner once, and continues. It is not a learned verifier.

\paragraph{Constrained decoding.} Two requests per call: the first constrained to an empty list or a list of valid tool names, the second constraining arguments with each tool's JSON schema. No native tool grammar is active. This approximates XGrammar-2's tag-triggered dispatch~\cite{dong2026xgrammar2} on stock llama-server.

\paragraph{Tool-name automaton.} A live finite automaton restricts the tool name to valid names while arguments are free, on JSON text, not stacked on stop-on-repeats. Execution accuracy here is not comparable to the F1 reported by Yu et al.~\cite{yu2026ptc}.

\paragraph{Training.} LoRA adapters on Gemma-4-E2B-it with mlx-lm; best-validation checkpoint fused and quantized to Q4\_K\_M; evaluated with JSON text. The rebuilt mix: 30{,}000 training / 1{,}500 validation rows; 45/40/10/5\% simulated / APIGen / ToolACE / xLAM; 22\% empty-list targets (all after a tool result); 41.2\% of rows with multi-call targets; no evaluation tool names copied into simulations. DPO: $\beta{=}0.2$, LoRA, scored on JSON text.

\paragraph{Side experiments (demoted from the main text).}
\emph{Helper model.} A second small model ranking the next tool scored 50/200; combined with the status card, 52/200; a likelihood-ranking helper, 11/200, with 107 tasks repeating one tool eight or more times. Better first-tool ranking (0.800 versus 0.739 top-1) did not mean better task completion.

\emph{Shell commands as actions.} On the 13 filesystem-only tasks, native calls passed 3/13, JSON text 1/13, and two shell-dialect variants 1/13 and 0/13.

\emph{Native-API harder splits.} Native calling on the missing-function, missing-parameter and long-context splits scored 16/200, 39/200 and 22/200.
