\begin{abstract}
Small language models (SLMs) with fewer than five billion parameters are attractive for local agents, but consecutive, stateful tool calling remains unreliable. This paper evaluates quantized SLMs on the Berkeley Function Calling Leaderboard (BFCL) v4, taking multi-turn \emph{execution} accuracy on the 200-case \texttt{multi\_turn\_base} split as the primary agentic metric and single-turn abstract-syntax-tree (AST) accuracy as a supporting diagnostic. All own measurements use llama.cpp on a MacBook Pro with Apple M4~Pro (48~GB) and Metal---local / on-device SLM serving on consumer Apple Silicon. Jetson-class 8~GB deployment is unmeasured; this paper does not claim that the reported accuracies run on that hardware.

On single-turn AST (990 cases; parallel categories excluded after a serving-layer grammar bug), Qwen3.5-4B Q4\_K\_M reaches 817/990 (82.53\%), ahead of Qwen2.5-3B (76.06\%), FunctionGemma-270M (39.90\%), and Llama-3.2-3B (36.87\%). A separate type-coercion diagnostic (not the Table~\ref{tab:single-turn} protocol) finds that schema-aware coercion plus a system prompt can move Llama \texttt{multiple} accuracy from 41.5\% to 92.0\% on that snapshot, consistent with argument serialization rather than tool selection.

On multi-turn, Gemma-4-E2B-it Q4\_K\_M scores 54/200 (27.0\%) with native function calling and 61/200 (30.5\%) with Instruction-Followed Function Calling (IFFC; JSON tool calls in ordinary assistant text). The observed ordering of stacked overlays is IFFC$+$STATE at 34.0\%, gated stop-on-repeat at 32.5\%, and an OODA-style status card \emph{on gated stop-repeat} at 35.5\%. Best-of-N majority voting ($N{=}5$) \emph{on IFFC$+$STATE} reaches 73/200 (36.5\%) at roughly $7\times$ generate wall-clock (${\sim}3.0$~h$\to{\sim}21.3$~h). Adjacent point-estimate gaps on $N{=}200$ are not significant by McNemar's test; a Wilson 95\% interval at 36.5\% has half-width ${\approx}{\pm}6.6$\pp. Constrained decoding (10.5\%) and a live tool-name automaton (13.5\%) are scored regressions. Supervised fine-tuning on IFFC mixes scores 0.5\% when ToolACE empty-list (\texttt{[]}) targets after tool results dominate the mix, recovers to 15.0\% after curriculum repair, and still underperforms the untuned base model. Direct Preference Optimization has passed a 10-example health gate; as of 2026-09-29 a capped full train is in flight with no $N{=}200$ accuracy yet.
\end{abstract}

\section{Introduction}
\label{sec:intro}

An on-device agent must do more than emit a single well-formed API call. It has to choose a tool, fill typed arguments, incorporate execution feedback, and decide when \emph{not} to call anything. Errors cascade: a wrong function, a stringified integer, or a hallucinated call can leave the environment in a state that later turns cannot recover. Cloud-scale models are routinely scored for these behaviors. Local / on-device SLM serving instead needs interactive latency on consumer silicon---here, a MacBook Pro with Apple M4~Pro (48~GB).

This work studies SLMs under five billion parameters served with llama.cpp~\cite{llamacpp} on Apple Silicon. The motivating setting is a local agent loop: the model proposes calls, a harness executes them against a live \emph{backend} (a simulated application such as a vehicle controller or a sandbox filesystem), and the next user turn depends on the resulting state. Two failure families dominate that loop. \emph{Format} failures are syntactic or channel mismatches---native \texttt{tool\_calls} versus JSON in text, stringly-typed arguments, truncated parallel grammars---that can look like reasoning errors on a leaderboard. \emph{State} failures are agentic: the model calls something valid but drifts from the environment, repeats a completed action, or \emph{under-calls} (stops before a required tool has run). Differences are reported in percentage points (\pp).

The questions are empirical:

\begin{enumerate}
  \item How accurately do quantized SLMs perform single-turn tool selection and multi-turn consecutive calling on BFCL v4 when served locally with Metal?
  \item How much of measured failure is format and serving infrastructure versus genuine multi-turn state tracking?
  \item Which inference-time interventions (output channel, working memory, decoding constraints, test-time voting, simple guardrails) and which training-time interventions (supervised fine-tuning, preference optimization) move the primary multi-turn metric?
\end{enumerate}

Retrieval-augmented generation (RAG) appeared in an earlier registered-title framing. It is \emph{out of scope} for this work: not evaluated, and not deferred as a near-term claim.

\paragraph{Contributions.}
\begin{enumerate}
  \item \textbf{A local / on-device BFCL v4 baseline} for four quantized SLMs on single-turn AST, plus Gemma-4-E2B-it on multi-turn execution, all on a MacBook Pro M4~Pro (48~GB) with llama.cpp Metal. These accuracies are not claimed for 8~GB Jetson-class hardware.
  \item \textbf{Format is first-order, with a serving caveat.} Gemma IFFC JSON-in-text scores ${+}3.5$\pp versus native tool calls on \texttt{multi\_turn\_base} (61/200 versus 54/200). That native baseline used eight parallel server slots (\texttt{-np 8}); IFFC used four (\texttt{-np 4}). A matched native run at \texttt{-np 4} has not been scored, so part of the gap may be serving rather than channel. Separately, a type-coercion diagnostic on Llama \texttt{multiple} (not the Table~\ref{tab:single-turn} snapshot) moves 41.5\% to 92.0\%. A published xLAM-1b checkpoint scores 0\% on this native-tools harness and 3\% on a JSON-in-text adapter---neither figure is the public overall BFCL number.
  \item \textbf{Stacked inference overlays, as an observed $N{=}200$ ordering.} On base Gemma, IFFC$+$STATE is 34.0\%; gated stop-on-repeat is 32.5\%; an OODA-style card \emph{on gated stop-repeat} is 35.5\%; Best-of-N majority vote \emph{on IFFC$+$STATE} is 36.5\% at ${\sim}7\times$ generate wall-clock. Adjacent McNemar tests are not significant (Section~\ref{sec:results-helped}). Constrained decoding and a live name automaton do not help. Missing factorials (OODA on plain IFFC; BoN on plain IFFC) are listed in Section~\ref{sec:roadmap}.
  \item \textbf{Supervised IFFC fine-tuning is brittle on this mix.} A supported hypothesis is that ToolACE empty-list targets after tool results teach stop-after-tools; the original mix scores 0.5\%. Mix surgery recovers 15.0\% but does not beat untuned IFFC (30.5\%) or native calling (27.0\%). Working memory that helps the base model does not help that checkpoint. No single-factor empty-list ablation holding optimizer and mix size fixed was run.
  \item \textbf{Preference optimization is the open training path.} A Direct Preference Optimization (DPO) smoke run passed a 10-example health gate. As of 2026-09-29 a capped full train is in flight; this draft reports no $N{=}200$ DPO accuracy.
\end{enumerate}

\section{Background and Related Work}
\label{sec:related}

\subsection{BFCL and consecutive tool calling}
The Berkeley Function Calling Leaderboard (BFCL) and the Gorilla line of work evaluate language models as API callers~\cite{patil2023gorilla,patil2024bfcl}. We use BFCL v4.

Single-turn categories are scored with an AST checker: the model sees a user query and a tool schema and must emit a call (or none) whose structure matches a reference, allowing equivalent argument order. Categories include \texttt{simple} (one available function), \texttt{multiple} (several functions, pick the right one), \texttt{parallel} / \texttt{parallel\_multiple} (several calls in one turn), \texttt{irrelevance} (the query needs no call), and Java / JavaScript typed variants.

Multi-turn categories are scored with an \emph{execution} checker. The model enters an agent loop; tools run against a live \emph{backend}---a simulated application whose instance state the checker compares to a reference trajectory. Recurring backends in this paper include VehicleControl (start/lock/brake-style vehicle APIs) and GorillaFileSystem (a sandbox Unix-like filesystem). The four slices are \texttt{multi\_turn\_base} (full tool set), \texttt{miss\_func} (some tools withheld until later), \texttt{miss\_param} (required arguments omitted from the query), and \texttt{long\_context} (large histories). This paper's optimization target is \texttt{multi\_turn\_base} ($N{=}200$). Paper percentages on that slice are \emph{not} public overall-BFCL leaderboard scores, which mix many categories and often different serving stacks.

We bucket failed entries with one primary label each. \emph{Empty turn} means the model emitted no callable output on a turn that needed one. \emph{Under-call} (missing ground-truth execution) means required tools never ran. \emph{State mismatch} means tools ran but the backend instance diverged from the reference. Observe--orient--decide--act (OODA) in this paper is a one-pass status card, not Boyd's four-stage military loop and not a four-pass controller~\cite{guo2026ooda}.

\subsection{Native versus instruction-followed function calling}
\paragraph{Native function calling (NFC).}
The server is given OpenAI-style \texttt{tools} and the model is expected to return structured \texttt{tool\_calls}. llama.cpp may compile a grammar (GBNF) once chat-template trigger tokens appear. This is the default production channel for many local stacks.

\paragraph{Instruction-followed function calling (IFFC).}
Taheri et al.~\cite{taheri2026iffc} argue that small models can follow JSON instructions more reliably than native tool APIs. Their paper reports large gains on BFCL v3 \emph{single-turn} suites, often with a dual-model design that separates a QA model from a small reasoning model (their Algorithm~1). We implement only Appendix~B: the \emph{same} model emits a JSON list of \texttt{\{function\_name, parameters\}} objects in assistant text, with no native \texttt{tools} field. Dual-model IFFC is deferred (Section~\ref{sec:roadmap}).

\subsection{Structured decoding, templates, and test-time compute}
XGrammar-2 describes efficient dynamic structured generation, including TagDispatch for tag-triggered grammar switches~\cite{dong2026xgrammar2}. That work reports, for example, lifting Llama-3.2-3B correct-call rates from 33\% to 78\% \emph{under its engine and metric}---prior-work figures, not our measurements, and \emph{not} comparable to the Llama 33.50\% BFCL v4 \texttt{multiple} cell in Table~\ref{tab:single-turn} (different task, checker, and serving stack). Our constrained-decoding ablation approximates TagDispatch with two stock llama-server requests and is not full XGrammar-2. Guided generation more broadly is studied by Willard and Louf~\cite{willard2023outlines}; format restrictions can also hurt quality~\cite{tam2024format}.

He et al.~\cite{he2025gst} propose seven-step guided-structured templates (GST) that improve function calling on BFCL v2. We overlay their Detail template as a prompt on NFC; the checker executes native \texttt{tool\_calls} and ignores GST draft text. This is not a grammar and not IFFC.

Snell et al.~\cite{snell2024testtime} frame test-time compute versus parameter scaling. Our Best-of-N is majority vote over sampled tool-call tuples, not tree search and not a learned verifier.

\subsection{Working memory and specialist SLM callers}
ACON compresses older turns with learned or LLM-written summaries~\cite{kang2025acon}. Our STATE overlay is a harness-written key-value snapshot from \emph{executed} tool results, not an LLM summary.

Guo et al.\ propose OODA-Tool, a typed observe--orient--decide--act controller, including a multi-pass Specialized variant~\cite{guo2026ooda}; we do not score that paper's method. Yu et al.\ propose PTC-Decoder (plan-to-act plus a tool-name DFA) and report F1 on a Jetson/satellite LLM-judge setup~\cite{yu2026ptc}; we do not reproduce those F1 numbers. Our PTC-A row is execution accuracy on this BFCL harness.

Error taxonomies for sub-7B callers often rank type mismatch among dominant failures~\cite{liu2024apigen}. Specialist models such as FunctionGemma~\cite{google2025functiongemma}, Hammer~\cite{ye2025hammer}, and xLAM~\cite{zhang2024xlam} show that fine-tuning and format design can make small models competitive. We treat type coercion as an inference-time mitigation that does not change weights, and we score a published xLAM-1b GGUF on \emph{this} harness rather than citing the public overall figure (${\sim}78.94\%$) as a reproduction.

\subsection{Training-time methods}
QLoRA is the standard efficient-finetuning reference~\cite{dettmers2023qlora}; we train LoRA adapters with MLX on Apple Silicon~\cite{mlx}, not QLoRA-on-CUDA. ToolACE~\cite{liu2024toolace} and xLAM supply the IFFC JSON-in-text mix. Direct Preference Optimization~\cite{rafailov2023dpo} and dialogue-level variants such as DiaTool-DPO~\cite{jung2025diatool} motivate a preference path after SFT proved brittle; our DPO evidence in this draft is a health gate, not a BFCL score.

\subsection{Output channels}
\label{sec:method-channels}

\paragraph{NFC.}
The harness sends \texttt{tools} and \texttt{tool\_choice=auto}. Assistant outputs are native \texttt{tool\_calls}. This is the Gemma multi-turn baseline and the channel used for the xLAM native-tools probe.

\paragraph{IFFC.}
Following Appendix~B of~\cite{taheri2026iffc}, we omit \texttt{tools}. The system prompt asks for a JSON list of \texttt{function\_name} / \texttt{parameters} objects in assistant text. Tool results return as user-role messages. Trajectories are mapped to the same BFCL function strings used by NFC.

\paragraph{xLAM JSON channel.}
Salesforce xLAM-1b-fc-r is trained to emit \texttt{\{"tool\_calls":[\ldots]\}} in content, not OpenAI \texttt{tool\_calls}. A format adapter parses that JSON and executes tools. This is a channel fix for a published checkpoint, not a new training method.

\paragraph{Shell dialect.}
An allowlisted Unix-like text dialect is mapped onto GorillaFileSystem calls (e.g., \texttt{cd notes} $\to$ \texttt{cd(folder='notes')}) and scored only on the 13 filesystem-only IDs in \texttt{multi\_turn\_base}. It is a format ablation, not a substitute for the 200-entry score.

\subsection{Inference overlays on IFFC or NFC}
\label{sec:method-overlays}

\paragraph{Guided-structured templates (GST$+$NFC).}
The He et al.\ Detail curriculum is prepended as a one-shot system prompt on top of NFC~\cite{he2025gst}. The model is asked to write a \texttt{[GST]} scaffold before native \texttt{tool\_calls}. The checker ignores the scaffold.

\paragraph{Harness STATE.}
IFFC is unchanged as a channel. After each successful tool execution, the harness writes a compact \texttt{[STATE]} snapshot from real results (cwd, known files, last executed calls) and attaches it in user messages. The last two turns stay verbatim; older raw dumps are dropped. This is not LLM summarization~\cite{kang2025acon}. Example shape (fields come from executed backends, not from the model):

\begin{quote}
\footnotesize\texttt{[STATE]}\\
\texttt{cwd: /workspace/notes}\\
\texttt{files: todo.txt, log.csv}\\
\texttt{last: cd(folder='notes')->ok; cat(file\_name='todo.txt')->ok}\\
\texttt{[/STATE]}
\end{quote}

\paragraph{Best-of-N (BoN).}
On the IFFC$+$STATE channel, each agent step samples $N{=}5$ completions at temperature 0.7, majority-votes the \texttt{(function\_name, arguments)} tuple, executes the winner once, and continues. Latency is roughly $N$ greedy decodes. This is not a verifier. \emph{API calls} in timing tables are llama-server request counts (BoN inflates them by about $N$ samples per step), distinct from tools executed and from user turns.

\paragraph{Stop-on-repeat.}
After a tool-result observation, the harness may stop the turn without re-executing. Logic (from \texttt{benchmark/stop\_on\_repeat.py}):

\begin{enumerate}
  \item If the proposed IFFC call set equals the previous assistant call set (\texttt{consecutive\_identical}), stop immediately.
  \item Else if every proposed call was already executed in this user-ask \emph{and} at least $\mathrm{MIN}{=}6$ nonempty assistant tool-turns have occurred (\texttt{observe\_same\_call}), stop.
  \item Otherwise execute. The MIN window resets on a fresh BFCL user question, not on an execution dump, so short VehicleControl re-calls (3--5 steps) are not treated as loops.
\end{enumerate}

An \emph{ungated} version fires observe-same immediately ($\mathrm{MIN}{=}0$). This is a decode/harness guardrail, not a retrain.

\paragraph{OODA-card.}
A one-pass status card with fields \texttt{goal}, \texttt{slots}, \texttt{last}, and \texttt{next} is stacked on tightened stop-repeat ($\mathrm{MIN}{=}6$). Per METHODS, \texttt{next} is an advisory construction (a one-pass status hint, not a scored oracle ablation). This paper does not add a formal no-oracle proof beyond that METHODS wording. This is not Guo et al.'s four-pass Specialized OODA-Tool~\cite{guo2026ooda} and not the STATE overlay. An OODA-card on \emph{plain} IFFC (without stop-repeat) is a missing ablation; this draft reports no such accuracy.

\paragraph{TagDispatch-style constrained decoding (CD).}
Stock llama-server does not expose intra-request tag-triggered grammar switches. We approximate TagDispatch with two requests and never send \texttt{tools}, so native tools GBNF does not activate. Pass~1 constrains the completion to an empty list or a list of live \texttt{function\_name} values. Pass~2 constrains arguments for the selected names via \texttt{json\_schema}. This is not full XGrammar-2 (no intra-request tag switch, two HTTP requests per tool invocation).

\paragraph{Prefix-tree name constraint (PTC-A).}
A live deterministic finite automaton constrains the tool \emph{name} while arguments remain free. This is inspired by Yu et al.'s PTC-Decoder~\cite{yu2026ptc}; it is not a reproduction of that work's F1 numbers (different metric, hardware, and judge), and it is not the two-pass CD ablation above. PTC-A is scored on base IFFC, not stacked on stop-repeat. Token-level forced-name decoding versus loop behavior is not fully audited; we report measured residuals rather than a mechanism story.

\subsection{Type coercion}
\label{sec:method-coerce}

Llama-3.2-3B often selects the correct function on \texttt{multiple} but serializes integers, floats, arrays, and objects as JSON strings. We apply (i)~a system prompt requiring native JSON types and (ii)~schema-aware post-hoc coercion of argument values to the BFCL parameter types. Both are inference-time only.

\subsection{Parallel grammar bug}
\label{sec:method-parallel}

When \texttt{tools} are present, llama-server may compile a tools grammar whose repetition structure mismatches the model's trained multi-call delimiters. Generation can stop after the first closing tag, truncating parallel output. A bypass (\texttt{tool\_choice none} with content parsing) is implemented; re-measurement is pending, so tables still report 0\% for \texttt{parallel} and \texttt{parallel\_multiple}.

\subsection{Supervised fine-tuning and preference optimization}
\label{sec:method-sft}

We train LoRA adapters on Gemma-4-E2B-it with mlx-lm~\cite{mlx} using an IFFC JSON-in-text mix (ToolACE multi-turn~\cite{liu2024toolace} plus stratified xLAM~\cite{zhang2024xlam}), fuse a best-validation checkpoint, quantize to Q4\_K\_M, and evaluate under IFFC on \texttt{multi\_turn\_base}. Mix variants drop empty-list assistant targets after tool results, drop first-turn empty answers, and try turn-0 / state-consistency filters. A serve-time diagnostic strips trailing assistant \texttt{[]} from chat history without retraining; we do not treat that diagnostic as a method.

A 100-update DPO smoke ($\beta{=}0.2$) from the untouched Gemma MLX base is used only as a health gate (call volume, parseability, first-turn tool use on 10 IDs). As of 2026-09-29 a capped full DPO train is in flight. This paper does not report a DPO \texttt{multi\_turn\_base} accuracy.

\section{Experimental Setup}
\label{sec:setup}

\subsection{Hardware and serving}
All own experiments run on a MacBook Pro with Apple M4~Pro (48~GB), Metal GPU acceleration, llama.cpp build 8111 (commit \texttt{11c325c6e}), compiled with \texttt{-DGGML\_METAL=ON}. Models are served with \texttt{llama-server --jinja}, flash attention on, and full GPU offload (\texttt{-ngl 99}). Peak resident set size (RSS) on this stack is dominated by the KV cache at the configured context length, plus model weights (bf16 for FunctionGemma). NVIDIA Jetson Orin Nano Super (CUDA, 8~GB) deployment is unmeasured. Several Mac peak-RSS values already exceed 8~GB; this paper does not claim that current accuracies run on that board (Section~\ref{sec:roadmap}).

\subsection{Models}
Single-turn matrix (Q4\_K\_M unless noted): Qwen2.5-3B-Instruct, Llama-3.2-3B-Instruct, Qwen3.5-4B, and FunctionGemma-270M-IT (bf16; the published precision). Multi-turn primary model: Gemma-4-E2B-it Q4\_K\_M. External baseline: Salesforce xLAM-1b-fc-r Q4\_K\_M. Decoding for reported accuracy uses temperature 0.0 except BoN (temperature 0.7, $N{=}5$). Overnight multi-turn jobs use \texttt{-np 4 -c 65536}, except the NFC baseline, which used \texttt{-np 8} (Section~\ref{sec:results-helped}).

\subsection{Evaluation protocol}
Single-turn: BFCL AST checker. Multi-turn: BFCL execution checker. FunctionGemma control-token outputs are normalized with a dedicated parser when llama-server does not already map them to \texttt{tool\_calls}. Weighted single-turn averages exclude \texttt{parallel} and \texttt{parallel\_multiple} (990 remaining cases). Failure buckets use one primary error per failed entry unless noted as raw eval-error rows. In timing tables, \emph{API calls} means llama-server / model-server request count, not tools executed and not user turns; BoN inflates the count by about $N$ samples per agent step. Chronological IDs in Appendix~\ref{app:runs} are local SQLite bookkeeping for the \texttt{multi\_turn\_base} $N{=}200$ scoreboard only.

\section{Single-turn Results}
\label{sec:results-st}

\subsection{What helped (observed ordering)}
\label{sec:results-helped}

Point estimates on $N{=}200$ have a Wilson 95\% half-width of about ${\pm}6.6$\pp at 36.5\%. McNemar exact two-sided tests on adjacent pairs are not significant, so language below is an \emph{observed ordering}, not a claim of pairwise-significant lifts.

\paragraph{IFFC versus NFC (${+}3.5$\pp point estimate).}
JSON-in-text scores 61/200 versus 54/200 native. Pairwise, both fail on 124 entries; IFFC rescues 22 and regresses 15. Using the same primary buckets as Table~\ref{tab:fail} (one error per failed entry), empty-turn counts fall 59$\to$41 and state-mismatch 68$\to$60. (Raw NFC \texttt{eval\_errors} rows are much larger because one entry can contribute several rows; we do not mix those with IFFC primaries.) Once calls parse, residual error is environment fidelity, not the channel label.

The NFC baseline was served with \texttt{-np 8}; IFFC used \texttt{-np 4}. A matched NFC@\texttt{-np 4} accuracy has not been measured, so the ${+}3.5$\pp channel gap is confounded with serving.

\paragraph{Harness STATE (${+}3.5$\pp over IFFC).}
Working memory from executed tools scores 68/200 (34.0\%) on \emph{base} Gemma, above the 30.5\% IFFC/GST plateau. Versus IFFC the overlap is shared 48, rescue 20, regress 13 (net ${+}7$). Empty turns fall 41$\to$31 while state mismatch does not improve (60$\to$64). STATE appears to help forgotten calls more than env-diff fidelity. Stored response blobs contain literal \texttt{[STATE]} in 0/200 rows, as expected: STATE is conversation context written by the harness.

\paragraph{Gated stop-on-repeat (${+}2.0$\pp over IFFC).}
Waiting until six observe-same tool-turns before forcing a stop scores 65/200 (32.5\%). Versus plain IFFC: shared 54, rescue 11, regress 7; McNemar $p{\approx}0.48$ (n.s.). Stop flags fall from 37/200 (ungated) to 3/200, all still failures. VehicleControl state-mismatch counts return to the IFFC baseline (22, versus 33 ungated). This is a harness guardrail on the base checkpoint, not a training win.

\paragraph{OODA-card on gated stop-repeat (${+}3.0$\pp over gated stop-repeat).}
The one-pass status card, stacked on $\mathrm{MIN}{=}6$ stop-repeat, scores 71/200 (35.5\%): best non-BoN point estimate, 1.0\pp\ below BoN. Versus gated stop-repeat: shared 45, rescue 26, regress 20; McNemar $p{\approx}0.46$ (n.s.). Empty-turn primaries fall 38$\to$17 while state mismatch rises 60$\to$71 and under-call 37$\to$41, consistent with anti-abstention rather than better state tracking (Q10). Median TTFT was 517.8~ms versus 630.5~ms on gated stop-repeat; we do not interpret that as a causal end-to-end speedup (card-build cost and generate wall were not the claim). OODA on \emph{plain} IFFC is a missing ablation (no accuracy reported).

\paragraph{Best-of-N majority vote on IFFC$+$STATE (${+}2.5$\pp over STATE, ${\sim}7\times$ generate wall).}
Sampling $N{=}5$ on IFFC$+$STATE scores 73/200 (36.5\%), the best measured inference point estimate. Versus greedy STATE: shared 56, BoN-only 17, greedy-only 12. Table~\ref{tab:bon-cost} reports cost: ${\sim}7\times$ is generate wall-clock (${\sim}3.0$~h$\to{\sim}21.3$~h); other rows are different meters (${\sim}8.8\times$ predicted time, ${\sim}9.5\times$ prompt time, ${\sim}5.1\times$ API-call count). Only one BoN seed (temperature 0.7) was run. We did not score BoN on plain IFFC.

\subsection{What did not beat IFFC}
\label{sec:results-hurt}

\paragraph{Ungated stop-on-repeat (27.0\%, ${-}3.5$\pp versus IFFC).}
Stopping at the first repeated observation matches NFC's 54/200 but is a different method, not a reproduction of native calling. All 37 stop flags land among the 146 failures (zero stopped-and-correct). VehicleControl state mismatches rise 22$\to$33. Early stopping helps only loop-dominated traces; on healthy base Gemma it cuts good trajectories.

\paragraph{Constrained decoding (10.5\%).}
The two-pass name-then-args approximation scores 21/200: ${-}16.5$\pp versus NFC and ${-}20.0$\pp versus IFFC (179 errors). Syntactic validity is not consecutive correctness on this stack. This is not a claim about full XGrammar-2 TagDispatch.

\paragraph{PTC-A (13.5\%, scored failure).}
A live tool-name automaton on \emph{base IFFC} scores 27/200: ${-}22.0$\pp versus OODA-card on gated stop-repeat, ${-}19.0$\pp versus gated stop-repeat, ${-}17.0$\pp versus IFFC. Measured residuals: state mismatch 102, empty turn 17, under-call 54. Yu et al.\ report F1 in a different setting~\cite{yu2026ptc}; those F1 numbers are not this harness Acc. A token-level diagnosis of forced-name decoding versus loop behavior is not fully audited; we do not invent a mechanism story. We treat PTC-A as a scored failure and do not remix prefix constraints as the next accuracy bet. A second PTC variant is unscored.

\paragraph{xLAM on this harness (0\% then 3\%).}
Under NFC, the published xLAM-1b-fc-r Q4\_K\_M GGUF scores 0/200: every error is an empty turn-0 tool-call list. The server generated tokens (mean 3.63 llama-server requests), but NFC never parses assistant \texttt{content}. \subsection{SFT empty-list mixes collapse}
\label{sec:results-sft-collapse}

LoRA on the original IFFC mix scores 1/200 (0.5\%). A live single-step probe still emits valid IFFC JSON, so this is not a parser or chat-template failure. The dominant behavior is early stop with an empty list \texttt{[]} after tool results. The MLX mix contains 5520 assistant \texttt{[]} targets, all from ToolACE (32.5\% of ToolACE assistant turns; xLAM 0\%). After a ``Function execution results'' user message, 78.1\% of assistant targets are \texttt{[]} (2121 empty versus 596 continue). A \textbf{supported hypothesis}, not a single-factor proof, is that this mix teaches stop-after-tools, whereas BFCL multi-turn requires continued calls on later user turns. Mix variants v2--v6 change several filters at once; no ablation holds optimizer, rank, and mix size fixed while toggling only empty-list targets.

Figure~\ref{fig:sft} shows the scored slice. Stripping trailing assistant \texttt{[]} from chat history at serve time, without retraining, reaches only 4/200 (2.0\%). Turn-0 empty errors remain 153. \subsection{Further mix surgery regresses; STATE does not transfer}
\label{sec:results-sft-later}

IFFC$+$STATE on the same v4 GGUF scores 26/200 (13.0\%): ${-}2.0$\pp versus plain IFFC on that checkpoint. Contrast: STATE on base Gemma was ${+}3.5$\pp. Empty stays rare (3); residual remains state mismatch (112) and under-call (59).

SFT-v6 keeps v4 empty/recovery plus only the state-inconsistency drop (turn-0 underspecification filters off). It scores 26/200 (13.0\%): a miss versus v4, a modest lift versus v5. Empty remains essentially suppressed (1). Mean API calls return to 13.34. State mismatch is 118 and under-call 55.

Thin filter ablations on this ToolACE$+$xLAM IFFC family did not beat v4. A later 10-ID quota-remix smoke failed a health gate (mean 25.7 llama-server requests, 6/10 traces hit the step limit); that gate is not a BFCL percentage, and no $N{=}200$ score is claimed.

\subsection{DPO: health gate passed, full-train results pending}
\label{sec:results-dpo}

A 100-update DPO smoke ($\beta{=}0.2$, LoRA, fused Q4\_K\_M) passed the same style of 10-ID health gate used to reject collapsed SFT smokes: mean llama-server requests 4.4 (band 4--8.3), 0/10 step-limit hits, 0/10 unparseable IFFC, 7/10 first-turn tool uses. That is evidence the training stack did not immediately collapse. It is not a \texttt{multi\_turn\_base} score.

As of 2026-09-29 a capped full DPO train is in flight. This draft reports no $N{=}200$ DPO accuracy, does not treat the smoke checkpoint as a scoreboard row, and does not claim a method win. Whether to add an $N{=}200$ row when that train is scored remains an open documentation choice (Section~\ref{sec:roadmap}).

\section{Discussion}
\label{sec:discussion}

\paragraph{Format versus reasoning.}
Several large swings are format. IFFC versus NFC (with the \texttt{-np} confound), Llama type coercion on a separate snapshot, and xLAM's native-tools collapse all show that the channel the harness parses can dominate the score before agentic policy is tested. That is useful: format is often cheaper to fix than weights. It is also a warning. Publishing an overall BFCL number from a different channel, or treating NFC 0\% on xLAM as an ability floor, would mis-state the result.

Once calls parse, consecutive accuracy is limited by environment-state tracking. IFFC still shares 124 failures with NFC. STATE and BoN move the point estimate by a few points and still leave VehicleControl and GorillaFileSystem mismatches as the mode. GST increases calling without reducing those mismatches. OODA-card on gated stop-repeat improves the point estimate while empty turns fall and state-mismatch counts stay above the IFFC baseline. Constrained name decoding (CD, PTC-A) improves or enforces syntax and \emph{lowers} execution accuracy. Validity of a call is not fidelity of a trajectory.

\paragraph{Cost--accuracy.}
On base Gemma, the observed Pareto picture is: IFFC at 30.5\% as the cheap JSON channel; gated stop-repeat and OODA-card-on-stop-repeat as low-overhead harness additions (32.5\% and 35.5\%); STATE at 34.0\% with extra context tokens; BoN on IFFC$+$STATE at 36.5\% for about $7\times$ generate wall. For a local laptop agent, a 2.5\pp\ BoN point-estimate gain at $7\times$ wall is a research measurement, not an obvious default. We did not apply BoN to collapsed or below-IFFC SFT checkpoints: majority vote cannot be assumed to rescue a policy that abstains or drifts.

\paragraph{Why SFT failed, then plateaued.}
A supported hypothesis is that the first SFT mixes taught the model to stop after tools because ToolACE empty-list targets dominate post-execution assistant turns. Removing those targets restores calling (empty errors ${\approx}0$) but does not install BFCL-style state tracking. Further filters that try to complete turn~0 or drop state-inconsistent continues either over-call (v5) or miss the v4 recovery (v6). STATE, which helps the base model remember executed facts, is null or negative on the v4 checkpoint: the overlay is not a universal substitute for a policy that already mismatches the environment. Preference data that contrasts advance versus loop, rather than another supervised empty-list filter, is the remaining training hypothesis---untested at $N{=}200$ in this draft.

\paragraph{Paper IFFC versus the IFFC paper.}
Large lifts in~\cite{taheri2026iffc} are reported on single-turn Live/Non-Live suites, often where NFC is already weak, and often under dual QA / small-reasoner decoupling. Our Appendix~B-only multi-turn setup sits in a modest-gain band (${+}3.5$\pp point estimate, with an \texttt{-np} confound). That is a different claim, not a refutation of theirs.

\section{Limitations and Roadmap}
\label{sec:roadmap}

All accuracy numbers are from a MacBook Pro M4~Pro (48~GB) with llama.cpp Metal. The registered working title still says ``edge devices'' (local branding); body claims are narrowed to that measured consumer-Apple-Silicon setting. Peak RSS for Gemma multi-turn is about 15~GB, well above an 8~GB Jetson Orin Nano Super budget. Jetson deployment is unmeasured; this paper does not claim that current accuracies run on 8~GB hardware. RAG appeared in an earlier title framing and is \emph{out of scope} for this work---not evaluated, and not deferred as a near-term claim before December 2026. Multi-turn coverage is Gemma-centric, plus an xLAM channel contrast. Parallel AST categories remain artifactual zeros. Method knobs (STATE fields, $\mathrm{MIN}{=}6$, OODA card, SFT filters) were selected against the same \texttt{multi\_turn\_base} $N{=}200$ slice used for ranking; confirmatory re-score on \texttt{miss\_func}, \texttt{miss\_param}, \texttt{long\_context}, or an untouched split is deferred. Health-gate probes are not BFCL percentages.

The following items are explicitly \emph{open}: no conclusion is claimed yet. No invented accuracies are implied.

\section{Conclusion}
\label{sec:conclusion}

Quantized SLMs on a MacBook Pro M4~Pro with llama.cpp already achieve strong single-turn tool selection in the Qwen 3--4B family (weighted non-parallel AST up to 82.53\%), while FunctionGemma delivers interactive latency at 270M parameters. A separate type-coercion diagnostic is consistent with Llama \texttt{multiple} gaps being partly serialization, but that diagnostic is not a recovery of Table~\ref{tab:single-turn}.

For consecutive tool calling on Gemma-4-E2B-it, the story is narrower. Changing the output channel (IFFC) and adding cheap harness memory or guardrails moves the \texttt{multi\_turn\_base} point estimate from 27.0\% into the low-to-mid 30s, with an \texttt{-np} confound on the native baseline and with non-significant McNemar tests on thin adjacent pairs. Majority vote on IFFC$+$STATE reaches 36.5\% at roughly $7\times$ generate wall. Constrained decoding and a live name automaton hurt. Supervised IFFC fine-tuning is easy to get spectacularly wrong (0.5\%) and, even after repairing empty-list targets, stalls at 15.0\%---below the untuned model. Residual failures are environment-state mismatches, especially on VehicleControl and filesystem backends, not unparsable JSON.

Preference optimization is the open training question: a DPO smoke is healthy, a full train is in flight as of 2026-09-29, and this paper stops short of a BFCL conclusion. Completing that train, optional NFC@\texttt{-np 4}, other models' multi-turn baselines, dual-model IFFC, and parallel re-runs after the GBNF fix will determine how far local / on-device SLM serving of this size can be pushed on the measured Mac stack before December 2026. Jetson 8~GB deployment remains unmeasured. RAG is out of scope.

\section{Method caveats}
\label{app:caveats}

These distinctions are part of the method identity:

\begin{itemize}
  \item Constrained decoding is a two-pass TagDispatch-style approximation on stock llama-server, not full XGrammar-2.
  \item GST is a prompt overlay on NFC. It is not GBNF and not IFFC. The checker ignores GST drafts.
  \item STATE is a harness-written snapshot from executed tool results, not LLM summarization.
  \item Best-of-N is majority vote at $N{=}5$ \emph{on IFFC$+$STATE}, not a learned verifier; generate wall is about $7\times$ (${\sim}3.0$~h$\to{\sim}21.3$~h).
  \item Strip-empty (2.0\%) is serve-time history bookkeeping on the SFT-v2 GGUF, not a training method.
  \item SFT-v4 (15.0\%) is a recovery from 0.5\% collapse, not a win over IFFC or NFC.
  \item STATE on SFT-v4 (13.0\%) is a null/negative overlay: STATE helps base Gemma, not that checkpoint.
  \item xLAM 0\% / 3\% are this harness's native versus JSON channels, not published overall BFCL ${\sim}78.94\%$.
  \item PTC-A (13.5\%) is execution accuracy on this harness, not Yu et al.'s reported F1~\cite{yu2026ptc}. Token-level forced-name versus loop diagnosis is not fully audited.
  \item The DPO 10-ID result is a health-gate pass, not a BFCL percentage. Full train in flight as of 2026-09-29; no $N{=}200$ Acc yet.
  \item RAG appeared in an earlier registered-title framing and is out of scope for this paper---not evaluated, not deferred.
  \item Title ``edge devices'' is registered/local branding; measured accuracies are MacBook Pro M4~Pro (48~GB) / llama.cpp Metal. Jetson 8~GB is unmeasured.
\end{itemize}
