\begin{abstract}
Assistants that \emph{act} do so by emitting \emph{tool calls} that a surrounding program, the \emph{harness}, executes. Running that loop locally with a small language model keeps data private and costs nothing per request, but small models fail when a task needs several dependent calls. We study why on the multi-turn base split of the Berkeley Function Calling Leaderboard (BFCL v4; 200 tasks graded by the final state of a simulated backend), using Gemma-4-E2B-it served on a MacBook Pro. The failure is \emph{state}, not \emph{syntax}. The model scores 83.1\% on single-call selection yet completes only 27.0\% of multi-turn tasks through the native tool API, and forcing syntactically valid output makes it worse (10.5\% and 13.5\%). Optimizing the harness helps with no weight updates: JSON-in-text calls reach 30.5\%, a three-part minimal recipe 35.5\%, and the full stack---JSON text, a harness-written state summary, a gated stop-on-repeat rule and a four-line status card---77/200 (38.5\%; +8.0 points, McNemar $p=0.023$ uncorrected; not significant after Holm correction), on par with a five-sample majority vote (36.5\%) at about a seventh of its generation time. Training did not reach that level: the best supervised fine-tune scored 15.0\% ($p<0.001$ below JSON text) and preference tuning 26.5\%. A null test clears the training pipeline; the data mix remains the open suspect.
\end{abstract}

\section{Introduction}
\label{sec:intro}

A useful assistant has to act, not only chat. To check a calendar or lock a car, a language model emits a \emph{tool call}: a machine-readable request (a function name plus arguments) that a surrounding program---the \emph{harness}---runs against a \emph{backend}, here a simulated vehicle or filesystem, and whose result is fed back to the model (Figure~\ref{fig:vignette}). Real tasks need several dependent calls in a row (\emph{multi-turn} tool calling): look up a value, use it, check the outcome, and know when to stop.

Running this loop locally with a \emph{small language model} (SLM) keeps private data on the device, works offline, and has no per-request cost. The catch is accuracy. We measure Gemma-4-E2B-it~\cite{gemma4e2b}, a two-billion-effective-parameter model, on BFCL v4~\cite{patil2024bfcl}, served with llama.cpp~\cite{llamacpp} on a MacBook Pro. Out of the box, through the native tool interface, it completes 27.0\% of 200 multi-turn tasks.

We treat this as a \emph{harness optimization} problem. The model weights stay fixed; what we change is the loop around the model: how calls are parsed, what state the harness records and shows back, when the harness stops a turn, and how the next step is framed. Two of these levers (the state summary and the status card) still reach the model as text in its context, so this is not ``prompt-free'': it is control computed by the harness from executed results, delivered partly through the context. We contrast it with two other families of fixes: forcing the model's output to be syntactically valid, and changing the weights by fine-tuning. Our contributions:

\begin{enumerate}
  \item \textbf{A within-model failure anatomy: state, not syntax.} The same model, quantization and server score 83.1\% on single-call selection and 27.0\% on multi-turn tasks. Once calls parse, failures are tools that never ran and worlds that end in the wrong state, not malformed output; decoders that \emph{guarantee} valid output drop accuracy to 10.5\% and 13.5\% (Section~\ref{sec:fail}).
  \item \textbf{A training-free harness ladder, with paired statistics, that is also the cheap option.} JSON-in-text 30.5\% $\rightarrow$ minimal recipe 35.5\% $\rightarrow$ full stack 38.5\% (77/200), +8.0\pp over JSON text, greedy throughout, and on par with five-sample majority voting (36.5\%) at about $1/7$ of the generation time. The status card works as an act-versus-abstain control rather than a state-tracking aid (Section~\ref{sec:helps}).
  \item \textbf{A controlled negative result on fine-tuning a 2B tool caller.} No trained model beat the untuned model: best supervised fine-tune 15.0\% ($p<0.001$ below JSON text, surviving correction), preference tuning 26.5\% (within noise). Models trained on a rebuilt mix collapse on a 20-task gate, while a null test stays near the bar, which clears the training pipeline and points to the data (Section~\ref{sec:train}).
\end{enumerate}

\section{Background and Related Work}
\label{sec:related}

\paragraph{Benchmark.} The Berkeley Function Calling Leaderboard (BFCL) evaluates language models as API callers~\cite{patil2023gorilla,patil2024bfcl}. Its single-turn categories check one emitted call against a reference with an abstract-syntax-tree (AST) matcher. A \emph{turn} is one user request and everything the model does before handing control back. Its multi-turn categories run the model in an agent loop against simulated backends (for example VehicleControl and GorillaFileSystem, a sandboxed Unix-like filesystem) and compare the backends' final state to a reference. We use the \emph{multi-turn base} split (200 tasks, all tools available). Accuracy is the fraction of the 200 tasks whose final state matches; it is not the public overall BFCL score.

\paragraph{Output channel.} With \emph{native function calling} (NFC), the server receives a tool list and the model returns structured \texttt{tool\_calls}, as in most production APIs. With \emph{instruction-followed function calling} (IFFC), the model is asked in the prompt to write its calls as a JSON list in ordinary text, which the harness parses. Taheri et al.\ report that small models follow such JSON instructions more reliably than native tool APIs on single-turn BFCL~\cite{taheri2026iffc}; we use their single-model variant.

\paragraph{Constrained decoding.} Grammar-constrained generation restricts the next token so that output is always valid, for example to a JSON schema or a list of tool names~\cite{willard2023outlines,dong2026xgrammar2}; Yu et al.\ constrain tool names with a prefix-tree automaton~\cite{yu2026ptc}. Format restrictions can also reduce answer quality~\cite{tam2024format}.

\paragraph{Harness-side control and test-time compute.} Context-compression methods summarize long histories~\cite{kang2025acon}; our state summary is instead written by the harness from executed results. Typed observe--orient--decide--act (OODA) controllers structure agent steps~\cite{guo2026ooda}; our status card borrows only the name. Guided templates add a reasoning scaffold before calls~\cite{he2025gst}. Sampling several answers and voting is a standard way to buy accuracy with compute~\cite{snell2024testtime}.

\paragraph{Training for tool use.} Specialist small callers such as xLAM~\cite{zhang2024xlam} and Hammer~\cite{ye2025hammer} are trained on synthetic tool data such as ToolACE~\cite{liu2024toolace} and APIGen~\cite{liu2024apigen}. \emph{Supervised fine-tuning} (SFT) trains the model to reproduce target responses; we use low-rank adapters (LoRA)~\cite{hu2021lora} with MLX~\cite{mlx}. \emph{Direct Preference Optimization} (DPO) trains on pairs of preferred and rejected responses~\cite{rafailov2023dpo,jung2025diatool}.

\section{Setup and Methods}
\label{sec:setup}

\paragraph{Model and serving.} All results use Gemma-4-E2B-it, quantized with Q4\_K\_M (a 4-bit weight format of llama.cpp), served by \texttt{llama-server} (llama.cpp build 8111) with Metal acceleration on a MacBook Pro (Apple M4~Pro, 48~GB). Decoding is greedy (temperature 0) except for majority voting. Most runs used four parallel server slots and a 65{,}536-token context; the native-API baseline used eight slots, a difference we return to in Section~\ref{sec:discussion}.

\paragraph{Harness interventions.} All leave the weights untouched and use the same checker (Appendix~\ref{app:method} gives exact rules and examples):
\begin{itemize}\setlength{\itemsep}{1pt}
  \item \textbf{JSON in text (IFFC)} instead of the native tool API (NFC); the harness parses the calls.
  \item \textbf{State summary (scratchpad).} After each executed call, the harness writes a short \texttt{[STATE]} snapshot of facts from real results (current directory, known files, last calls) into the conversation.
  \item \textbf{Stop on repeats.} The harness ends a turn when the model re-proposes calls it has already executed, but only after at least six tool steps in the current request. An \emph{ungated} variant stops at the first repeat.
  \item \textbf{Status card.} A four-line card (goal, known facts, last call and outcome, and an advisory next move: call, ask, finish or refuse) is prefixed to the latest user message. The harness fills it deterministically from the conversation and executed results; it never sees reference answers. JSON text + stop on repeats + card is our \emph{minimal recipe}.
  \item \textbf{Full stack (headline).} JSON text + state summary + stop on repeats + status card. Greedy; no sampling.
  \item \textbf{Vote of five (Best-of-N, BoN).} At each step, sample five candidate calls at temperature 0.7, execute the most common one; on top of the state summary. This is the compute-heavy comparison point.
  \item \textbf{Forced-valid decoding.} \emph{Constrained decoding} restricts output in two passes (tool names, then arguments by schema); a \emph{tool-name automaton} constrains only the name, inspired by~\cite{yu2026ptc}.
\end{itemize}

\paragraph{Training.} We train LoRA adapters on Gemma-4-E2B-it with MLX, merge, quantize to Q4\_K\_M and evaluate with JSON text. Early mixes combine ToolACE dialogues with sampled xLAM data; a later \emph{rebuilt mix} (30{,}000 rows) combines about 45\% newly simulated, execution-checked episodes with cleaned public data. We also train one DPO model. Because a 200-task run takes about three hours, trained models first face a fixed 20-task \emph{gate} drawn from the same split (bar: 17/20, the untuned model with the card); a smaller 10-task regression check is described in Appendix~\ref{app:train}.

\paragraph{Error labels.} Each failed task gets one primary label from the checker's message: \emph{empty turn} (no call on a turn that needed one), \emph{under-call} (a required tool never ran), or \emph{state mismatch} (tools ran but the backend's final state differs from the reference).

\paragraph{Statistics.} We report Wilson 95\% intervals, which stay accurate for small counts. For paired comparisons on the same 200 tasks we use exact two-sided McNemar tests, which count only the tasks where two conditions disagree, from per-task results in our evaluation database. We ran eight planned tests; $p$-values are uncorrected, and we note where a Holm correction for eight tests changes the conclusion.

\section{Where Small Models Fail}
\label{sec:fail}

\paragraph{One call is easy; a chain is not.} On single-call BFCL categories (simple, multiple, irrelevance, Java and JavaScript; 990 cases), Gemma-4-E2B-it through the native API scores 823/990 (83.1\%, interval 80.7--85.3\%; Appendix~\ref{app:st}). On multi-turn tasks, the \emph{same model, quantization and server} completes only 54 of 200 (27.0\%). The gap is between choosing one call and carrying a chain of calls through a changing state.

\paragraph{After calls parse, errors are about the world.} Figure~\ref{fig:fail} breaks down failed tasks. With JSON text, the two biggest buckets are state mismatches (60) and under-calls (38): tools that should have run never did, and the ones that ran left the world wrong. The native API fails differently: its main non-state error is empty turns (59), and under-calls are its smallest bucket (19). For every JSON-text condition in Figure~\ref{fig:fail}, state mismatch is the largest bucket (53--109 tasks); with the state summary, 22 of its 64 state mismatches are in VehicleControl and 21 in the filesystem. The full stack has 20 empty turns, 35 under-calls and 68 state mismatches.

\paragraph{Forcing valid syntax hurts.} If failures were mostly malformed output, guaranteeing valid output should help. It does the opposite. Two-pass constrained decoding scores 21/200 (10.5\%; interval 7.0--15.5\%), 20.0\pp below JSON text, with 70 under-calls and 95 state mismatches. The tool-name automaton scores 27/200 (13.5\%; 9.4--18.9\%), with state mismatch rising to 102. Our two-pass decoder approximates, rather than reproduces, full grammar engines~\cite{dong2026xgrammar2}, but the effect is large and in the wrong direction: a valid call is not a correct next step.

\paragraph{JSON text over the native API (+3.5\pp).} Writing calls as JSON text scores 61/200 versus 54/200 natively; paired, it solves 22 tasks the native run misses and loses 15 ($p=0.32$, not significant). Part of the gap may come from serving (eight slots versus four), and a guided template on the native API ties it (Section~\ref{sec:discussion}). We use JSON text as the base for the harness ladder because it is what the harness can parse and inspect most easily, not because the channel switch alone is established.

\paragraph{State summary (+3.5\pp).} The harness-written snapshot scores 68/200; versus JSON text it gains 20 tasks and loses 13 ($p=0.30$). Empty turns fall (41 to 31) while state mismatches do not (60 to 64), so the summary mainly keeps the model calling.

\paragraph{Stop on repeats and the status card (minimal recipe, 35.5\%).} Stopping on a repeated call after six tool steps scores 65/200 (+11/$-7$ versus JSON text, $p=0.48$). Stopping at the \emph{first} repeat instead scores 54/200: all 37 forced stops were on tasks that failed, so the gate matters. Adding the status card scores 71/200, +5.0\pp over JSON text (+26/$-16$, $p=0.16$). The card is best read as an act-versus-abstain control: empty turns fall from 38 to 17, while state mismatches rise from 60 to 71. It helps the model act, not track state.

\paragraph{Full stack: the best measured result (38.5\%).} Combining all four greedy changes scores 77/200 (38.5\%, interval 32.0--45.4\%) in about 2.9 hours for 200 tasks. Paired against JSON text it gains 30 tasks and loses 14 ($p=0.023$ uncorrected; not significant after Holm). Against the minimal recipe, the state summary alone and the vote of five the differences are within noise (Table~\ref{tab:mcnemar}). This configuration was assembled \emph{after} we had seen earlier results on the same 200 tasks, so its lead is subject to tuning leakage. Its harness code is on draft pull request \#90 (commit \texttt{c894ec6}), run with the same model, quantization and server.

\paragraph{Cost: majority vote (36.5\%).} Voting over five samples on top of the state summary scores 73/200, four tasks fewer than the greedy full stack (+24/$-20$ for the full stack, $p=0.65$). It costs about $7\times$ the generation wall-clock (21.3 hours versus 3.0 for the state summary alone and 2.9 for the full stack, 200 tasks), from a single sampling seed. A greedy harness matches it at a fraction of the time, which matters on a local device.

\paragraph{How sure are we?} Every interval in Table~\ref{tab:ladder} is about $\pm6$--7\pp wide. Among harness conditions, only the full stack versus JSON text ($p=0.023$) and the minimal recipe versus the native API ($p=0.033$) fall below 0.05, and neither survives Holm correction. The ordering among the harness rows is therefore observed, not proven; the +8.0\pp is suggestive, not established. Two contrasts are robust. The best supervised fine-tune solves only 7 tasks that JSON text misses while missing 38 that it solves ($p<0.001$, surviving correction), and the full stack's interval (32.0--45.4\%) does not overlap those of the best fine-tune (10.7--20.6\%) or the forced-valid decoders. Preference tuning (26.5\%) is \emph{not} separable from JSON text.

\section{Why Fine-Tuning Did Not Help}
\label{sec:train}

Fine-tuning is the obvious way to teach a small model a task. Here no trained model beat the untuned model. We treat the runs as evidence about \emph{what} goes wrong; the full version history is in Appendix~\ref{app:train}.

\paragraph{Public data taught the model to stop; repairs restored calling, not accuracy.} The first mixes scored 1/200 (0.5\%). A \emph{stop target} is a training response that is an empty list (``no further call''). After a tool result, 78.1\% of targets in that data were stop targets (2{,}121 versus 596 continue), all from ToolACE, so the model learned to stop after its first tool result while BFCL needs further calls. Removing those targets and adding recovery examples scored 30/200 (15.0\%), our best fine-tune: empty turns nearly vanished (167 to 2), but failures moved to state mismatch (109) and under-call (59). Adding the state summary to this fine-tune \emph{lowered} it to 26/200, although the summary helps the untuned model. A DPO model scored 53/200 (26.5\%), within noise of JSON text.

\paragraph{A rebuilt mix collapsed; a null test clears the pipeline.} The best-validation checkpoint of the rebuilt mix scored 2/20 on the gate (Figure~\ref{fig:gate}); validation loss did not predict the collapse. It usually made one call and stopped, even when a setup step was needed (looking up a stock symbol, changing directory, logging in), and invented missing values such as an order number. Removing the card scored 1/20, and continued training on test-style tool layouts still scored 2/20. Was the pipeline the problem? A \emph{null test} should change nothing if the machinery is sound: we fine-tuned the untuned model on 156 of its own logged answers through the same template, adapter, merge, quantization and serving steps. It scored 15/20 (interval 53--89\%), within noise of the bar (17/20; 64--95\%), while the rebuilt mix's 2/20 (3--30\%) is far outside it. The collapse came from \emph{what} the mix taught.

\paragraph{A candidate cause that targeted retrains did not confirm.} \emph{Self-distillation}---training on the model's own answers that the checker marked correct---scored 8/20; in 6 of 12 failures the model said an ID or price was missing and stopped instead of calling the tool that would supply it. Compared with the null-test data, look-up-type calls fell from 37.9\% to 19.7\% of calls and stop targets rose from 23.1\% to 33.2\%. Two targeted retrains tested this: capping the stop share scored 14/20, and restoring the look-up share (39.6\%) scored 12/20. Neither passed, so the data are \emph{consistent with}, but do not establish, a shift in the decision mix (stop versus continue, look up versus act) as the cause.

\section{Discussion and Limitations}
\label{sec:discussion}

\paragraph{State, not syntax.} Across conditions, the hard part is deciding the next step given the current state of the world---including whether to keep going---not writing a valid call. Harness levers that support that decision help modestly: a summary of real results, a gated stop, and a card that mostly controls whether the model acts or abstains. Levers that \emph{constrain} the surface form hurt. Training appeared to shift the balance between acting and stopping rather than improve tracking.

\paragraph{The guided-template tie.} A seven-step reasoning template on the native API also scored 61/200, the same as JSON text (19 tasks swap each way; it raised state mismatches to 79). So the +3.5\pp from switching the output channel may owe as much to prompt structure as to the channel, and we do not claim the channel switch alone is a gain ($p=0.32$ in any case). The claim we do make is narrower: on top of JSON text, harness control adds +8.0\pp, and the template result does not test that ladder; whether a guided template adds to, or substitutes for, the harness levers is untested. We did not stack the harness levers on the native API.

\paragraph{What we recommend.} For an on-device agent: JSON-in-text calls, a harness-written state summary, a gated stop rule and a status card. The full stack is the best configuration we measured (38.5\%) and is greedy; if context is tight, the minimal recipe (35.5\%) is a smaller fallback. Both need no training data or GPU time. Before fine-tuning, gate on task-level checks rather than validation loss. Even the best configuration completes fewer than two tasks in five; small models are not yet reliable multi-step agents on this benchmark.

\paragraph{Limitations.}
\begin{itemize}\setlength{\itemsep}{1pt}
  \item \textbf{One model, one split, one device, tuned in place.} All multi-turn results use Gemma-4-E2B-it on the 200-task base split on one laptop. Settings (stop threshold, card fields, mix filters) were tuned and reported on the same tasks. Other models and the harder BFCL splits are untested.
  \item \textbf{Headline selection.} The full stack was assembled after seeing earlier results on the same 200 tasks (tuning leakage), and its only nominally significant gain does not survive multiple-comparison correction. Its code is not yet merged (draft PR \#90).
  \item \textbf{Context-delivered control.} The state summary and status card are injected into the model's context; ``harness optimization'' here includes these harness-written messages, not only parsing and stopping logic.
  \item \textbf{Sample size and decoding.} Intervals are about $\pm7$\pp; greedy decoding with one quantization and one seed; the vote of five uses one sampling seed.
  \item \textbf{Gate design.} The 20 gate tasks were picked post hoc using historical per-task results from the same split, and the bar was set by the configuration it screens against, so the gate is a screening heuristic.
  \item \textbf{Fairness of comparisons.} The native baseline used eight server slots versus four elsewhere; the card and the vote were never run on plain JSON text. Per-task results come from a local evaluation database that is not in the repository.
  \item \textbf{Home-made constrained decoding.} Ours is a two-pass approximation on stock llama-server, so ``forcing valid syntax hurts'' may partly mean ``our approximation hurts''.
  \item \textbf{Training confounds.} Mix variants changed several factors at once, and self-distillation also took about $3\times$ as many updates as the null test.
\end{itemize}

\section{Future Work and Conclusion}
\label{sec:conclusion}

\paragraph{Future work.} First, \emph{confirmatory runs}: re-score the full stack and the JSON baseline on held-out tasks, the harder BFCL multi-turn splits and a second small model, with matched serving. Second, \emph{retrieval-augmented tool selection}: retrieve the few relevant tools (and their documentation or past usage) for each step instead of placing every schema in context~\cite{patil2023gorilla,qin2023toolllm}; shorter, more relevant context could help a small model choose look-ups before actions. Third, \emph{decision-balanced training data}: vary the look-up and stop shares while holding everything else fixed, to test the mix-shift hypothesis directly.

\paragraph{Conclusion.} A small model running locally can pick a single tool well but fails most multi-step tasks: Gemma-4-E2B-it scores 83.1\% on single calls and 27.0\% on multi-turn tasks through the same native interface. Those failures are about state---tools that never ran and worlds that end wrong---not malformed output, and forcing valid output makes them worse. Optimizing the harness reached 38.5\% with no sampling and no training, +8.0 points over JSON-text calls and on par with a five-sample vote at a seventh of the time; the gain is suggestive ($p=0.023$ uncorrected) and was found on the tasks used for tuning. Fine-tuning did not reach that level (15.0\% SFT, 26.5\% DPO), and a null test places the fault in the data rather than the pipeline. For practitioners, the best configuration we measured is also one of the cheapest: four greedy harness changes.

\section{Intervention details}
\label{app:method}

\paragraph{JSON in text (IFFC).} Following Appendix~B of~\cite{taheri2026iffc}, the tool list is omitted from the API request; the system prompt asks for a JSON list of \texttt{\{function\_name, parameters\}} objects in assistant text. Tool results return as user messages. Calls map to the same BFCL function strings as native calling.

\paragraph{State summary (scratchpad).} After each successful tool execution, the harness writes a compact \texttt{[STATE]} block from real results (current directory, known files, last executed calls). The last two turns stay verbatim; older raw outputs are dropped. It is not a model-written summary. Example:
\begin{quote}\footnotesize\ttfamily
[STATE]\\ cwd: /workspace/notes\\ files: todo.txt, log.csv\\ last: cd(folder='notes')->ok
\end{quote}

\paragraph{Stop on repeats.} After a tool result: (1) if the proposed call set equals the previous one, stop; (2) else if every proposed call was already executed in this user request \emph{and} at least six non-empty tool turns have occurred, stop; (3) otherwise execute. The six-step window resets on a new user question. The ungated variant applies rule (2) with no minimum.

\paragraph{Status (OODA) card.} Prefixed to a working copy of the latest user message (the stored transcript is unchanged), stacked on stop-on-repeats. Fields: \texttt{goal} (latest user question, truncated); \texttt{slots} (up to eight key--value facts from executed arguments and results); \texttt{last} (last executed call and outcome); \texttt{next} (advisory: \texttt{refuse} if no tools are available, \texttt{ask} if the last result signals a missing or invalid argument, \texttt{final} if the user's message is a closing ``thanks/done'', otherwise \texttt{call}). The hint does not constrain decoding and the card never reads reference trajectories. It is not the multi-pass OODA-Tool of~\cite{guo2026ooda}. Example:
\begin{quote}\footnotesize\ttfamily
[OODA]\\ goal: lock the doors and start the engine\\ slots: lockStatus=locked\\ last: startEngine()->error: brake pedal must be pressed\\ next: call
\end{quote}

\paragraph{Vote of five.} On the scratchpad configuration, each step samples five completions at temperature 0.7, majority-votes the \texttt{(function\_name, arguments)} tuple, executes the winner once, and continues. It is not a learned verifier.

\paragraph{Constrained decoding.} Two requests per call: the first constrained to an empty list or a list of valid tool names, the second constraining arguments with each tool's JSON schema. No native tool grammar is active. This approximates XGrammar-2's tag-triggered dispatch~\cite{dong2026xgrammar2} on stock llama-server.

\paragraph{Tool-name automaton.} A live finite automaton restricts the tool name to valid names while arguments are free, on JSON text, not stacked on stop-on-repeats. Execution accuracy here is not comparable to the F1 reported by Yu et al.~\cite{yu2026ptc}.

\paragraph{Training.} LoRA adapters~\cite{hu2021lora} on Gemma-4-E2B-it with mlx-lm; best-validation checkpoint fused and quantized to Q4\_K\_M; evaluated with JSON text. The rebuilt mix: 30{,}000 training / 1{,}500 validation rows; 45/40/10/5\% simulated / APIGen / ToolACE / xLAM; 22\% empty-list targets (all after a tool result); 41.2\% of rows with multi-call targets; no evaluation tool names copied into simulations. DPO: $\beta{=}0.2$, LoRA, scored on JSON text.

\subsection{Training history}
\label{app:train}

\paragraph{Version history.} Dropping only mid-dialogue empty targets from the first mix still scored 1/200; deleting trailing empty answers at serving time scored 4/200. After the repaired mix (30/200), two further filtering variants scored 26/200 and 23/200 (Table~\ref{tab:board}); each changed several filters at once, so they are not single-factor ablations. The rebuilt mix's training was stopped early at step 26{,}500 of 32{,}000; the best validation loss (0.030) was at step 22{,}000, and that checkpoint is the one evaluated. Continued training for 2{,}500 steps on test-style tool layouts scored 2/20.

\paragraph{Self-distillation counts.} Look-up-type calls: 67/177 in the null-test data versus 78/395 in the self-distillation data; stop targets: 36/156 versus 146/440. Capping the stop share (22.9\%) left the look-up share low (20.6\%). The look-up-restoring retrain lost 7 tasks the untuned model solves, and empty turns returned (9 of 66 turns). Look-up counts rest on a name-matching heuristic.

\paragraph{Stop targets in the rebuilt mix.} Stop targets were 22\% of all rebuilt-mix rows, all after a tool result. That is a different denominator from the first mix's 78.1\% (the share of targets \emph{after a tool result} that were stops), so the two are not directly comparable. The rebuilt-mix models still under-called, so stop share alone does not explain the collapse.

\paragraph{10-task tripwire.} Before the 20-task gate, trained models faced a disjoint 10-task check. Two fine-tuned checkpoints and the untuned model with the card all scored 3/10, passing the same three tasks, and across 11 strong historical 200-task runs its rank correlation (Spearman) with the 200-task score was 0.118 (approximate 95\% interval $-0.52$ to $0.67$). We therefore used it only as a regression tripwire, never to rank runs.
