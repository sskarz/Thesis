\begin{abstract}
Assistants that \emph{act} emit \emph{tool calls}---a function name plus arguments---that a surrounding program, the \emph{harness}, executes. Running this loop locally with a small language model keeps data private and costs nothing per request, but small models fail when a task needs several dependent calls. We study why with Gemma-4-E2B-it on a MacBook Pro, using the 200 multi-turn base tasks of the Berkeley Function Calling Leaderboard (BFCL v4), which grade each task by the final state of a simulated backend. The failure is \emph{state}, not \emph{syntax}: the model scores 83.1\% on single-call selection but completes only 27.0\% of multi-turn tasks through the native tool API, and two decoders that force syntactically valid calls score lower still (10.5\% and 13.5\%). Changing only the harness helps. With calls written as JSON text the model reaches 30.5\%; adding a harness-written state summary, a stop rule for repeated calls and a four-line status card reaches 77/200 (38.5\%). This gain of 8.0 percentage points is suggestive rather than established (paired $p=0.023$ uncorrected; not significant after correcting for multiple comparisons), and it matches a five-sample majority vote (36.5\%) at about a seventh of the generation time. Fine-tuning did not reach that level (best supervised fine-tune 15.0\%, preference tuning 26.5\%), and a control fine-tune that should change nothing points to the training data, rather than the training pipeline, as the main suspect.
\end{abstract}

\section{Introduction}
\label{sec:intro}

To check a calendar or lock a car, a language model emits a \emph{tool call}: a function name plus arguments. A surrounding program, the \emph{harness}, runs the call against a \emph{backend} (here a simulated vehicle or filesystem) and feeds the result back to the model (Figure~\ref{fig:vignette}). Real tasks chain several dependent calls, which we call \emph{multi-turn} tool calling: look up a value, use it, check the outcome, and know when to stop.

Running this loop locally with a small model keeps private data on the device, works offline and has no per-request cost. The catch is accuracy. We study Gemma-4-E2B-it~\cite{gemma4e2b} (``E2B'': about two billion effective parameters; ``it'': instruction-tuned) on BFCL v4~\cite{patil2024bfcl}, served with the llama.cpp inference engine~\cite{llamacpp} on a MacBook Pro. Through the native tool interface it completes 27.0\% of 200 multi-turn tasks.

Is the model failing to \emph{write} calls or to \emph{choose} them? Section~\ref{sec:fail} shows it is mostly the latter: tasks fail because a needed tool never ran or the backend ended in the wrong state. We therefore treat the problem as \emph{harness optimization}. The weights stay fixed; we change the loop around the model: how calls are parsed, what state the harness records and shows back, when it ends a turn, and how the next step is framed. Two of these levers, a state summary and a status card, reach the model as text in its context, so the harness acts partly through the context; both are computed from executed results. We compare harness control with two other families of fixes: forcing syntactically valid output, and fine-tuning the weights. Our contributions:

\begin{enumerate}
  \item \textbf{A failure anatomy within one model: state, not syntax.} With the same model, quantization and server, single-call accuracy is 83.1\% and multi-turn accuracy 27.0\%. Its failures are mostly under-calls (required tools that never ran) and wrong final states, and decoders that force valid calls lower accuracy to 10.5\% and 13.5\% (Section~\ref{sec:fail}).
  \item \textbf{A training-free harness ladder with paired statistics.} With greedy (deterministic) decoding for every harness configuration, JSON-text calls reach 30.5\%, a three-part minimal recipe 35.5\% and the full stack 38.5\% (77/200). The full stack's gain of 8.0 percentage points (pp) over JSON text is suggestive ($p=0.023$ uncorrected; not significant after correcting for multiple comparisons), and it matches a five-sample majority vote (36.5\%) at about $1/7$ of the generation time (Section~\ref{sec:helps}).
  \item \textbf{A controlled negative result on fine-tuning a 2B tool caller.} The best supervised fine-tune scores 15.0\%, significantly below JSON text even after correction; preference tuning scores 26.5\%. Models trained on a larger rebuilt data mix fail a 20-task screening check (1--2 of 20, against 17 for the untuned model), while a control fine-tune stays close to the untuned model (15 of 20), which points to the data mix rather than the training pipeline (Section~\ref{sec:train}).
\end{enumerate}

\section{Background and Related Work}
\label{sec:related}

\paragraph{Benchmark.} The Berkeley Function Calling Leaderboard (BFCL) evaluates language models as API callers~\cite{patil2023gorilla,patil2024bfcl}. Its single-turn categories check one emitted call against a reference with an abstract-syntax-tree (AST) matcher. Its multi-turn categories run the model in an agent loop against simulated backends (for example VehicleControl and GorillaFileSystem, a sandboxed Unix-like filesystem) and compare the backends' final state with a reference. A \emph{turn} is one user request and everything the model does before handing control back; each multi-turn task has several turns. We use the \emph{multi-turn base} split (200 tasks, all tools available). Accuracy is the fraction of the 200 tasks whose final state matches; it is not the public overall BFCL score.

\paragraph{Output channel.} With \emph{native function calling} (NFC), the server receives a tool list and the model returns structured \texttt{tool\_calls}, as in most production APIs. With \emph{instruction-followed function calling} (IFFC), the prompt asks the model to write its calls as a JSON list in ordinary text, which the harness parses. Taheri et al.\ report that small models follow such JSON instructions more reliably than native tool APIs on single-turn BFCL~\cite{taheri2026iffc}; we use their single-model variant.

\paragraph{Constrained decoding.} Grammar-constrained generation restricts each next token so that output is always valid, for example to a JSON schema or a list of tool names~\cite{willard2023outlines,dong2026xgrammar2}; Yu et al.\ constrain tool names with a token-level automaton~\cite{yu2026ptc}. Format restrictions can also reduce answer quality~\cite{tam2024format}. Section~\ref{sec:fail} tests whether forcing validity helps in a multi-turn loop.

\paragraph{Harness-side control and test-time compute.} Context-compression methods summarize long histories~\cite{kang2025acon}; our state summary is instead written by the harness from executed results. Typed observe--orient--decide--act (OODA) controllers structure agent steps~\cite{guo2026ooda}; our status card borrows only the name. Guided templates add a reasoning scaffold before calls~\cite{he2025gst}. Sampling several answers and voting is a standard way to buy accuracy with compute~\cite{snell2024testtime}; our vote of five is that baseline.

\paragraph{Training for tool use.} Specialist small callers such as xLAM~\cite{zhang2024xlam} and Hammer~\cite{ye2025hammer} are trained on synthetic tool data such as ToolACE~\cite{liu2024toolace} and APIGen~\cite{liu2024apigen}. \emph{Supervised fine-tuning} (SFT) trains the model to reproduce target responses; we use low-rank adapters (LoRA)~\cite{hu2021lora}, small trainable matrices added to frozen weights. \emph{Direct Preference Optimization} (DPO) trains on pairs of preferred and rejected responses~\cite{rafailov2023dpo,jung2025diatool}. Terms used in this paper are collected in a glossary (Appendix~\ref{app:runs}).

\section{Setup and Methods}
\label{sec:setup}

\paragraph{Model and serving.} All results use Gemma-4-E2B-it, quantized with Q4\_K\_M (a 4-bit weight format of llama.cpp), served by \texttt{llama-server} (llama.cpp build 8111) with Metal acceleration on a MacBook Pro (Apple M4~Pro, 48~GB). Decoding is greedy (temperature 0, so outputs are deterministic) except for majority voting. Most runs used four parallel server slots (requests the server processes concurrently) and a 65{,}536-token context; the native-API baseline used eight slots, a serving difference that could affect its results.

\paragraph{Harness interventions.} All leave the weights untouched and use the same checker (Appendix~\ref{app:method} gives exact rules and examples). By design, the state summary targets lost state, the stop rule targets runaway repetition, and the status card targets the choice between acting and abstaining.
\begin{itemize}\setlength{\itemsep}{1pt}
  \item \textbf{JSON text (IFFC)} instead of the native tool API (NFC); the harness parses the calls.
  \item \textbf{State summary.} After each executed call, the harness writes a short \texttt{[STATE]} snapshot of facts from real results (current directory, known files, last calls) into the conversation.
  \item \textbf{Stop on repeats.} The harness ends the current turn when the model repeats its previous set of calls, or when it re-proposes calls already executed in this turn after at least six tool steps. An \emph{ungated} variant drops the six-step minimum.
  \item \textbf{Status card.} A four-line card (goal, known facts, last call and outcome, and an advisory next move: call, ask, final or refuse) is prefixed to the latest user message. The harness fills it deterministically from the conversation and executed results; it never sees reference answers. JSON text + stop on repeats + card is our \emph{minimal recipe}.
  \item \textbf{Full stack (headline).} JSON text + state summary + stop on repeats + status card, greedy.
  \item \textbf{Vote of five.} On top of the state summary, at each step the harness samples five candidate calls at temperature 0.7 and executes the most common one. This is the compute-heavy comparison point.
  \item \textbf{Forced-valid decoding.} \emph{Constrained decoding} restricts output in two passes (tool names, then arguments by schema); a \emph{tool-name automaton} constrains only the name, inspired by~\cite{yu2026ptc}.
\end{itemize}

\paragraph{Training.} We train LoRA adapters on Gemma-4-E2B-it with MLX~\cite{mlx}, Apple's machine-learning framework, merge them into the weights, quantize to Q4\_K\_M and evaluate with JSON text. Early mixes combine ToolACE dialogues with sampled xLAM data; a later \emph{rebuilt mix} (30{,}000 rows) combines about 45\% newly simulated, execution-checked episodes with cleaned public data. We also train one DPO model. Because full 200-task runs are slow, trained models first face a fixed 20-task \emph{gate} drawn from the same split and run with the status card; the bar is 17/20, the untuned model's score with the card. A smaller 10-task regression check is described in Appendix~\ref{app:train}.

\paragraph{Error labels.} Each failed task gets one primary label from the checker's message: \emph{empty turn} (no call on a turn that needed one), \emph{under-call} (a required tool never ran), or \emph{state mismatch} (tools ran but the backend's final state differs from the reference). Output the harness cannot parse counts as no call, so a parse failure can only appear as an empty turn.

\paragraph{Statistics.} We report Wilson 95\% intervals~\cite{wilson1927}, which stay accurate for small counts. For paired comparisons on the same 200 tasks we use exact two-sided McNemar tests~\cite{mcnemar1947}, which use only the tasks on which two conditions disagree. Eight comparisons form the family for multiple-comparison correction; four of them involve the full stack, so the family was fixed after that configuration was built. We report uncorrected $p$-values and note where correcting for the eight comparisons (Holm's method~\cite{holm1979}, which keeps the chance of any false positive among them at 5\%) changes the conclusion.

\section{Where Small Models Fail}
\label{sec:fail}

\paragraph{One call is easy; a chain is not.} On single-call BFCL categories (simple, multiple, irrelevance, Java and JavaScript; 990 cases), Gemma-4-E2B-it through the native API scores 823/990 (83.1\%, interval 80.7--85.3\%; Table~\ref{tab:board}). On multi-turn tasks, the \emph{same model, quantization and server} completes only 54 of 200 (27.0\%). The two settings differ in grading as well as length, but the gap is consistent with carrying a chain of calls through a changing state, rather than choosing one call, being the bottleneck.

\paragraph{Most failures are about the world.} Figure~\ref{fig:fail} breaks down the failed tasks (full counts in Table~\ref{tab:failfull}). For every JSON-text condition, state mismatch is the largest bucket (53--109 tasks). With plain JSON text it is followed by empty turns (41) and under-calls (38); the native API has more empty turns (59) and far fewer under-calls (19). Harness control mainly removes empty turns: the full stack has 20, against 41 for JSON text, while its state mismatches stay at 68. Because parse failures can only appear as empty turns, most of what remains is not a formatting problem.

\paragraph{Forcing valid syntax hurts.} If failures were mostly malformed output, guaranteeing valid output should help. It does the opposite. Two-pass constrained decoding scores 21/200 (10.5\%; interval 7.0--15.5\%), 20.0\pp below JSON text, with 70 under-calls and 95 state mismatches. The tool-name automaton scores 27/200 (13.5\%; 9.4--18.9\%), with state mismatch rising to 102. Our two-pass decoder approximates, rather than reproduces, full grammar engines~\cite{dong2026xgrammar2}, but the effect is large and in the wrong direction: a valid call is not a correct next step.

\section{What Helps: Harness-Side Control}
\label{sec:helps}

If the bottleneck is choosing the next step, the harness, which sees every executed result, is a natural place to intervene. Figure~\ref{fig:ladder} shows the results. Every change is greedy except the vote of five, and none touches the weights; exact counts and intervals for every condition are in Table~\ref{tab:board} (Appendix~\ref{app:runs}).

\begin{figure}[!htbp]
\centering
\includegraphics[width=0.9\textwidth]{ladder_n200.pdf}
\caption{Multi-turn accuracy on 200 BFCL v4 tasks, Gemma-4-E2B-it. Bars: share of tasks fully correct; error bars: Wilson 95\% intervals. Dark green: harness control on JSON text (the headline full stack is outlined and in bold); light green: majority vote, the compute-heavy comparison; grey: output format alone; red: forced-valid decoders; orange: training. Dotted line: JSON-text baseline (30.5\%).}
\label{fig:ladder}

\paragraph{JSON text over the native API (+3.5\pp).} Writing calls as JSON text scores 61/200 against 54/200 natively ($p=0.32$, not significant). Part of the gap may come from serving, and a guided template on the native API ties JSON text (Section~\ref{sec:discussion}), so we do not claim the channel switch alone as a gain. We build the harness ladder on JSON text because the harness can parse and inspect it directly.

\paragraph{State summary (+3.5\pp).} The harness-written snapshot scores 68/200 ($p=0.30$ against JSON text). Empty turns fall from 41 to 31 while state mismatches do not (60 to 64), suggesting that the summary mainly keeps the model calling.

\paragraph{Stop on repeats and the status card (minimal recipe, 35.5\%).} The gated stop rule scores 65/200 (+2.0\pp, $p=0.48$). Stopping at the \emph{first} repeat instead scores 54/200, 11 tasks below the gated rule, and all 37 forced stops fell on tasks that failed. Adding the status card gives the minimal recipe, 71/200 (+5.0\pp over JSON text, $p=0.16$). Relative to stop on repeats alone, empty turns fall from 38 to 17 while state mismatches rise from 60 to 71, so the error labels suggest the card acts mainly as an act-versus-abstain control.

\paragraph{Full stack: the best measured result (38.5\%).} Combining all four greedy changes scores 77/200 (38.5\%, interval 32.0--45.4\%). Paired against JSON text, it solves 30 tasks that JSON text misses and misses 14 that JSON text solves ($p=0.023$ uncorrected; not significant after correction). Against the minimal recipe, the state summary alone and the vote of five, the differences are within noise (Table~\ref{tab:mcnemar}). The configuration was assembled after we had seen earlier results on these tasks, so its lead is subject to tuning leakage (Section~\ref{sec:discussion}). Its harness code is in pull request \#90 (run at commit \texttt{c894ec6}, merged as \texttt{9aef7d7}).

\paragraph{Cost: majority vote (36.5\%).} Voting over five samples on top of the state summary scores 73/200, four tasks fewer than the full stack, which solves 24 tasks the vote misses and misses 20 it solves ($p=0.65$). The vote takes about $7\times$ as long to generate as the greedy full stack, from a single sampling seed. A greedy harness matches it at a fraction of the time, which matters on a local device.

\paragraph{How sure are we?} Intervals for the harness rows are about $\pm6$--7\pp wide (Table~\ref{tab:board}). Among harness conditions, only the full stack versus JSON text ($p=0.023$) and the minimal recipe versus the native API ($p=0.033$) fall below 0.05, and neither survives correction for multiple comparisons. The ordering among the harness rows is therefore tentative, and the +8.0\pp gain is suggestive. Two contrasts are robust. The best supervised fine-tune solves only 7 tasks that JSON text misses while missing 38 that it solves ($p<0.001$, surviving correction), and the full stack's interval (32.0--45.4\%) does not overlap those of the best fine-tune (10.7--20.6\%) or the forced-valid decoders. Preference tuning (26.5\%) is \emph{not} separable from JSON text.

\section{Fine-Tuning Did Not Help}
\label{sec:train}

Fine-tuning is the standard way to adapt a small model to a task. Here no trained model beat the untuned model: the best supervised fine-tune scored 15.0\%, significantly below JSON text, and the DPO model 26.5\%, within noise of it. We treat the runs as evidence about \emph{what} goes wrong; the version history is in Appendix~\ref{app:train}.

\paragraph{Public data taught the model to stop.} The first mixes scored 1/200 (0.5\%). A \emph{stop target} is a training response that is an empty list (``no further call''). After a tool result, 78.1\% of targets in that data were stop targets (2{,}121 versus 596 continue), all from ToolACE, so the model learned to stop after its first tool result while BFCL needs further calls. Removing those targets and adding recovery examples scored 30/200 (15.0\%), our best fine-tune: empty turns nearly vanished (167 to 2), but failures moved to state mismatch (109) and under-call (59). Adding the state summary to this fine-tune lowered it to 26/200, although the summary helps the untuned model.

\paragraph{A rebuilt mix collapsed.} The best-validation checkpoint of the rebuilt mix scored 2/20 on the gate (Figure~\ref{fig:gate}); validation loss did not predict the collapse. The collapsed model usually made one call and stopped, even when a setup step was needed (looking up a stock symbol, changing directory, logging in), and invented missing values such as an order number. Without the card it scored 1/20, and continued training on test-style tool layouts still scored 2/20. To test the pipeline, we ran a \emph{null test}, a fine-tune that should change nothing if the machinery is sound: the untuned model trained for one pass (39 updates) on 156 of its own logged answers through the same template, adapter, merge, quantization and serving steps. It scored 15/20 (interval 53--89\%), within noise of the bar (17/20; 64--95\%), while the rebuilt mix's 2/20 (3--30\%) is far outside it. The null test rules out those pipeline steps as the cause at small update budgets. The rebuilt mix differs from it in both content and training length (22{,}000 steps for the evaluated checkpoint), so its data are the leading suspect but not the only one.

\paragraph{A candidate cause that targeted retrains did not confirm.} \emph{Self-distillation}---training on the model's own answers to simulated tasks, keeping only turns the task checker marked correct---scored 8/20; in 6 of 12 failures the model said an ID or price was missing and stopped instead of calling the tool that would supply it. Compared with the null-test data, look-up-type calls fell from 37.9\% to 19.7\% of calls and stop targets rose from 23.1\% to 33.2\%. Two targeted retrains tested this: capping the stop share scored 14/20, and restoring the look-up share (39.6\%) scored 12/20. Neither passed, so the data are \emph{consistent with}, but do not establish, a shift in the decision mix (stop versus continue, look up versus act) as the cause. Leak checks found no evaluation task IDs or tool names in the null-test or self-distillation data.

\section{Discussion and Limitations}
\label{sec:discussion}

\paragraph{State, not syntax.} Across conditions, the hard part is choosing the next step from the current state of the world, including whether to stop; writing a valid call is the easy part. The levers that help support that decision: a summary of real results, a gated stop, and a card that mainly controls whether the model acts. None of them reduces state mismatches, which remain the largest failure bucket, so the gains come from acting at the right moments, and tracking state itself remains unsolved. Levers that constrain the surface form hurt, and training appeared to shift the balance between acting and stopping rather than improve tracking.

\paragraph{The guided-template tie.} A seven-step reasoning template on the native API also scored 61/200, tying JSON text (19 tasks swap each way; state mismatches rose to 79). The +3.5\pp channel gap may therefore reflect prompt structure as much as the channel ($p=0.32$ in any case). Our claim is narrower: on top of JSON text, harness control adds +8.0\pp, a suggestive gain (Section~\ref{sec:helps}). We did not test the harness levers on the native API or combined with the template.

\paragraph{What we recommend.} For an on-device agent: JSON-text calls, a harness-written state summary, a gated stop rule and a status card. All four are greedy and need no training data or training compute; the minimal recipe (35.5\%) is a smaller fallback. Before fine-tuning, screen on task-level checks rather than validation loss. Even the best configuration completes fewer than two tasks in five: this 2B model is not yet a reliable multi-step agent on this benchmark.

\paragraph{Limitations.}
\begin{itemize}\setlength{\itemsep}{1pt}
  \item \textbf{One model, one split, one device, tuned in place.} All multi-turn results use Gemma-4-E2B-it on the 200-task base split on one laptop. Settings (stop threshold, card fields, mix filters) were tuned and reported on the same tasks. Other models and the harder BFCL splits are untested.
  \item \textbf{Headline selection.} The full stack was assembled after seeing earlier results on the same 200 tasks (tuning leakage), and the correction family was fixed after that; its only nominally significant gain does not survive correction.
  \item \textbf{Sample size and decoding.} Intervals for the harness rows are about $\pm6$--7\pp; greedy decoding with one quantization and one seed. The vote of five uses one sampling seed, and its cost was measured with four parallel slots.
  \item \textbf{Heuristic error labels.} Each failed task gets one label from string matches on the checker's message, so shifts between labels suggest, but do not prove, a mechanism.
  \item \textbf{Gate design.} The 20 gate tasks were picked post hoc using historical per-task results from the same split, and the bar was set by the configuration it screens against, so the gate is a screening heuristic.
  \item \textbf{Fairness of comparisons.} The native baseline used eight server slots versus four elsewhere; the card and the vote were never run on plain JSON text. Per-task results come from a local evaluation database that is not in the repository.
  \item \textbf{Home-made constrained decoding.} Ours is a two-pass approximation on stock llama-server, so ``forcing valid syntax hurts'' may partly mean ``our approximation hurts''.
  \item \textbf{Training confounds.} Mix variants changed several factors at once; self-distillation took about $3\times$ as many updates as the null test, and the rebuilt mix far more.
\end{itemize}

\section{Future Work and Conclusion}
\label{sec:conclusion}

\paragraph{Future work.} First, \emph{confirmatory runs}: re-score the full stack and the JSON baseline on held-out tasks, the harder BFCL multi-turn splits and a second small model, with matched serving. Second, \emph{retrieval-augmented tool selection}: retrieve the few relevant tools for each step instead of placing every schema in context~\cite{patil2023gorilla,qin2023toolllm}. Third, \emph{decision-balanced training data}: vary the look-up and stop shares with everything else fixed.

\paragraph{Conclusion.} Gemma-4-E2B-it picks a single call well (83.1\%) but completes only 27.0\% of multi-turn tasks through the same native interface; its failures are mostly under-calls and wrong final states, and forcing valid output makes them worse. Four greedy harness changes reached 38.5\%, on par with a five-sample vote at a seventh of the time. The +8.0\pp over JSON text is suggestive ($p=0.023$ uncorrected; not significant after correction) and was found on the tasks used for tuning. Fine-tuning did not reach that level, and a null test points to the training data rather than the pipeline. For practitioners, the best configuration we measured is also far cheaper than voting or training.

\section{Intervention details}
\label{app:method}

\paragraph{JSON text (IFFC).} Following Appendix~B of~\cite{taheri2026iffc}, the tool list is omitted from the API request; the system prompt asks for a JSON list of \texttt{\{function\_name, parameters\}} objects in assistant text. Tool results return as user messages. Calls map to the same BFCL function strings as native calling.

\paragraph{State summary.} After each successful tool execution, the harness writes a compact \texttt{[STATE]} block from real results (current directory, known files, last executed calls). The last two turns stay verbatim; older raw outputs are dropped. It is not a model-written summary. Example:
\begin{quote}\footnotesize\ttfamily
[STATE]\\ cwd: /workspace/notes\\ files: todo.txt, log.csv\\ last: cd(folder='notes')->ok
\end{quote}

\paragraph{Stop on repeats.} After a tool result: (1) if the proposed call set equals the previous one, stop; (2) else if every proposed call was already executed in this user request \emph{and} at least six non-empty tool steps have occurred in it, stop; (3) otherwise execute. The six-step window resets on a new user request. The ungated variant applies rule (2) with no minimum.

\paragraph{Status card (tag \texttt{[OODA]}).} Prefixed to a working copy of the latest user message (the stored transcript is unchanged), stacked on stop on repeats. Fields: \texttt{goal} (latest user question, truncated); \texttt{slots} (up to eight key--value facts from executed arguments and results); \texttt{last} (last executed call and outcome); \texttt{next} (advisory: \texttt{refuse} if no tools are available, \texttt{ask} if the last result signals a missing or invalid argument, \texttt{final} if the user's message is a closing ``thanks/done'', otherwise \texttt{call}). The hint does not constrain decoding and the card never reads reference trajectories. It is not the multi-pass OODA-Tool of~\cite{guo2026ooda}. Example:
\begin{quote}\footnotesize\ttfamily
[OODA]\\ goal: lock the doors and start the engine\\ slots: lockStatus=locked\\ last: startEngine()->error: brake pedal must be pressed\\ next: call
\end{quote}

\paragraph{Full stack.} The state summary, stop on repeats and status card together: the summary is written into the stored transcript after each executed call, and the card is prefixed to a working copy of the latest user message, as above.

\paragraph{Vote of five.} On the state-summary configuration, each step samples five completions at temperature 0.7, majority-votes the \texttt{(function\_name, arguments)} tuple, executes the winner once, and continues. It is not a learned verifier.

\paragraph{Constrained decoding.} Two requests per call: the first constrained to an empty list or a list of valid tool names, the second constraining arguments with each tool's JSON schema. No native tool grammar is active. This approximates XGrammar-2's tag-triggered dispatch~\cite{dong2026xgrammar2} on stock llama-server.

\paragraph{Tool-name automaton.} A live finite automaton restricts the tool name to valid names while arguments are free, on JSON text, not stacked on stop on repeats. Execution accuracy here is not comparable to the F1 reported by Yu et al.~\cite{yu2026ptc}.

\paragraph{Training.} LoRA adapters~\cite{hu2021lora} on Gemma-4-E2B-it with mlx-lm; best-validation checkpoint fused and quantized to Q4\_K\_M; evaluated with JSON text. The rebuilt mix: 30{,}000 training / 1{,}500 validation rows; 45/40/10/5\% simulated / APIGen / ToolACE / xLAM; 22\% empty-list targets (all after a tool result); 41.2\% of rows with multi-call targets; no evaluation tool names copied into simulations. DPO: $\beta{=}0.2$, LoRA, scored on JSON text.

\subsection{Training history}
\label{app:train}

\paragraph{Version history.} Dropping only mid-dialogue empty targets from the first mix still scored 1/200; deleting trailing empty answers at serving time scored 4/200. After the repaired mix (30/200), two further filtering variants scored 23/200 and 26/200 (Table~\ref{tab:board}); each changed several filters at once, so they are not single-factor ablations. The rebuilt mix's training was stopped early at step 26{,}500 of 32{,}000; the best validation loss (0.030) was at step 22{,}000, and that checkpoint is the one evaluated. Continued training for 2{,}500 steps on test-style tool layouts scored 2/20.

\paragraph{Self-distillation counts.} Look-up-type calls: 67/177 in the null-test data versus 78/395 in the self-distillation data; stop targets: 36/156 versus 146/440. Capping the stop share (22.9\%) left the look-up share low (20.6\%). The look-up-restoring retrain lost 7 tasks the untuned model solves, and empty turns returned (9 of 66 turns). Look-up counts rest on a name-matching heuristic.

\paragraph{Stop targets in the rebuilt mix.} Stop targets were 22\% of all rebuilt-mix rows, all after a tool result, a different denominator from the first mix's 78.1\% (the share of targets \emph{after a tool result} that were stops). The rebuilt-mix models still under-called, so stop share alone does not explain the collapse.

\paragraph{10-task tripwire.} Before the 20-task gate, trained models faced a disjoint 10-task check. Two fine-tuned checkpoints and the untuned model with the card all scored 3/10, passing the same three tasks, and across 11 strong historical 200-task runs the tripwire's rank correlation (Spearman) with the 200-task score was 0.118 (approximate 95\% interval $-0.52$ to $0.67$). We therefore used it only as a regression tripwire, never to rank runs.

\paragraph{Glossary.}
\begin{multicols}{2}\scriptsize
\begin{description}[leftmargin=0pt,itemsep=0pt,parsep=0pt,topsep=0pt]
\item[AST] Abstract syntax tree; the single-turn BFCL matcher.
\item[BFCL] Berkeley Function Calling Leaderboard.
\item[BoN] Best-of-N; internal name for the vote of five.
\item[DPO] Direct Preference Optimization.
\item[Full stack] JSON text + state summary + stop on repeats + status card.
\item[Greedy decoding] Always picking the most likely next token (temperature 0); deterministic.
\item[Harness] The program around the model that parses calls, runs tools and records state.
\item[IFFC] Instruction-followed function calling: calls written as JSON in ordinary text; called \emph{JSON text} in this paper.
\item[LoRA] Low-rank adapters: small trainable matrices added to frozen weights.
\item[McNemar test] A paired test using only tasks where two conditions disagree.
\item[Minimal recipe] JSON text + stop on repeats + status card.
\item[NFC] Native function calling: structured \texttt{tool\_calls} via the server's tool API; called \emph{native API} in this paper.
\item[Null test] A training run that should change nothing if the pipeline is sound.
\item[OODA] Observe--orient--decide--act; here only the tag printed on the status card.
\item[pp] Percentage points.
\item[Q4\_K\_M] A 4-bit weight-quantization format of llama.cpp.
\item[Self-distillation] Training the model on its own answers to simulated tasks that a checker marked correct.
\item[SFT] Supervised fine-tuning.
\item[Slot] One request a server processes concurrently with others.
\item[State summary] Harness-written snapshot of facts from executed results.
\item[Status card] Four-line card prefixed to the latest user message.
\item[Stop on repeats] Ends a turn when the model re-proposes executed calls.
\item[Stop target] A training response that is an empty list: no further call.
\item[Tool-name automaton] Decoder constraining only the tool name.
\item[Turn] One user request and everything the model does before handing control back.
\item[Vote of five] Majority vote over five sampled calls per step.
\item[Wilson interval] A confidence interval for a proportion that stays accurate for small counts.
\item[10-task tripwire] Fixed 10-task regression check; does not rank models.
\item[20-task gate] Fixed 20-task screening check (bar 17/20); not a 200-task accuracy.
\end{description}
\end{multicols}
