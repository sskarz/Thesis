Written 2026-11-09, before any judge call. Branch `thesis/distill-data-scale`. Authorization: advisor note of 2026-11-09 carrying `SANS APPROVED (2026-11-09): "Forget the budget thing I'll up it to $50 for max headroom. And yes to all."`: items 1 (this step, cap $0.60), 2 (memory preflight) and 3 (G1 pre-registration, not a launch). Total API cap raised to $50 by the same line; spent so far $2.11 (yield Part 1). The Nov 25 stop is unchanged.

**Why.** The registered accuracy review (A1) of 40 sampled kept tasks failed: Codex marked 7 WRONG, two subagents 3 (all 3 inside Codex's 7); I verified Codex's 7 from the sample text (`docs/reviews/codex_a1_sample_verdicts.md`). The existing checks only show that the gold runs and that the teacher can reproduce its end state. They do not show that the gold does what the user asked.

## 1. What is added (API + CPU only; no GPU, no port 8080)
* `sft/yield_checks.py` (free, deterministic). Drop reasons: `id_collision` (a post_/place_/create_/open_ call returns an id already in the starting state or created earlier in the task, i.e. an object was overwritten or reused); `empty_read_with_state_key` (a read-only call returns an empty list/dict although a numeric argument is a key of a non-empty list in the starting state); `quoted_suffix_not_in_state` (the user says a card "ending in NNNN" and no `card_number` ends with those digits). Information only, not a drop reason: `info_seeded_comments_invisible` (TwitterAPI seeds comments or retweets, which the BFCL backend cannot read back because it converts tweet keys to int but not these; harmless unless the gold reads them).
  * **Deviation, logged:** the first version dropped every task with seeded comments. The first run of the checks on the 99 kept tasks showed it would drop `distill_y_1583`, which Codex and both subagents judged FAITHFUL (it never reads the comments). I changed the rule to information-only before any judge call. This is tuning on the calibration set; the fresh sample (section 4) is the real test.
* `sft/yield_judge.py` (API, capped). One DeepSeek call per task (same pinned model and provider as the rest of the pipeline, temperature 0, `max_tokens` 1800). The judge lists, per user turn, the requested actions, whether the gold covers each, whether every quoted value is grounded in the state, whether the function and arguments match the wording, and whether the results support the request; then FAITHFUL / AMBIGUOUS / WRONG (when unsure between FAITHFUL and AMBIGUOUS it must choose AMBIGUOUS). The prompt names error classes in general terms (missing performed action, reference that matches nothing in the state, function meaning, empty or id-reusing results) and quotes no task text. **Disclosure:** the choice of error classes was informed by the defects found in the 40 reviewed tasks, so the judge is not blind to those categories; calibration on those 40 therefore overstates how it will do on new kinds of defect, and the fresh sample (section 4) is the real test. After Codex review f1 the specific examples (a statistic named in one task, a numeric target from another) were removed from the prompt, and the value rule was split: references to existing objects must match the state, while content or parameters the user supplies (text to post, amounts, new titles, credentials) need no state support but must be reproduced exactly. Same cost guard as the other paid steps (halts on the first cost-less response or on a budget stop; exit 3). Request timeout 60 s with 2 retries, a watchdog at the 30-minute deadline (unfinished tasks become SKIPPED and the process ends with `os._exit`), and the invocation also runs under an external `timeout`. Skipped, unparsed or missing verdicts make the run **incomplete**: they never count as catches in calibration, and `yield_calibrate.py` reports `calibration_pass = false` unless every task has a parsed verdict and the guard flags are clean.
* `sft/yield_calibrate.py`: compares the filter (judge not FAITHFUL, or any non-info deterministic flag) with Codex's labels on the 40 reviewed tasks.

## 2. Registered calibration rule (before any judge call)
The filter is accepted only if, on the 40 reviewed tasks, it drops **at least 6 of the 7** tasks Codex marked WRONG **and at most 5 of the 27** Codex marked FAITHFUL (about 19%; the advisor's limit was "not a third"). Reported in addition: drops among the 6 AMBIGUOUS, judge-only and deterministic-only counts, ids of missed WRONG and of false drops. If the rule fails, nothing scales and the judge prompt may be revised once, with the revision, the reason and the new calibration run logged; a second failure stops the step and goes to the advisor.

## 3. Procedure and estimate
1. Offline: unit tests (`sft/test_yield_judge.py`), then a Codex review of this document and the scripts (major problems only).
2. Deterministic checks on the 99 kept tasks (already run once: 19 flagged before the comments change; recomputed after).
3. **Spend bound (answers Codex f2).** The run is invoked with `--max-cost 0.50`, below the registered $0.60 cap, because the watchdog's `os._exit` can abandon requests that are still in flight and the client counts only completed responses. At most 4 requests can be in flight, each with at most 2 retries; a request costs at most about $0.005 (about 8,000 input and 1,800 output tokens at $0.30 and $1.20 per million) [analysis], so the unreported overshoot is at most 4 x 3 x $0.005 = $0.06 and the true total stays under $0.56, inside the registered $0.60. The OpenRouter usage page is the reconciliation source if the total matters; Sans can check it.
4. One judge run over all 99 kept tasks (it covers the 40 reviewed ones, so calibration and survivor counting are the same run). 99 calls, 4 workers, hard stop 30 minutes, cap **$0.60**.
   * Time estimate [analysis, unmeasured]: 10 to 15 minutes. Cost estimate [analysis]: about $0.15 (about 2,000 input and 700 output tokens per call at $0.30 and $1.20 per million tokens), well under the cap.
5. `yield_calibrate.py` writes the calibration report and the list of survivors after removing the reviewed WRONG ones.

## 4. Fresh sample (the pass test)
The 40 reviewed tasks are spent for calibration. The fresh sample is drawn (seed 9091) from **filter survivors not among the 40 reviewed**, and reviewed under the same rule as A1 (Codex plus subagents; at most 2 WRONG per reviewer; a pass is worded "no evidence of a high error rate"). If fewer than 40 unreviewed survivors exist, the fresh sample is all of them and E0 (at least 40 kept tasks) is judged on survivors plus new authoring: that is G2's job, which stays on hold until the fresh sample passes.

## 5. G1 task list (not a launch)
Per the advisor: 40 tasks from the 99 kept, after removing the 7 WRONG, the ID-collision tasks and anything the free deterministic checks reject; chosen by sha256 of the task id. G1 asks only whether the adapter can learn its own training tasks. Whether the judge also applies to G1 is the advisor's call; this document gives both lists (deterministic-only, and deterministic plus judge).

## 6. Limits stated up front
Single judge run; the judge is a DeepSeek model judging DeepSeek-authored tasks (correlated errors are possible, which is why calibration against Codex's labels is required); the 40 labels come from one Codex run plus two subagent runs and my own reading of the seven WRONG ones; the 27/7 split is small (95% intervals are wide); the calibration set also informed the comments-rule change above.
