## 4. Contamination rules (the most important section)

The test set is the 200 BFCL v4 `multi_turn_base` tasks. Training rows must never come from:
- those 200 tasks, their prompts, their gold calls, or any past model response to them (the repo's own `sft/README.md` says the same);
- the 20-task gate ("mid20", Run 69 bar 17/20) or the fresh 20-task bank used in Run 77;
- the other BFCL multi-turn splits (`miss_func`, `miss_param`, `long_context`), because they are variants of the same base questions.

Required checks before any training:
1. Build an exclusion list: all 200 task IDs plus the user-turn text of every test task.
2. Reject any generated task whose user turns match an excluded task by exact text, or by near-duplicate similarity (pick a threshold, record it, and ask Sans if unsure). Also check tool-call argument values (names, IDs) that look copied.
3. The earlier leak checks looked for evaluation task IDs and tool names in the data. Repeat those and report the counts.
4. State in the data build log that no test task appears in the training data, with the counts that support it.

Teacher running on the 200 tasks as an evaluation (a teacher ceiling for the paper) is allowed only if Sans approves it, and those rows are never used for training.

## 5. What the data should look like (design)

Why: v11 was the most careful public-data mix (30,000 rows: 45% synthetic, 40% APIGen-MT, 10% ToolACE multi-call, 5% xLAM multi-call; 22% stop targets) and had the lowest validation loss yet (0.030). It still scored 2/20 on the gate, against a bar of 17/20. Validation loss did not predict collapse. v11 also trained far longer than the null test (22,000 steps for the evaluated checkpoint versus 39 updates), so content and length are both suspects.

Plan for the new data:
1. Same world as the test: use the BFCL tool backends (the ones `generate_multi_turn.py` already loads through `bfcl_eval`) with NEW tasks. Public datasets use other tools and states, which is where the model fails (state mismatch, under-calling, stopping early).
2. The teacher works each task in the same loop the student will run in: JSON-text calls (IFFC), the harness state summary, real tool execution, and real observations fed back. Rows are the teacher's actual next-step decisions in real states. Strip any teacher reasoning text; the student format has none.
3. Verified rows only. Suggested method: generate a task as user turns plus a gold call sequence, execute it in the backend to get the end state, have the teacher solve it blind, keep episodes whose end state matches. METHODS candidates in the same spirit (all `CANDIDATE`, none run): Turnslide, DiGiT-TC, SAP.
4. If the earlier simulator and checker (the self-distillation episodes, `sft/v13/` on this Mac, possibly in a worktree such as `Thesis-wt-*`) already cover this, reuse them and record what they do. Sans has not yet said which exists. Ask him if you cannot find it.
5. Decision mix report before training: stop-target share and look-up-call share, compared with the null-test data (stop 23.1%, look-up 37.9% of calls) and the earlier self-distillation data (stop 33.2%, look-up 19.7%). Cap stop rows. Report counts per task family (file system, vehicle, travel, trading, and so on).
6. Teacher log for every episode: model name, exact version string, date, token counts, whether it passed verification.

Teacher facts (checked 2026-11-06):

## 6. Stages, with a stop for Sans's approval at each

0. Setup (no spend). Locate the simulator/checker. Build the exclusion list. Write a DeepSeek adapter for the loop (base URL, auth header from the env var, model name, retries, rate limit). 2. Full generation (needs OK with the measured estimate). Generate, verify, run the leak check and the decision-mix report. STOP before any training.
3. Null-scale training (needs OK with a time estimate). Start at the null-test scale, 39 updates, through the full chain: template, LoRA, fuse, GGUF Q4_K_M, serve. Compare the 39-update null test (15/20). Report update counts for every run. Registry key: add a new distinct `api_name` and slug; do not overwrite existing rows.
4. Gate. The candidate is screened on the 20-task gate and the fresh 20-task bank with the status card (same setup as the bar). Pass rule: gate at or above the bar (17/20), no worse than base on the fresh bank, at most one regression versus base passes. Never screen on validation loss. Gate results are tripwires, not accuracies.
5. Larger training only if stage 4 passes, with a new approval. A 200-task run needs Sans's explicit GO.

Fail-fast rule: if stage 4 fails, stop and report. Do not tune on the gate or run variants on your own initiative; the repo already has a long list of mix variants that failed.

Mac build notes (from `sft/README.md`): do not LoRA-train `mlx-community/gemma-4-e2b-it-4bit` with mlx-lm (an mlx-vlm conversion missing text-only PLE weights); convert `google/gemma-4-e2b-it` yourself. Use the fused best-checkpoint, not the last one, and serve with `llama-server -m <local.gguf>`.

## 7. Caveats to keep in mind

- A stronger data source does not guarantee a result. Self-distillation on the model's own checker-approved answers already failed (Runs 74-77: 8, 14 and 12 of 20; the null test scored 15/20 and the bar is 17/20). A negative result with a clear test is still a valid result for the thesis (Chapter 6).
- The teacher's decisions may differ in style from what a 2B model can imitate. Look at examples by hand before scaling.
