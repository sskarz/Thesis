## 1. Question

Rounds 2 to 5 produced adapters that scored below the untuned base on every bank. Two explanations are not separated by any existing experiment:

* **H-update:** a small, narrow update of this kind perturbs a brittle greedy policy and costs passes.
* **H-content:** the specific training content (teacher-selected, reachable-only rows) costs passes.

Neither is "established" by anything below; each arm gives a description of one run (section 4). Adapter placement, capacity, and precision mismatch are not tested here.

* **D1, "R-S0": spectrum-preserving random-direction adapter.** For each LoRA pair in S0, P = A @ B. Keep the singular values of P (to float32 rounding, checked) and replace the singular vectors by random orthonormal ones (fixed seed 6061; factors balanced). The weight update therefore has S0's per-layer norm and spectrum up to float32 rounding, at S0's layers and modules, with random directions and no learned content (`sft/r6_random_adapter.py`; per-pair product norms, factor norms, and the error after an fp16 round trip are written to a report; the build fails if any of these exceeds its registered tolerance: spectrum 1e-4 relative, product norm 1e-5 relative, fp16 matrix error 1e-2 relative; the converted GGUF is then audited against the source adapter: exact tensor set, finite values, and the full per-pair update matrix (alpha/r times lora_b @ lora_a against scale times P transposed) within 1e-2 relative Frobenius error). ## 4. Registered readings (set before any data; descriptive, not causal)

Composite C = passes out of 155. The bands below are deliberately coarse **descriptive bands, not noise intervals**; they use the reference counts above (S0 = 59, mu_B = 67.5) and are exhaustive:

* **A: C <= 55** (below S0-like). **B: 56 to 62** (S0-like). **C: 63 to 64** (ambiguous). **D: 65 to 70** (base-like). **E: 71 to 76** (above base, below the screen). **F: C >= 77 and C > 68** (screen run 1 met).

Per arm, what the single run is *consistent with* (alternatives always remain: update magnitude, update direction, target exposure, Q4-versus-bf16 mismatch, run-to-run movement, and the single seed):

* **R-S0.** B or A, with probe actions changed comparable to S0's: consistent with a perturbation of this size and placement costing passes regardless of learned content. D: consistent with the loss not coming from perturbation size and spectrum alone. C, E, F: reported as observed, no reading.
* **S0 dose (0.5, 0.25).** Compare against S0-1.0c and B3 only. A rise toward band D as the scale falls is consistent with a dose-dependent loss and no better result at the tested scales. Flat in band A or B at every scale: no dose dependence at these scales. Any F is screen run 1 only and triggers the registered restarted repeat before any statement; the chain does not run repeats by itself.
* **S0-self.** B or A: consistent with a loss that does not depend on the teacher-selected content (the base's own replies produce it too). D: consistent with the Round 5 content contributing; a matched control and a second seed would be needed before saying more. C, E, F: reported as observed.
* **Session validity.** The closing base run (B3b in stage 1, B4 in stage 2) and B3 are reported with every result. If either lies outside band D (65 to 70), nothing is discarded or re-run silently: both runs stay in the report, one additional base run is added and all attempts are listed, and the session's readings carry a drift flag. The same applies to S0-1.0c versus Round 5's S0 (59): if S0-1.0c lies outside 56 to 62, the summarizer prints the same follow-up requirement (one additional base run, all attempts listed, drift flag).
* Any pattern not listed above is "inconclusive" by default. Nothing is changed after seeing results; any deviation is logged with its reason.

Limits stated up front: single runs; adapter-to-adapter and seed variance unmeasured; banks are synthetic and F is adaptively informed; in Round 5 two identical base runs over FK exchanged 6 gains and 7 losses (`docs/reviews/codex_r32.md` line 30); this describes those two pairs of runs and is not a repeatability interval; these arms test only the Round 5 recipe on Gemma-4-E2B-it, not another recipe, placement, or data scale.

## 5. Validity, stop rules and budget

* **Server ownership.** The chain starts its own `llama-server` with the Run 69 flags (the flag list is compared with `sft/serve_gguf.sh` at preflight), records its PID, checks that the listener on port 8080 is that PID, and stops only that PID (trap on exit). It never uses `pkill`. If port 8080 is busy at preflight or later, it aborts without touching the other process.
* **Identity checks before every run (structured, from `/props` and `/lora-adapters`, JSON saved):** model path equals the pinned bar GGUF path (sha256 prefix `923c4c86177d2ee1` checked at preflight), `build_info` equals `b10894-d344123fe` exactly, 4 slots, and either no adapter (base) or exactly one adapter with id 0, the canonical expected GGUF path, and the expected scale. F, K2 and git state (no modified tracked files) are checked at preflight and the commit is logged.
* **Invalid-run stops (the chain aborts):** wrong row count, duplicate tasks, any API-error episode, failed identity check, GGUF audit failure, K2 or F hash change, busy port, training process running, cap reached. A flagged FK run must be replaced completely (a new attempt directory); nothing is overwritten.
* **Outcomes never stop the chain** (any band, including F). Conditional work (a restarted repeat after F, extra base runs, replacements, the stage 2 matched control) is budgeted separately and, except for the single extra base run described in section 4, needs Sans's go.
* **Caps, enforced in code:** 2.5 h shared by F and K2 of one FK composite (per-run timeouts are the remaining time), and 16 h for the whole chain across stages (start time persisted in `chain_start_epoch`). Cleanup on INT, TERM or cap expiry kills the current bounded child and all its descendants (TERM, then KILL after 10 s); server start and identity checks also check the remaining budget. Every blocking phase (self-tests, adapter build, conversion, audits, probes, evals, report) runs under the remaining whole-chain budget (`timeout`, TERM then KILL after 30 s) and every HTTP call is limited to the smaller of 10 s and the remaining budget. The bounded job runs in its own process group; cleanup signals the whole group (TERM, then KILL after 10 s), so orphaned descendants are also killed. Stage 2 training will have its own 3.5 h cap.
* **Attempts are preserved:** every launch writes to a new, atomically allocated directory `sft/data/distill/r6/attempts/<timestamp>_<stage>.XXXXXX/` (`mktemp -d`) (chain log, server logs, saved `/props` and `/lora-adapters` JSON, argv, adapter hashes, probes, evals); preflight failures are logged there too.
* **Read-only isolation of R5:** all commands that run from the Round 5 worktree (probe, later provenance) use `python -B` and `PYTHONDONTWRITEBYTECODE=1`; the chain writes only under R6.
* **Order (stage 1):** build the random-direction adapter and audit it (source keys, shapes, dtype, finite values, singular values, fp16 matrix error, and the product norm read back from the converted GGUF); then B3, S0-1.0c, R-S0, S0-0.5, S0-0.25, B3b. Stage 2 (D3) is separate.
* **Estimates.** Sourced: FK about 55 to 60 min per arm and S0 training about 1.5 h (`docs/DISTILLATION_ROUND5_FINDINGS.md`, cost section); 2,832 generations took 3 h 28 min (`docs/DISTILLATION_RUNLOG.md`; not a measure of this workload). [analysis] Stage 1: 6 FK runs = 5 h 30 min to 6 h, plus an **unmeasured allowance (our guess) of about 1 h** for the adapter build and audit, six probes and server restarts. Both stages: 8 FK runs = 7 h 20 min to 8 h, plus training about 1.5 h, plus an **unmeasured allowance of about 2 to 3 h** (adapter construction, probes, restarts, base-reply generation), i.e. roughly 11 to 12.5 h, excluding conditional work.
* **Mandatory post-stage procedure (executable, run by the Thesis bot, not by the chain):** `sft/r6_tools.py summarize` prints each arm's composite and band and the registered follow-up flags (base arm outside 65 to 70; contemporaneous S0 outside 56 to 62; screen run 1 met). The Thesis bot then (1) runs a Codex review of `STAGE_REPORT.json` and the probe report against section 4, (2) tells Sans in chat what ran, the counts, and any follow-up flag, and (3) does not start the next stage until the review has no open BLOCKER. The chain schedules nothing by itself and does not declare completion unless both reports (`probe_report.json`, `STAGE_REPORT.json`) were produced and `summarize` accepted all six arms (exact rows, unique task ids, no API errors); the single extra base run after a base-drift flag is added to the report with all attempts listed.
* The Thesis bot launches the chain as a tracked background job. The handoff names a Claude Code PushNotification tool; this agent has none, so the equivalent is the tracked-job completion notice, followed by a chat message to Sans with the counts, stop reasons and any follow-up flag (Sans does not want Telegram, WhatsApp or iMessage notifications). Nothing else may use port 8080 or the GPU while it runs; the chain checks at start and re-checks before each server start.
