# Data-scale track, step 1: yield and format check (pre-registration, v1)

Written 2026-11-09 before any paid call of this track. Branch `thesis/distill-data-scale` (from `thesis/distill-stage0` at `5187288`), worktree `Thesis-wt-data`. Sans approved on 2026-11-09: a yield check with an API cap of **$5**, run on the Mac while the Round 6 diagnostics (stage 1) are running, with Codex review and an independent subagent review of this check before it runs.

**What this step is.** A measurement of whether the existing teacher pipeline (author tasks, check them by execution, let the teacher solve them, keep what the stock BFCL checker accepts, turn teacher steps into rows) can produce training data at a useful scale, and whether the output is correct and in the format the trainer and the served model need. It trains nothing, evaluates nothing, uses no GPU and no llama-server, and its outputs are **not training data yet** (see section 2). Whether more data helps is a separate question that this step does not answer.

**Hard rules** (`docs/DISTILLATION_HANDOFF_ROUND6.md` section 4, applied unchanged): no invented numbers, scope fixed to Gemma-4-E2B-it / BFCL `multi_turn_base`-style tasks / one Mac, the 200 BFCL tasks, mid20, fresh-20, confirm, dev banks, F and K2 are never training data and F and K2 per-task text is aggregate-only (code may read it for dedupe, nobody reads it), the key comes only from the environment and is never printed or logged, data stays gitignored, commits stay local, no push/PR/merge/upload without Sans's OK, no AI attribution, no edit of `paper/main.tex`. Spend: this step is capped at **$5.00 in total**; every paid stage also has its own `--max-cost`.

## 1. Fixed materials

* Code: `benchmark/` is byte-identical to the Round 6 diagnostics worktree (`diff -rq`, checked in preflight), so the harness prompts in the data are the ones the model is evaluated with (mode `iffc-ooda-card`).
* Teacher: `deepseek/deepseek-v4.1-flash-1017` through OpenRouter, provider pinned to DeepInfra, no fallbacks, reasoning disabled (`benchmark/teacher_api.py`). Every call logs the API-reported model and provider string; acceptance A4 requires exactly one of each.
* Authoring: the stock `benchmark.distill_tasks.author` (prompt, validation, repair loop, strict 8-gram dedupe against every earlier task file, leak check against all BFCL splits, grounding check). The only addition is `sft/yield_author.py`, a wrapper that adds a wall-clock deadline and refuses to continue if the API reports no cost (the stock CLI has neither, and writes its output file only at the very end). Same prompt as Round 5 K2, so rates are comparable.
* Slots: 2,000, seed 7001, task-id prefix `distill_y` (registered choices, not measurements).
* Held-out set (also the provenance set): `r3/dev_all.jsonl` (103), `dev/confirm_bank.jsonl`, `f/tasks_F.jsonl` (81), `k/tasks_K2.jsonl` (74, sha256 `e2ac40e4ece912d07a3646a3b6a787c4dd880bd8a2b7dc1f2a4e966bfc98c8ef`). Same four files as Round 5's provenance check. File hashes are logged at start.
* Strict-dedupe set for authoring: the Round 5 K2 list plus F, K2 and the K2 raw/audited files (full list in `sft/data_yield_chain.sh`).

## 2. What the rows from this step are (and are not)

The rows built here are **JSON-only teacher rows**: the prompt is the exact request the harness sent to the teacher in the student's loop, the target is the teacher's call list re-serialised as strict JSON (`[]` for a stop). They have **no reasoning text**. Round 2 found that training on such rows teaches "answer without thinking" and Round 3 introduced the native format, because the served model answers in a thought channel first (`docs/DISTILLATION_HANDOFF_ROUND6.md` section 6, items 1 and 4). They are therefore the *input* to the native-format conversion (a student-written reasoning plus the same action; `benchmark/distill_rationalize.py`) and not a training set. The conversion needs the local GPU server, so it is part 2, after stage 1 of the diagnostics ends. Which conversion to use for a real training set (student reasoning without a hint, student reasoning with a private note, or teacher reasoning) is an open design decision for Sans, to be made after part 2's numbers; this step does not make it.

## 3. Part 1 (API + CPU, runs now): procedure

`sft/data_yield_chain.sh part1`, from the worktree, each step bounded by a timeout, in its own process group, at low priority (`nice 10`, 2 workers), with a unique attempt directory:

1. Preflight: branch, `timeout(1)` present, a cross-attempt spend ledger (the sum of `cost_usd` over all earlier real attempts plus this attempt's registered caps of $3.65 must stay within $5.00; any earlier cost-less response blocks a re-launch until Sans has reconciled the charges with the provider, so a re-launch after an abort cannot exceed the total), clean tracked tree, F and K2 hashes, key present (presence only), all input files present, disk space, no other authoring process, `benchmark/` identical to the Round 6 worktree.
2. Smoke: 3 slots, cap $0.05. `sft/yield_smoke_check.py` then requires at least one logged call, a positive cost on every call, exactly one API model string equal to the pin, exactly one provider containing DeepInfra, and a finish reason on every call; otherwise the chain aborts before the paid author run. (Authoring a valid task in 3 slots is not required; the valid rate is about 10%.)
3. Author 2,000 slots (cap $3.00; internal deadline 145 min and an external hard stop at 160 min, 4 workers as in the K2 run, whose 5,682 authoring calls for 1,300 slots took 84 minutes by the call timestamps in `sft/data/distill/k/author/calls.jsonl`, so about 130 minutes is expected for 2,000 slots [analysis]; `sft/yield_author.py`). Requests stop at the first API response that carries no cost (`sft/yield_guard.py`), so the dollar cap cannot silently stop working mid-run. A budget stop is latched too (the harness turns a refused request into an ordinary episode error, so the solve's own `stopped_early` would stay empty); both wrappers write `guard_flags.json`, exit 3 on either condition, and the report fails A6 on a latched budget stop and A5 on any cost-less response.
4. Gold audit (`build_bank_f.py audit`: re-run under a fresh id, `cp`/`mv` semantic check).
5. Teacher solve in the student's loop, k = 4 (greedy plus three sampled at T = 0.7), stock checker verdicts (cap $0.60; internal limit 60 min and an external hard stop at 70 min, 4 workers; K2's solve of 540 episodes took 568 s; `sft/yield_solve.py`, the same cost guard). Skipped verdicts (budget or deadline) have no task id; `build_bank_f.py filter` was fixed to ignore them and count them, because the unmodified code raised `KeyError` and would have discarded the whole paid run (Codex d1).
6. Keep checker-verified tasks; drop any whose gold function-name signature, id or user-turn text (difflib ratio at least 0.85) matches a held-out bank. This differs from the K2 filter, which also dropped matches against earlier *training* pools; for training data only held-out matches matter, so the drop rate reported here is the held-out drop rate. The signature rule (identical per-turn function-name sequence) is the coarsest and most expensive filter, and it removes the most common workflow skeletons first because the held-out banks already contain them; the report therefore gives the drop count by kind, and whether to keep this rule at scale is a decision for Sans. (A comparison with the stricter filter can be recomputed from the files.)
7. Rows from the surviving tasks only: every solve episode of a dropped task is quarantined by id, because the row builder otherwise takes all verified episodes in the solve directory. At most 2 verified samples per task, stop rows capped at 25%, task-disjoint 10% validation split, per-row leak scan, failed-action and ungrounded targets dropped (`benchmark/distill_rows.py`, unchanged).
7b. Conflicting prompts: the builder removes only rows identical in prompt *and* target. With k = 4 sampled teacher episodes the same state can get two different actions, which would teach opposite things for one prompt (Round 5 removed such prompts; handoff pitfall 11). `sft/dedupe_conflicts.py` drops **all** rows of every prompt that has more than one distinct target, across train and valid, counts them, and writes `rows_clean/`. The replay on Round 3 artifacts found 9 such rows among 589 before this step existed (the conformance check caught them), which is why the step was added. Everything after this point uses `rows_clean/`.
8. Provenance gate: `sft/check_provenance.py` on the rows against the four held-out banks (same arguments as Round 5), including 8-gram, turn-similarity, signature and BFCL-text checks. A failure is reported, never silently fixed. Tasks the gate names may be quarantined and steps 7 to 9 re-run once, logged as a deviation with the list of removed tasks; a second failure fails the step.
9. `sft/yield_report.py` writes `YIELD_REPORT.json`; `sft/sample_for_review.py` draws 40 kept tasks with seed 9090 for the independent review.

Fail-closed local guard: `sft/yield_solve.py` points the harness's local server URL at a dead port, so a request that bypassed the teacher client could not reach the diagnostics run's llama-server on :8080. Tasks with any API-error episode are quarantined whole (the row builder does not look at `api_error`). The author report is written to its own JSON file, not parsed from mixed output.

Offline validation done before any paid call: `sft/test_yield_report.py` and `sft/test_dedupe_conflicts.py` (synthetic fixtures, each acceptance flag flips on its violation), and a replay of steps 6 to 9 on the Round 3 artifacts (no API; those tasks were authored in the same batch as `dev_all`, so the held-out filter drops 81 of 157 verified tasks there, 80 by signature; the replay checks the code, not the rates).

**Reference points from earlier runs** (copied from `docs/DISTILLATION_RUNLOG.md` and `docs/DISTILLATION_ROUND5_FINDINGS.md`; this step is compared against them, not tuned to them): Round 3: 1,500 slots, 249 valid tasks, 157 teacher-verified. Curriculum G: 1,500 slots, 140 audited, 83 verified, 79 kept after dedupe. K2: 1,300 slots, 135 valid, 79 verified, 74 kept; its rejects were gold errors (570 of 1,300), duplicates within the batch (294), unparseable replies (182) and ungrounded values (106), from `sft/data/distill/k/author.out`.

**Limits stated up front.** (a) A task is kept only if the teacher verifies it in at least one of four episodes, so the yield is the yield of teacher-solvable tasks, not of useful training tasks. (b) The signature rule and the within-batch duplicate rule depend on the size of the held-out banks and of the batch, so rates measured at 2,000 slots do not extrapolate linearly. (c) Dropping both sides of a conflicting prompt removes exactly the states where the teacher is unstable. (d) Rows per task (at most 2 samples) and stop share (cap 25%) are design parameters, not measurements. (e) The token audit measures JSON-only rows without the think marker or reasoning; reasoning was 84% of supervised tokens in Round 3 (`docs/DISTILLATION_RUNLOG.md` line 102), so these lengths understate native training lengths and part 2 must re-measure. (f) The prompts of these rows contain earlier assistant turns as the teacher wrote them; the report counts rows whose history is not a bare JSON list. (g) The spend ledger counts logged successful responses; requests that failed or were retried may be billed without appearing there, so spend is also checked against the OpenRouter usage page by Sans if the total approaches the cap.

## 4. What is measured (all counted from files; ratios with 95% Wilson intervals)

* **Funnel:** slots, valid authored tasks (with reject reasons and repair rounds), gold-audit survivors, tasks with at least one checker-verified teacher episode, per-episode and greedy verification rates, tasks surviving the held-out filter (by drop kind), rows (train/valid), rows per task, stop share, look-up share, dropped-row counts by cause.
* **Spend:** from the per-call `cost_usd` in `calls.jsonl` (smoke, author, solve): total, per kept task, per row, tokens, number of calls with no reported cost, API model and provider strings.
* **Diversity of the kept tasks:** distinct gold signatures and the largest repeat, per-backend coverage, turn counts, gold calls per task, the five most common first-turn 3-word openings and the top-1 share, within-set near-duplicate pairs (any shared 8-gram or turn ratio at least 0.85).
* **Row format:** structure (system first, then alternating user/assistant ending with assistant), no empty message, target is a strict JSON list of `{"function_name", "parameters"}` objects with no code fence, `n_calls` and `action` agree with the target, meta keys present, no think marker yet (it is added at training-set build time by `sft/add_think_marker.py`), no identical prompts with conflicting targets, no duplicate (episode, step), token-length audit with the Gemma tokenizer (from the build log).

## 5. Acceptance criteria (pipeline soundness; set before any data)

These decide whether the pipeline is trustworthy enough to scale. They say nothing about whether the data will improve the model.

* **E0 Sufficient evidence (precondition for every other criterion).** At least 40 kept tasks, at least 100 train rows and at least 10 validation rows after conflict dedupe (registered minimums; set before any data). If E0 fails, the step is **inconclusive**: the funnel is reported and nothing is certified, and no acceptance flag may be read as a pass.
* **A1 Task accuracy (independent review).** (Power is low: with 40 tasks and at most 2 WRONG allowed, a pipeline whose true WRONG rate is 10% still passes about 22% of the time, 5% about 68%, 15% about 5% [analysis, binomial]; the Wilson upper bound is reported with the verdict and a pass is worded "no evidence of a high error rate", never "accurate". The review sample shows the full initial state, up to 6,000 characters, and what each gold call returned when re-run.) A seeded random sample of 40 kept tasks (requires E0, so there are always 40) is judged by two independent reviewers who do not see each other's verdicts: Codex (`gpt-6.1-sol`, medium) and a Thesis-bot subagent. For each task and turn: does the gold call sequence do what the user turn asks, using only values the user, the initial state or earlier results provide? Verdicts FAITHFUL, AMBIGUOUS, WRONG. **Pass: at most 2 of 40 WRONG per reviewer.** Any task either reviewer marks WRONG is quarantined from later use and listed. More than 2 WRONG for either reviewer fails the step: the pipeline is not accurate enough and nothing scales until the cause is found.
* **A2** Rows come only from checker-verified episodes (valid, no API error) of tasks in the held-out-filtered kept set. Zero API-error episodes used.
* **A3** Row-format conformance: zero violations, zero identical-prompt/conflicting-target pairs, zero duplicate keys.
* **A4** Exactly one API-reported model string, equal to `deepseek/deepseek-v4.1-flash-1017`, and exactly one provider (DeepInfra).
* **A5** Every call has a reported cost and the total is at most $5.00.
* **A6** Authoring slots lost to API errors or the deadline are at most 2%, and the solve step was not stopped early by its budget or time limit.
* **Provenance** `check_provenance.py` exits 0.

Not criteria (reported, no threshold): the funnel rates, diversity numbers and costs. A projection to a larger set is labelled [analysis] and uses the lower end of the 95% intervals.

## 6. Part 2 (after stage 1 ends; needs the local server, separate reviewed script)

Registered here so the plan is complete; not started, and needing Sans's go:

* **Render parity** on 100 random rows: the prompt as tokenised for training (Gemma chat template plus the added think marker) equals the prompt the server renders for the same request (`/apply-template` and `/tokenize`, exactly one think marker), in the manner of Round 5's A1 probe, which compared rendered prompts between a Q4 and a BF16 server (70 of 70 identical); trainer-versus-server parity itself is what `sft/add_think_marker.py` claims to have checked against `/apply-template`, and part 2 re-checks it, including the history turns.
* **Training-render consistency:** for the same rows with a native assistant message, the supervised span begins exactly where the server's generation prompt ends.
* **Native conversion throughput and agreement** on 100 verified teacher steps: fraction where the student's own greedy reply already equals the teacher action, and the keep rate and speed of hint-free student reasoning (Round 4 Stage B kept 60 of 166 recovery candidates hint-free before the strict-JSON filter and 45 after it, `docs/DISTILLATION_RUNLOG.md` line 98 and `docs/DISTILLATION_ROUND4_FINDINGS.md`; Round 5's 2,832 sampled generations took 3 h 28 min, i.e. about 13.6 per minute by division [analysis]). This sizes the real bottleneck of any scale-up.

## 7. After the check

Results go to `docs/DATA_YIELD_FINDINGS.md` with every number tied to its file. The scale-up decision (how many tasks, which row format, whether to add public data, what budget) is Sans's, made from the funnel, the reviews and part 2. A public-dataset shortlist (licence, multi-turn share, BFCL contamination, refusal share) is a separate document-only task that needs no Mac time.

Codex reviews this plan, the scripts and, afterwards, the report and the sample verdicts (`sft/codex_review.sh`, major problems only, at most two rounds per step).
