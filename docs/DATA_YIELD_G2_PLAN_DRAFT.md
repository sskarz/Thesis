## 1. Target and sizing (advisor recommendation: 400 surviving tasks, $15 cap)
Measured rates from yield Part 1 (all [DOC]: `YIELD_REPORT.json`, `author/report.json`, `docs/DATA_YIELD_FACTORY_FIX.md`, `THESIS_PROGRESS.md`):
* authoring 12.5 slots/min (1 process, 4 workers); authoring cost $1.89 per 2,000 slots = $0.000945 per slot;
* 181 valid tasks of 1,819 attempted slots (9.95%); audit + teacher solve of those 181 cost about $0.22 ($0.0012 per valid task) [analysis: total $2.109 minus authoring $1.89];
* 99 kept after solve and held-out filter (5.44% of attempted slots); 71 of 99 survive the factory-fix filters (71.7%), i.e. 71 / 1,819 = 3.9% of attempted slots;
* judge $0.0128 for 99 tasks.

Arithmetic [analysis] for N = 400 surviving tasks: slots = 400 / 0.039 = about 10,300. Authoring cost = 10,300 x $0.000945 = $9.7. Valid tasks about 1,025 (9.95%), audit + solve about $1.2, judge about $0.14. **Expected total about $11.1; cap $15.** Expected yield has a wide interval: the 3.9% rests on 71 tasks from one run (Wilson 95% about 3.1% to 4.9% of attempted slots [analysis]), so 400 survivors could realistically land between about 320 and 500.

## 2. Three parallel authoring processes: what breaks and what does not
Read from `benchmark/distill_tasks.py:author()` and `sft/yield_author.py` (code read, not run):
1. **Task ids.** Ids are `{prefix}_{slot:04d}`. Three processes need three prefixes (`distill_g2a`, `distill_g2b`, `distill_g2c`), 3,434 slots each (under the 4-digit limit). `yield_merge.py` refuses duplicate ids. **Needs a change:** `sft/sample_for_review.py` refuses any id that does not start with `distill_y_`; it must accept the new prefixes.
2. **Seeds.** Slot plan = `random.Random(seed)` and anchor rotation `(slot + seed) % 9`. Seeds 7101, 7102, 7103 give independent streams. Fine.
3. **Duplicate detection (the real issue, and a yield risk at scale).** In Part 1 `dup_in_batch` was already the largest single reject reason: **394 of 2,000 slots (19.7%)** with only 181 tasks accepted [DOC: `author/report.json`]. The rule compares each candidate with every accepted task, so the rejection rate can only rise as the accepted pool grows (the topic list and the 9-backend anchor rotation are fixed). At about 1,000 accepted tasks the yield per slot could fall noticeably below Part 1's, which is not reflected in the 3.9% used for sizing. I cannot quantify it from the record; the 3-process smoke does not show it either (it is small). The honest statement is that the 400-task target is an estimate from a pool 5 times smaller, and the run report will show the dup share as it grows.
   Details: Inside one process a candidate is rejected if its user turns share any 8-word n-gram with an earlier accepted task or with the `--existing` files. Processes cannot see each other's accepted tasks (the output file is written only at the end). So cross-process duplicates are not caught during authoring. **Fix, tested offline:** `sft/yield_merge.py` applies the same rule across the merged files in a fixed order (first process wins) and lists every drop (`test_yield_merge.py` passes). Each process also gets `--existing` = Part 1's `tasks_raw.jsonl` plus the held-out banks' task files, so new tasks cannot duplicate Part 1. The merge must run before the audit and the solve, so no paid solve is spent on a duplicate.
4. **Cost guard.** `GuardedClient` limits (cost cap, first cost-less response) are per process (class-level flags in separate processes). The total cap is therefore the sum of the per-process caps; set 3 x $3.60 = $10.8 for authoring (expected $9.7), solve cap $2.4, judge $0.4, total $13.6 plus Part 1's $2.11 and judge $0.0128 already spent; the preflight in `data_yield_lib.sh` has `TOTAL_CAP_USD=5.0` hard-coded and an arithmetic check `earlier + 3.65 <= cap`; both must be rewritten for the new caps (Sans raised the API cap to $50 overall).
5. **Rate limits: unknown, not tested.** Part 1 ran 4 workers in one process; the authoring report lists no `api:` rejection among its reasons and the solve had 0 API-error episodes. Three processes x 4 workers = 12 concurrent requests to the same provider (DeepInfra via OpenRouter) is 3 times the tested load. I did not test it. Proposed first step: a 3-process, 12-slot smoke (about $0.02 [analysis]) that must show 0 API errors and every response reporting a cost, before the full run; if errors appear, drop to 2 workers per process.
6. **Deadline.** Per process 3,434 slots at 12.5 slots/min = 275 min; with 25% slack **343 min** (the A6 criterion is at most 2% of slots lost to the deadline). If the three processes share an API limit and each slows, A6 will fail again and the run is shorter than planned; the report will say so. Hard external `timeout` per process: 6.2 h.
7. **Memory/CPU on the Mac.** Authoring is API-bound. It would run alongside G1 (GPU) at `nice 10`; Part 1 showed no interference with the stage 1 chain. G1 training peaks near 44 GiB on a 48 GiB machine with 7 GB swap already in use, so I would keep the authoring processes to a few hundred MB each and watch swap; this is a risk to G1's speed, not to its correctness.
